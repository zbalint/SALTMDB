  2. Real naming collision between G4 and G8, both named expansion_truncated.
          G4's is a fan-out/node-eligibility signal; G8's is a token-budget/payload-size signal — the map
          itself says these are independent axes, but both were given the identical flat field name in
          two different resolution write-ups. Flattened, they'd silently shadow each other. Fix applied
          here: namespace them as metadata.fan_out.expansion_truncated vs.
          metadata.budget.expansion_truncated — toggle both free-play buttons independently

  3. G7's "extends G4's expansion_truncated signal" reading, applied literally:
          conflict-set-cap truncation is reported at metadata.fan_out.conflict_sets_truncated
          (same family as the general fan-out cap), not a third independent truncation flag.
    4. 
        
  4. Resolved conflicts fully vacate conflict_sets. Read literally, G7 says a
          lifecycle-resolved conflict surfaces "via the ordinary lineage path, NOT the conflict reserve" —
          taken at face value, that means it doesn't appear in conflict_sets at all once
          resolved, only in lineage. That has a real cost: the fact that two memories were
          ever explicitly flagged contradicts (not just superseded) disappears from the
          response. This was the open gap in memory 8cd3413f — now closed, see the
          next two items for the locked, prototyped shape.
    5. 
        
  5. [ce08d466] was_flagged_contradiction/contradicted_with nest as
          sibling keys on the specific entry object, never head-only. Ticket 2a5c1357 locked the
          policy (per-entry, exact-edge-only, never transitive/component-level); this revision settles the
          literal shape: both lineage[head].current and every
          lineage[head].historical[i] are entry objects ({id, title, ...},
          historical[i] additionally carrying archived_at), and whichever
          one was literally a contradicts-edge endpoint gets
          was_flagged_contradiction: true + contradicted_with: [<entity_id>,
          ...] added as sibling keys on that entry — never hoisted to the head. This required
          promoting lineage[head].current from a bare id string (the shape locked by the
          original schema-prototype ticket) to an entry object matching historical[i]'s
          shape, since current is exactly as likely to be the flagged endpoint as any
          historical entry — see the contradiction walkthrough, where current
          (synthetic-budget-new) carries the flag. Exact-edge matching is scoped against the
          full chain (current + every historical entry, capped or not) — see next item for why.
    6. 
        
  6. [ce08d466] historical_truncated + historical_dropped_count land as
          siblings directly on lineage[head], alongside current/
          historical — matching the <name>_truncated +
          <name>_dropped_count pattern G4/G8 already established for
          metadata.fan_out/metadata.budget, not a new naming convention. Ticket
          0ca97ddc's cap of 5 (keep-most-recent) is applied in this prototype's extended contradiction
          scenario: the resolved chain now runs 6 synthetic revisions deep (mid5…mid1, then
          synthetic-budget-old), so the cap drops exactly the oldest one —
          synthetic-budget-old, the very entry current is flagged as
          contradicting. Confirmed live in this run: historical_truncated: true,
          historical_dropped_count: 1, and current.contradicted_with still
          names synthetic-budget-old even though no entry for it appears in the (capped)
          historical array — the contradiction signal survives its own referent's
          entry object being truncated away, since exact-edge matching runs against the full untruncated
          chain before the cap is applied for display. This is a deliberate, examined consequence of
          0ca97ddc's own stated assumption ("keep-most-recent retains a resolved conflict's flagged
          entries by construction — they're necessarily recent") holding only loosely: a chain can keep
          accumulating unrelated revisions after a contradiction is resolved, eventually pushing the
          flagged historical peer past the cap. Not reopening 0ca97ddc over this — the signal loss is
          confined to the truncated entry's own title/archived_at metadata, not
          the fact-of-contradiction itself, which is exactly the graceful-degradation behavior a fixed,
          low-stakes cap should have.
