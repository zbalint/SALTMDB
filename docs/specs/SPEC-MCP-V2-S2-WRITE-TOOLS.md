## 1. Why

`store_memory` mixes create and update and hides conditional core fields behind 15 parameters; `merge_tags` accepts a list or a comma string; `update_memory_metadata` cannot delete a key. The review of the first draft showed that the list-based `archive_memory` and `manage_relation` are NOT a shape-only change: the bulk services report failures as a single error string with no item index or code, `bulk_archive_memory` drops the per-item owner check and the resolved id, and the relation batch loses community detection and the original rejection codes. Those two tools are therefore a separate slice (S2b) with their own service work. This slice stays at the adapter plus one small service change.

## 2. Decisions

- D1 `store_memory` becomes CREATE-ONLY. Parameters (10): `title: str`, `content: str | None`, `content_file_path: str | None` (exactly one of the two; both or neither is rejected exactly as today; the description says the path must be readable by the SALTMDB server host), `tags: list[str] | None = None` (fixes the latent bug: an explicit `null` is accepted as "no tags"), `memory_type`, `scope`, `context_id`, `metadata: dict | None`, `retrieval_text: str | None = None` (the `_RETRIEVAL_TEXT_UNSET` sentinel class is deleted; the internal `retrieval_text_provided` flag becomes `retrieval_text is not None`), `core: CoreInput | None = None`. The parameters `entity_id`, `is_core`, `core_reason`, `core_exit_condition`, `core_review_after`, `detail_memory_ids` are removed; `parse_is_core` is no longer called by the tool. `CoreInput` is a pydantic model with `extra="forbid"`: `reason: str`, `exit_condition: str`, `review_after: str | None = None`, `detail_memory_ids: list[str] | None = None`. The adapter calls `model_dump()` on it at the boundary (before validation, `corrected_call` construction and the RPC payload, so only plain dicts reach them), maps it to the unchanged internal keys (`is_core=True`, `core_reason`, `core_exit_condition`, `core_review_after`, `detail_memory_ids`), and sends `is_core=None` when `core` is absent (create with `None` is an ordinary memory and inherits nothing; the developer confirms this with a baseline test). A direct Python call may pass `core` as a `CoreInput` or as a dict; the schema constraints (`extra="forbid"`, required `reason`/`exit_condition`) are enforced on the MCP path and tested there. Length limits, capacity and overdue-review rules and their error codes stay in the service. The service's own `entity_id` update path stays (S3 uses it); only the tool stops exposing it. YAML front-matter rejection and duplicate detection behave exactly as today (`data.duplicate_candidates` and the `NEAR_DUPLICATE` warning stay, because the live nudge hook reads them).
- D2 `store_memory` response: `data.memory_id` replaces `data.id`; the rest of `data` (including `message` and `duplicate_candidates` with its current record keys) is unchanged; nested record keys change only in the slice that owns the record. `_WRITTEN_ID_KEY["store_memory"]` becomes `"memory_id"` in `tools.py` (the trace-link recording reads the new key) and `WRITTEN_ID_KEY["store_memory"]` in `hooks/saltmdb-stop-trace-capture.py` in the same change (the other three entries change in S3). The live hook sources outside the repository have no trace-capture hook, so that coupling does not exist there.
- D3 `update_memory_metadata(memory_id: str, metadata: dict)`: shallow merge as today with ONE behaviour change: a TOP-LEVEL key whose submitted value is `null` is DELETED from the stored metadata (today the null is kept). The rule is shallow only: `{"drift_flag": {"x": null}}` stores the nested null unchanged. Deleting an absent key is a no-op and is not reported as updated or deleted. `{}` stays a successful no-op. The success messages (the developer pins every literal with a test): when only updates happen the current text, `Memory '<id>' metadata updated (<n> key(s): <a>, <b>).`; when both happen `Memory '<id>' metadata updated (<n> key(s): <a>, <b>); deleted (<m> key(s): <c>).`; when only deletions happen `Memory '<id>' metadata deleted (<m> key(s): <c>).`; when nothing was updated and nothing deleted (an empty patch, or only absent keys set to null) the existing empty-patch text of the service is reused unchanged. Core lifecycle keys: the service has NO guard today (any key, including `outcome`, `core_review_after` or `review_rationale`, is stored as an inert metadata key and the core columns are unchanged); this slice keeps exactly that and its tests pin it literally. Ownership: another agent's memory returns `NOT_FOUND` as today. Response `data.memory_id` replaces `data.id`. The service change is confined to `update_memory_metadata`/`_write_metadata_update` in `lifecycle.py`, with its docstring updated (the "no key-deletion sentinel" sentence is replaced).
- D4 `merge_tags(keep_tag: str, tags_to_merge: list[str])`: both required, the list non-empty (at most 50, enforced in the schema); the comma-string form is removed (a string for the list is a type error from the schema); the response shape is unchanged (`merged`, `skipped`, `canonical_tag`).
- D5 `log_event`, `search_tags`, `list_predicates` are unchanged.
- D6 Hooks (repository copies only): `hooks/saltmdb-stop-trace-capture.py` per D2; `hooks/saltmdb-checkable-fact-drift-sweep.py` prompt step 4 now tells the sweep agent to call `mcp__saltmdb__update_memory_metadata` with `memory_id=<id>` and `metadata={'drift_flag': {...}}` (no `get_memory` and no resubmission of title, content and tags is needed any more); the sentence forbidding consolidate/revise/supersede stays. `hooks/tests/test_trace_capture_copilot.py` (which builds a `store_memory` transcript result with `data.id` and expects the trace link) is updated, and a NEW hook test `hooks/tests/test_checkable_fact_drift_sweep.py` asserts the new step-4 text (it names `update_memory_metadata` and `memory_id`, it does not tell the agent to call `store_memory` with `entity_id`, and the forbidding sentence is still there). S5 must ship the live drift-sweep (outside the repository) in the same cutover as the server update, because the live copy says `store_memory` with `entity_id`, which becomes `UNKNOWN_FIELD`.
- D7 Errors and field names. (1) The store service reports many validation failures as a bare STRING (for example `Error: content exceeds N`, an empty title, the scope and memory type checks, the retrieval-text normaliser, the `core_reason` and `core_exit_condition` validators, a core-governance rejection with a string payload), and `tests/test_mcp_tools.py` (about lines 188 to 197) pins that string as the tool result today. Decision (the architect's, to keep this slice bounded): the ADAPTER wraps any string result of the store service into `rejected([error("VALIDATION_ERROR", <the string unchanged>)])` with no `field`; the field is NOT parsed out of the message text, and the message text keeps naming the offending parameter. Making the store service return envelopes with a field and code is a follow-up (backlog row). The matching test at about line 196 changes from the string to that envelope (D9 category 0). (2) Dict-shaped errors keep their codes; the adapter remaps ONLY these internal field names to public ones: `entity_id` to `memory_id` (the `update_memory_metadata` errors `VALIDATION_ERROR`, `NOT_FOUND` and `AMBIGUOUS_ID_PREFIX`, the last one keeping its `candidates` and `candidates_truncated` data). Fields that are already public stay: `content` (the content-source errors and the YAML front-matter rejection), `metadata`, `keep_tag`; errors without a field stay without one (`CORE_CAPACITY_EXCEEDED`, the duplicate rejections, `INTERNAL_ERROR`). The `is_core` field of the old adapter parse disappears with `parse_is_core`. The `core_*` names are never fields of dict errors today, so there is nothing to remap for them. Schema (pydantic) errors already carry public paths (`title`, `tags[0]`, `core.reason`).
- D8 The tool descriptions of the three tools are rewritten to rule R5 (the `store_memory` description also says that `retrieval_text` omitted and `null` mean the same, so nobody re-adds the sentinel) (first sentence "Use this when X; use Y when Z", required inputs, side effects/immutability, one minimal example, no policy essays; correctness constraints kept: duplicates, server-host path, null-deletes, shallow-only). `docs/architecture.md` is updated only where it quotes the old signatures.
