## 1. Why

The published tool schema is the interface that every agent uses in every session. Evidence from the usage study and the caller reviews:

- `store_memory` mixes create and metadata update (`entity_id` path that forces a caller to resubmit the unchanged body), has conditional core fields and a sentinel default that leaks into the schema; `consolidate_memories` mixes a single and a batch form with every field optional; `revise_memory` and `supersede_memory` share one field set that gives no help in choosing; bare lists and envelopes mix across tools; unknown fields are silently dropped by the server; `capture_trace_*` are hook plumbing listed as agent tools; core-memory machinery is spread over three tools although no core memory is active today.
- The two S107 findings are symptoms of overloaded tools. Nesting fields would hide them; separating intents removes them. Rejected: a FastMCP `__signature__` override or a hand-registered flat model (hides the parameter list, uses private API), a Sonar exception (the real fix exists), leaving the schema as is.

## 2. Decisions

### 2.1 Rules (apply to every tool)

- R1 One intent per tool; required fields are required in the schema; no field that only matters in another mode.
- R2 Flat short fields. A nested typed object only for a cohesive group (`core`, batch items). JSON-schema `$defs`/`$ref` produced by nested pydantic models is allowed (three client families showed such schemas usably); `oneOf`/discriminated unions are NOT used (client rendering unverified). `metadata` is the only free-form object.
- R3 Unknown fields are rejected, naming the field and listing the valid fields. Implemented by a `FastMCP` subclass overriding the public `call_tool`: the allowed keys come from the tool's published `inputSchema` properties (cached), unknown top-level keys and unknown tool names produce a rejection envelope (a removed tool name gets the replacement from an old-to-new map), nested models use `extra="forbid"`. A guard test proves the override is the code path that runs. Slice S1 first verifies what rejection exists today at each layer (the backlog item BL-010 refers to an earlier unknown-argument change; the studies observed a silent drop at the FastMCP layer) and records it. Free `metadata` keys stay free. The existing corrected-call helper is signature-derived and top-level only; slice S1 extends it to nested models (`core`, batch items).
- R4 One envelope for every tool, success or failure: `{"status": "ok"|"rejected", "data": {...}, "warnings": [...], "errors": [{"code", "message", "field", "corrected_call"|"corrected_calls"}]}`; `errors` is `[]` on success; empty results are `data` with empty lists, never a bare list; list tools return `data.items` plus `data.next_cursor` (and `data.has_more`); `corrected_call` is one structured call object (built from the tool signature, reusing the existing corrected-call helper); `corrected_calls` is a list of alternatives (used by `CORE_DECISION_REQUIRED`). A business rejection is a normal tool result with `status: "rejected"` (as today); only protocol or internal failures use the MCP error flag, and they also carry the envelope with code `INTERNAL_ERROR`. Mechanism: a tool function returns a dict and cannot set the flag, so the `call_tool` override converts an `INTERNAL_ERROR` envelope (and any exception) into a `CallToolResult` with `isError=true` whose content is the envelope; today internal faults are ordinary results such as a one-item error list, which no hook or source code depends on as an MCP error flag. An internal failure never becomes a successful empty result.
- R5 Descriptions: first sentence "Use this when X; use <other tool> when Z", then required inputs, side effects/immutability, inheritance and bounds, one minimal example. Policy (core-memory caps, tag etiquette) lives in the skills, not in descriptions. Target about 1000 characters; correctness constraints are never cut to meet the target (for example: a strict-mode empty result is abstention, not proof of absence; compact hits are not full content).
- R6 Alpha: old names and fields are removed outright; a stale call gets a rejection that names the replacement. No aliases.
- R7 Batches (`consolidate_memories`, `archive_memory`, `manage_relation`) are atomic per request: any failed item rejects the whole request with zero changes, the error names the item index and field path (for example `items[1].title`), success returns `data.items` in request order, `data.items` is empty on rejection. A single item is a batch of one. Reads with several ids (`get_memories`) are not atomic: each item carries its own status. Failure mechanism: the adapter cannot hold a database transaction (the daemon owns the database), so every batch is one daemon request that validates, then writes inside one transaction.
- R8 Naming: `memory_id`/`memory_ids` (the word `entity` retires from the agent surface), `parent_memory_ids`, `query` (was `query_keywords`), responses use `predecessor_memory_id`/`successor_memory_id` where two ids appear, `limit` and `cursor` on every list tool (`get_events` loses `offset`), tags accepted with or without a leading `#` everywhere (this is today's behaviour, the tag-name normaliser already prefixes `#`; the rule is unchanged and only legacy rows may still hold an unprefixed spelling), `merge_tags` takes lists only. An id argument accepts a full UUID or a unique prefix; an ambiguous prefix is a rejection listing candidates.
- R9 Renames are adapter-level: the adapter maps public names to the existing internal names (`memory_id` to `entity_id`, ...), and RPC method names stay. The BEHAVIOURS below are not renames and DO change the service or the daemon; each belongs to the scope of its slice: atomic list-based `archive_memory` (the service takes one id today; atomicity needs a service function that archives a list inside one daemon-held transaction), `core`/`demote_core`/`CORE_DECISION_REQUIRED` and `retrieval_text` on `revise_memory`/`supersede_memory` (`_ReplacementRequest` has no core or retrieval-text input today), `update_memory_metadata` null-deletes-key (today a null is kept as a value), the new `get_memories` and `set_core_memory` entry points (today promotion runs through the `store_memory` entity-id path), `has_more`/`next_cursor` in list results, `get_events` cursor instead of offset, and the new envelope fields.

### 2.2 Write tools

- D1 `store_memory` (create only): `title`, `content` XOR `content_file_path` (exactly one; the path must be readable by the SALTMDB server host and the description says so; both or neither is rejected), `tags`, `memory_type`, `scope`, `context_id`, `metadata`, `retrieval_text`, `core?` (about 10 parameters). The `entity_id` update path and the core fields move out. Duplicate detection keeps its current shape exactly (exact duplicate rejected with the existing entity named; near duplicates returned in `data.duplicate_candidates` AND a `NEAR_DUPLICATE` warning with the same detail payload), because the live nudge hook reads both; any change to that shape updates the hook in the same slice.
- D2 `update_memory_metadata(memory_id, metadata)`: shallow merge; a `null` value deletes the key (replaces the old "cleared marker"). Core lifecycle keys stay governed by the core tools.
- D3 `revise_memory` and `supersede_memory` stay two tools with ONE shared field set: `memory_id`, `title`, `content` XOR `content_file_path`, `tags`, `reason`, `scope`, `memory_type`, `retrieval_text`, `repoint_relations`, `context_id`, `core?`, `demote_core?` (13 parameters). First sentences: revise = "the stored memory was wrong or badly worded when written"; supersede = "it was true then, the facts changed since". Omitted `tags`, `scope`, `memory_type`, `context_id` (and `metadata`, `agent_id`, which are not caller inputs) inherit the predecessor's value, as today (verified in the lifecycle code; the implementation spec pins each with a literal baseline test). `retrieval_text` is new as a caller input on these tools: omitted means none, as on create (it is NOT inherited, because the content changed), and the description says so. The response carries `predecessor_memory_id` and `successor_memory_id`.
- D4 `consolidate_memories(items, context_id?)`: `items` is a required list (at most 20) of `{parent_memory_ids, title, content XOR content_file_path, tags?, scope?, override_justification?, context_id?, core?, demote_core?}`; atomic per request (R7); `weight` is removed from the agent schema (the stored column stays internal with default 1 because full-text ranking multiplies by it); parents of different items must be distinct (an earlier item that archives a shared parent already aborts the batch today; this makes the rejection explicit and early); the cohesion gate and its `override_justification` escape hatch are unchanged.
- D5 `archive_memory(memory_ids)` list-based and atomic; repeat of an already archived id is a declared no-op warning, an unknown id rejects the whole request. `manage_relation(relations)` required list (at most 100) of `{source_id, target_id, predicate, invalidate?, valid_at?, invalid_at?, override_justification?}` and atomic; the single-form fields are removed. `merge_tags(keep_tag, tags_to_merge: list)`. `log_event` unchanged (envelope).
- D6 Core (existing semantics preserved, surface reduced):
  - `core` on `store_memory`, `revise_memory`, `supersede_memory` and consolidation items is an object `{reason, exit_condition, review_after?, detail_memory_ids?}`; presence means "the result is core", absence means ordinary. There is no tri-state and nothing depends on telling an omitted field from a null.
  - If any predecessor or parent is an ACTIVE core, the call must carry EITHER `core` (declare the result's core) OR `demote_core: true` (flat boolean; atomic with the write; mutually exclusive with `core`, both together is rejected). Otherwise it is rejected with `CORE_DECISION_REQUIRED` and `corrected_calls` for both options (the keep option pre-filled with the predecessor's current declaration). A failed write never leaves a parent demoted. Non-core predecessors: absent `core` = ordinary.
  - Two tools for EXISTING memories: `set_core_memory(memory_id, core)` promotes a non-core memory or edits a core memory's declaration (`reason`, `exit_condition`, `detail_memory_ids`); `review_core_memory(memory_id, outcome: retain|demote|archive, review_rationale, core_review_after?)` reviews (`core_review_after` is only set here). The existing capacity limits, the overdue-review block and their error codes stay.

### 2.3 Read tools

- D7 `search_memory(query?, limit?, cursor?, context_id?, agent_session_id?, tags_filter?, memory_type_filter?, is_core?, include_related?, mode?, detail?, return_diagnostics?)`: returns `data.items` of COMPACT hits by default: `memory_id`, `title`, `snippet` (about 200 characters), `score` (the description says what it means), `memory_type`, `status`, `successor_memory_id` when not active, `is_core`, `created_at`, `drift_flag`; `detail: "preview"` opts in to the longer preview; `mode` values (`broad`, `strict`, `history`) are documented in the field description, strict-empty means abstention; the `is_core` filter trap stays documented; `has_more` and `next_cursor` replace "page until empty".
- D8 `get_memory(memory_id, detail?: "full"|"summary", include_trace_provenance?)`: the default is `full` (a forgotten argument never returns a snippet that gets cited as fact); `summary` is what `inspect_memory` returned. `get_memories(memory_ids, detail?)`: at most 20 ids, results in request order, per-item `status` (`ok`, `not_found`, `ambiguous`, `forbidden`), duplicate ids rejected. `inspect_memory` and the `memory_id` alias of `get_memory` disappear (the name is now the parameter).
- D9 `get_lineage(memory_id, direction?, max_depth?)` kept (bounded node and edge traversal); `get_related_memories(memory_id, max_depth?, direction?, include_inspect?)` kept; `retrieve_context(memory_ids, budget_tokens?, strategy?)` keeps only the id-anchored mode (the query mode is removed: find anchors with `search_memory`, then expand); all enter the envelope.
- D10 `get_events` (`offset` becomes `cursor`), `search_traces`, `get_trace`, `search_tags`, `list_predicates` enter the envelope with uniform `limit`/`cursor`.
- D11 `capture_trace_start`, `capture_trace_memory_link`, `capture_trace_complete` leave the agent tool list and remain daemon methods called by hooks only. The 22 remaining tools: `log_event`, `get_events`, `search_tags`, `list_predicates`, `merge_tags`, `store_memory`, `update_memory_metadata`, `revise_memory`, `supersede_memory`, `consolidate_memories`, `archive_memory`, `manage_relation`, `set_core_memory`, `review_core_memory`, `search_memory`, `get_memory`, `get_memories`, `get_lineage`, `get_related_memories`, `retrieve_context`, `search_traces`, `get_trace`.
- D12 Dropped capabilities (recorded so nobody re-opens them by accident): the in-place `retrieval_text` change (never observed set to a non-default value; a change goes through `revise_memory`/`supersede_memory`, and a dedicated tool can be added later without breaking anything), `weight` as an agent input, the `store_memory(entity_id=...)` update path, a dedupe-only check tool (exact duplicate rejection and near-duplicate warnings on create already cover it).

## 4. Tests

Every implementation slice carries the contract matrix below, using raw public MCP calls (not only Python functions) against the live server object:

- Shared strict-validation tests for EVERY tool: top-level and nested unknown fields, removed names and fields with a replacement-naming rejection, wrong types, enum errors, explicit null, missing fields, several simultaneous errors, bounded arrays/strings/depth, coercion policy (the lax pydantic coercion of numbers and booleans stays; the description of each field states the expected type), duplicate ids, unique-prefix ambiguity.
- Envelope tests: every tool returns the envelope; business rejections are normal results with `status: "rejected"`; internal failures carry `INTERNAL_ERROR` and the MCP error flag; empty result versus failure; cursor exhaustion, invalid and filter-mismatched cursors; deterministic ordering.
- Atomicity: validate the whole batch and also inject a failure after an earlier write; rows, parent status, tags, edges, core capacity and embedding/indexing side effects stay consistent; late rejection leaves zero changes.
- Per tool: `store_memory` (both/neither content sources, inaccessible server path, duplicate rejection, core errors, zero changes on rejection); `revise_memory`/`supersede_memory` (inactive or ambiguous target, inheritance versus override per field, `repoint_relations` on and off, the core decision, unambiguous predecessor/successor ids); `consolidate_memories` (minimum distinct parents, cross-item overlap rejected, late-failure rollback, ordered success); `archive_memory` (unknown, duplicate and mixed ids, atomic late rejection, repeat behaviour); `manage_relation` (reserved and unknown predicates, duplicate no-op, invalidate of a missing relation, nested extras, mixed-valid batch rollback); `merge_tags` (missing canonical tag, normalisation collisions, repeats); `update_memory_metadata` (null deletes, unknown memory, core keys refused); `set_core_memory`/`review_core_memory` (required and forbidden fields per tool, state transitions, deadline bounds, repeats, capacity and overdue errors); `CORE_DECISION_REQUIRED` (active core versus ordinary or inactive parents, one core among many, absent declaration, both `core` and `demote_core`, `demote_core: false`, malformed `core`, capacity/overdue rejection, stale pre-filled keep hint; every rejection leaves predecessors unchanged); search and list tools (limits, cursor rules, visibility boundaries); `get_memory`/`get_memories` (full versus summary, large bodies, missing/private/archived targets, prefix ambiguity, ordering, bounds); lineage/related/context (depth and budget bounds, cycles, private-node exclusion, invalid anchors, no silent mode fallback); `get_trace` visibility; `log_event` validation and redaction.
- A coupling test (slice S5) that fails when an old tool or field name remains in hooks, skills, docs or settings examples.
- Mutation pass per slice by the tester, as in the existing workflow.

## 6. Migration and rollout

- M1 One breaking release. The slices land on `develop` one by one (each green, each reviewed). The live MCP install is a separate checkout that the owner updates only after the whole set is done, so running agents see the old surface until then.
- M2 Slice order (each area slice renames AND reshapes its tools together, so no tool is renamed twice):
  - S1 foundation: the `call_tool` override (strict unknown-field and removed-name rejection, `isError` mapping), the envelope for every tool, the corrected-call helper extended to nested models, the old-to-new name map, the raw-MCP contract-test harness, and the inventory list of tool and field names used by the coupling test.
  - S2 write tools: D1, D2, D3, D5 with their renames (`memory_id`, `reason` unchanged, response ids), including the service changes of R9 for `archive_memory`, `update_memory_metadata` and the `retrieval_text` input of replacements.
  - S3 consolidate and core: D4, D6 (the service-layer `CoreDeclaration` and grouping objects already exist), `set_core_memory`, `review_core_memory`, the `demote_core` write path.
  - S4 read tools: D7 to D11 with their renames (`get_memory` drops its `memory_id` alias and takes `memory_id` as THE parameter), `get_memories`, `has_more`/`next_cursor`, the `get_events` cursor, `capture_trace_*` removed from the agent list.
  - S5 sweep: the repository hooks and settings examples (`hooks/`), the LIVE hook sources (see M6), `skills/`, `docs/`, `MIGRATION.md`, the coupling test, and the shared agent instruction sources outside the repository (edited by the owner or architect through the central render procedure, never by hand in generated files). The hook-side changes that a slice forces (for example the near-duplicate reader or the written-id map) land in that slice, not in S5, so the repository hooks stay consistent with the tools.
- M3 After S2 and S3 the two `mcp/tools.py` S107 findings are gone by construction (`store_memory` about 10 parameters, `consolidate_memories` 2). The service-layer `store_memory` (25) and `search_memory` (30) S107 slices then resume and reuse `Provenance`, `CoreDeclaration` and `EntityAnnotations`.
- M4 MCP tool-call telemetry (a counter per tool and per field, no payload) is a separate follow-up so the next redesign has real usage data; it is not part of this release.
- M5 Latent bugs found by the studies, fixed in the slice that touches them: a list parameter declared with a `None` default and no optional type rejects an explicit null; the retrieval-text sentinel string leaks into the published schema.

- M6 Release cutover. The live hooks are a THIRD location: the owner's agent configuration links its hook directory to shared hook sources outside the repository, and those copies already differ from the repository `hooks/` examples (the trace-capture, nudge, common and circuit-breaker hooks all differ). The hooks match tool names and read response keys, so they must switch at the same moment as the MCP install. Cutover checklist (owner action, architect prepares it): update the MCP install to the new release; update the shared hook sources and instruction sources and re-render; restart every MCP client session; verify with the coupling test and a raw-MCP smoke call. S5 records how the repository hooks and the live hook sources are kept in sync (the repository `hooks/` stay the shipped, tested reference).
