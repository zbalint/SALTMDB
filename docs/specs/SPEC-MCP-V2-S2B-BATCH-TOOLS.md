## 1. Why

The review found that the existing bulk services are atomic but report badly: `bulk_archive_memory` raises a bare `RuntimeError` with the first error message (no item index, no code), returns the REQUEST string instead of the resolved id, drops the already-archived state, and never passes the caller's `agent_id`, so the owner check of a single archive disappears; `bulk_store_relations` also loses the original rejection code (`REJECT_LOW_RELATION_SIMILARITY` and the other governance codes become `INTERNAL_ERROR`) and, unlike the single form, never triggers community detection. A list-only public tool cannot be built on those shapes. Rejected: parsing the message text; changing the old bulk functions in place (their existing tests and callers pin the old shapes); keeping a single form next to the list (two shapes per tool, the thing v2 removes).

## 2. Decisions

- D1 `archive_memories(archive_requests, agent_id=None, db_connection=None, db_path=None) -> dict` in `lifecycle.py`: `archive_requests` is a list of id strings (full UUID or unique prefix). One write transaction. Phase 1 (validate, no writes): for every item resolve the id with `resolve_entity_ref` (full UUID or UNIQUE PREFIX, as `update_memory_metadata` does; the single `archive_memory` uses `resolve_entity_id`, which also matches by TITLE and must NOT be copied: a title lookup would silently archive the newest memory of that title), then check existence (`NOT_FOUND`; an ambiguous prefix is `AMBIGUOUS_ID_PREFIX` with its candidates; an empty or non-string item is `VALIDATION_ERROR`). The checks run in the SAME ORDER as the single `archive_memory`: an already archived memory reports `already_archived: true` BEFORE any owner check (so another agent's already-archived memory is not a `CONFLICT`), and the owner check (mismatch is `CONFLICT`) applies only when both the caller's `agent_id` and the stored owner are set; a test pins each of the two rules. After resolution, a second occurrence of the same resolved id is `DUPLICATE_ID`. Every problem is collected with `field: "memory_ids[i]"` (the public name, documented in the docstring) and the original code; if there is any problem the transaction rolls back and the function returns ONE rejected envelope with ALL the errors in item order. Phase 2: archive each item that is not already archived by calling `_archive_entity_unchecked` directly on the resolved id (do not call `archive_memory`, which would resolve again). Phase 1 writes nothing, so a rejection needs no cleanup of vector or job tables. Success: `ok({"items": [{"memory_id": <resolved id>, "already_archived": bool}, ...], "archived_count": n, "already_archived_count": m})`, items in request order; a repeat of an already archived memory is not an error. Requests of more than 50 items are rejected in the schema of the tool; the service accepts any length; an empty list is rejected by the service with `VALIDATION_ERROR` at `memory_ids`.
- D2 `BatchRejected(Exception)` in `utils/envelope.py` carries a list of error entries; the services raise it inside the transaction to roll back and catch it outside to return `rejected(errors)`. An unexpected exception becomes `INTERNAL_ERROR` as in the sibling functions (no stack trace in the message).
- D3 `apply_relations(relations, agent_id=None, db_connection=None, db_path=None, coordinator=None) -> dict` in `relation_service.py`: `relations` is a list of dicts (`source_id`, `target_id`, `predicate`, optional `valid_at`, `invalid_at`, `invalidate`, `override_justification`). One write transaction. Each item runs through the existing `store_relation` / `invalidate_relation` with `_in_transaction=True` (the item's own `invalidate`; no batch-wide flag); a REJECTED item (an envelope rejection) does NOT stop the loop: its errors are collected with the ORIGINAL code and the field prefixed `relations[i].` (an inner field `predicate` becomes `relations[i].predicate`; an error without a field, which most relation errors are, uses `relations[i]`). Later items see the uncommitted writes of earlier items (sequential semantics: an edge created at item 0 makes the same edge at item 3 a `duplicate`). An item that comes back as `INTERNAL_ERROR`, or any moment when the connection is no longer inside the transaction, is NOT collected: the loop stops at once and the batch returns ONE `INTERNAL_ERROR` (an SQLite fault can roll the transaction back by itself, after which later items would commit in autocommit mode and break the zero-change guarantee). After the loop, any collected rejection rolls the whole batch back and returns ONE rejected envelope with all errors in item order and zero changes. The function ignores any per-item `agent_id` (the owner identity comes only from the caller's `agent_id` argument, which the adapter injects). An already-invalidated edge is an `ALREADY_DONE` success that counts as `duplicate_count` with `status: "duplicate"`. Success: `ok({"items": [...], "created_count": n, "duplicate_count": m, "invalidated_count": k})` where each item is `{"status": "success"|"duplicate", "source_id", "target_id", "predicate", "action": "store"|"invalidate", "result": <as today>}` (`source` and `target` are renamed to `source_id` and `target_id` in this new shape). After a successful commit that created or invalidated at least one edge, community detection is triggered ONCE, outside the write transaction (a trigger inside would let the background pass race the uncommitted batch), with the arguments the single form uses (`db_path`, `coordinator`). This is a deliberate narrowing of the single form, which triggers after ANY non-exception return, including a gate rejection or a duplicate no-op: the batch triggers only when it changed the graph.
- D4 `dispatch.py`: `_dispatch_archive_memory` gets `mode == "batch"` (reads `archive_requests`, passes `agent_id=kw.get("agent_id")`, calls `archive_memories`); `_dispatch_manage_relation` gets `mode == "batch"` (reads `relations`, passes `agent_id` and `coordinator`, calls `apply_relations`). The old modes and branches stay untouched, so dispatch-level callers and tests keep working.
- D5 `archive_memory(memory_ids: list[str])` tool: required, `Field(min_length=1, max_length=50)`; annotated `-> dict`; sends `mode: "batch"` with `archive_requests` and the injected `agent_id`; returns the service envelope unchanged (its field names are already public). The single-id form, the omitted-id form and the mixed return shapes are gone; the description and docstring lose every sentence that teaches the old shapes.
- D6 `manage_relation(relations: list[RelationInput])` tool: required, `Field(min_length=1, max_length=100)`; annotated `-> dict`. `RelationInput` is a pydantic model with `extra="forbid"`: `source_id: str`, `target_id: str`, `predicate: str`, `valid_at: str | None = None`, `invalid_at: str | None = None`, `invalidate: bool = False`, `override_justification: str | None = None` (a per-item `agent_id` is an unknown field now). The adapter calls `model_dump()` on every item at the boundary (a direct Python call may pass dicts or models). The pre-flight `_validate_relation_batch` (predicate vocabulary gate with `corrected_call`) stays, with error fields `relations[i].predicate`; `_validate_relation_single` and the single-form parameters (`source_id`, `target_id`, `predicate`, `invalidate`, `valid_at`, `invalid_at`, `override_justification` at the top level) are removed. It sends `mode: "batch"` with `relations`, the injected `agent_id` and no other keys.
- D7 Existing tests: the authorised assertion changes are exactly these categories, enumerated in the developer report: (a) adapter `tools.manage_relation(source_id=..., target_id=..., predicate=...)` calls become `relations=[{...}]` and their expected results follow D3 (about 35 call sites, 25 of them single-form, in `tests/test_mcp_tools.py` and the other files a grep of `tools.manage_relation` finds); (b) adapter `tools.archive_memory(entity_id=...)` calls (about 2 sites) become `memory_ids=[...]` and follow D1; (c) tests that assert the removed docstring sentences or the removed single-form validators; (d) `tests/test_mcp_guard.py`: remove the now stale `_SKIP_REASONS` entries for `archive_memory` and `manage_relation` (both tools now have a required, non-null field, so the generic matrices cover them) and replace those two tools in `test_output_schema_rejections_pass_lowlevel_validation` by other tools that still have the output-schema wrapper (or note that the case no longer applies); (e) one new dispatch-level assertion in the style of `tests/test_phase3_mcp_surface.py` that `mode == "batch"` forwards the coordinator for `manage_relation` and the caller's `agent_id` for `archive_memory`. NOT edited: service-level and dispatch-level tests (`tests/test_relation_service.py`, the `bulk_*` tests, dispatch tests), because the old functions and modes stay. (f) `tests/test_mcp_guard.py::test_guard_result_matches_fastmcp_conversion_for_plain_and_wrapped_tools`: the wrapped representative `archive_memory` is replaced by `store_memory` (`isinstance(actual, tuple) == (name == "store_memory")`), because `archive_memory` loses its output wrapper (D5, D8; amendment 1); (g) `tests/test_mcp_tools.py::test_bulk_item_agent_id_overrides_are_removed_before_dispatch`: the `manage_relation` half, which submitted a per-item `agent_id` and expected it stripped, is replaced by two checks: a raw `mcp_contract` call with a per-item `agent_id` is rejected as `UNKNOWN_FIELD` at `relations[0].agent_id` with nothing dispatched, and a direct `tools.manage_relation(relations=[{...}])` call with a plain dict item (no `agent_id`) reaches the backend as the `model_dump()` of `RelationInput` with the injected top-level `agent_id`; the `consolidate_memories` half stays unchanged (amendment 1). - D8 New tests (literal expected values; zero-change assertions on entity status, relation and event counts for every rejection): `tests/test_batch_services_v2.py` for the two services: archive (empty list gives `VALIDATION_ERROR` at `memory_ids`, unknown id in the middle, ALL errors reported in order, resolved id returned for a prefix, an ambiguous prefix gives `AMBIGUOUS_ID_PREFIX` with candidates, a TITLE is not accepted as an id (`NOT_FOUND`), duplicate by prefix and full id gives `DUPLICATE_ID` at the second index, an already archived memory of another agent reports `already_archived: true` and not `CONFLICT`, repeat of an archived id gives `already_archived: true`, mixed active/archived, ownership `CONFLICT` for another agent's memory, nothing archived when any item fails, success order);
