## 1. Why

The repository has no property-based or fuzz tests. Example-based tests cover the inputs their authors thought of; the two input boundaries that take untrusted text (the daemon's length-prefixed JSON frames, and the text that becomes an FTS5 query) deserve tests that generate hostile inputs. Groundwork on `develop` at `b6f61cc` (the relevant code is unchanged at `c4b3950`) (probes with Hypothesis 6.170.9 from a scratch environment, an in-memory SQLite table, a fake socket; no `saltmdb.db` opened):

1. `protocol.recv_frame` is documented to raise `FrameError` on any malformed input, and every daemon caller catches only `(OSError, FrameError)` (`daemon/server.py` lines 689, 711, 778). A frame whose JSON body is nested 200000 levels deep (about 400 KB, far under the 32 MiB cap) raises `RecursionError`; a body with an integer of 5000 digits raises `ValueError` (Python's integer-string conversion limit). Neither is caught. Traced effect today: the handler thread of that connection ends in an uncaught exception, `socketserver` prints a traceback to stderr and drops the connection, the `finally` in `_session_loop` still unregisters the session, and `_handle_probe_connection` releases its semaphore and closes the socket; the daemon survives and no state leaks. The client side has the same weakness: `server.py` line 802 (`_probe_identify`) and `client.py` lines 221, 428, 594 and 911 catch only `(OSError, FrameError)`, and line 764 has no local handler, so a hostile listener on the probed or daemon port could raise `RecursionError` into daemon start-up or an adapter. Any local process can send such a frame, or listen on the port.
2. `sanitize_fts_query` keeps upper-case `AND`, `OR`, `NOT`, so its raw output can raise `fts5: syntax error` when passed unquoted to `MATCH`. This is NOT a production defect: every production caller quotes each term (`search_primitives.py` lines 123 to 124, 152, 182, 197: `"{term}"*`), and a 4000-example targeted probe of the composed quoted query found no failure. It is a misleading docstring: the docstring says natural-language input never reaches the query parser as a special character, which is only true after quoting. Decision: pin the real invariant (the composed query never raises) and correct the docstring; do not change the function's output, which has no unquoted consumer.
3. Plain random text did not find the FTS5 operator case in 3000 examples, and random bytes did not find the nesting case. Fuzzing here needs strategies that carry the domain vocabulary (the operator words, quote and bracket characters, deep nesting, long digit runs) plus pinned `@example` inputs for every defect found. The spec requires both.

Rejected: bundling the redaction, viewer, tag-normalisation and hook-input targets into this slice (each needs its own probe of old-code behaviour before its properties can be specified; they follow as a later spec); adding a scheduled deep-fuzz CI job now (it follows once the `fuzz` profile has run clean by hand); changing `sanitize_fts_query` to lower-case the operator words (no consumer needs it, and it would alter outputs that `tests/test_lexical_adapter.py` pins).

## 4. Tests

Written failing first. `unittest` style like the neighbouring tests; Hypothesis `@given` on test methods. A fake socket class in the frame test file returns slices of a `bytes` buffer from `recv(n)` (empty bytes at the end), no real network. No test opens `saltmdb.db`.

`tests/test_fuzz_daemon_frame.py`:
- F1 (contract). For any `st.binary(max_size=256)` used as the raw stream, `recv_frame` returns a `dict` or raises `FrameError`. The `try` catches `FrameError` ONLY: no `except Exception` (it would make the property vacuous). Passes on the old code.
- F2 (abuse; fails on the old code). For a body drawn from a strategy that mixes (via `st.one_of`, building the bytes by multiplication, no `.filter()`): nested JSON objects and lists built with `st.recursive(..., max_leaves=30)`; a bracket-nesting generator `b'{"a":' + b"[" * n + b"]" * n + b"}"` with `n` from 2000 to 400000; an integer-digit generator `b'{"a":' + b"9" * n + b"}"` with `n` from 4290 to 6000; non-object JSON (`b"[]"`, `b"1"`, `b"null"`, `b'"x"'`); and arbitrary short binary. The stream is the 4-byte big-endian length of the body followed by the body. `recv_frame` returns a `dict` or raises `FrameError` (the `try` catches `FrameError` only). Pinned `@example`s: depth 200000 and a 5000-digit integer. Old code: `RecursionError` and `ValueError` (two distinct failures).
- F3 (contract). Round trip over `socket.socketpair()` with `settimeout(5)` on both ends (a deadlock then fails instead of hanging): for any JSON object from `st.dictionaries(st.text(max_size=8), st.recursive(<leaves from st.none(), st.booleans(), st.integers(), st.floats(allow_nan=False, allow_infinity=False), st.text(max_size=8)>, <lists and dictionaries>, max_leaves=30))`, no `.filter()`, `recv_frame` after `send_frame` returns an equal object. The frames are a few KB, below the socket buffer, so the single-threaded send then receive cannot block.
- F4 (contract). Size cap, with bytes left after the prefix: the fake socket holds the 4-byte prefix followed by 16 bytes `b"x" * 16`. For any length drawn from `st.integers(min_value=DAEMON_RPC_MAX_MESSAGE_BYTES + 1, max_value=2**32 - 1)` (`DAEMON_RPC_MAX_MESSAGE_BYTES` from `saltmdb.config`, 33554432), `recv_frame` raises `FrameError` whose message contains `exceeds`, and exactly the 16 trailing bytes remain unread. Boundary example: a prefix equal to `DAEMON_RPC_MAX_MESSAGE_BYTES` with only those 16 bytes raises `FrameError` whose message contains `connection closed` and not `exceeds` (the cap is `>`, not `>=`).
- F5 (contract; Amendment 1). Raw UTF-8 wire bytes, not produced by `send_frame`: for any dictionary built as in F3 but with text drawn from `st.text(alphabet=st.characters(blacklist_categories=("Cs",)), max_size=8)` (no lone surrogates, so the bytes encode), the body is `json.dumps(obj, ensure_ascii=False).encode("utf-8")`, framed with the 4-byte length, fed through the fake socket; `recv_frame` returns an object equal to `obj`. Pinned `@example`: `{"é": "😀"}`. It exists because `send_frame` uses the default `ensure_ascii=True`, so F3 only ever sends ASCII bodies and cannot tell a UTF-8 decode from a Latin-1 one; any peer that frames its own JSON can send raw UTF-8. Passes on the old code.

`tests/test_fuzz_fts_query.py` (one `init_db` database in a temp directory created once per class, one seeded row, not per example):
- Q1 (contract). For any text from `st.text()` mixed with a token strategy built from `["AND", "OR", "NOT", "NEAR", "foo", '"', "(", ")", "*", "^", ":", "-", "+", ",", ".", "'", "_", "é", "٠", "á", "😀", "​"]` joined by spaces, `_run_fts_search(conn, sanitize_fts_query(text), [], [], 5, 0)` and the same call with `or_only=True` both complete without raising. Passes on the old code (probed). Pinned `@example`s: `"OR"`, `"foo AND"`, `'"'`.
- Q2 (contract). For any text, `sanitize_fts_query(text)` fully matches the pattern `(\w+( \w+)*)?`. Pinned `@example`s: `'a, b'`, `' x'`, `'a"b'`.
- Q3 (pin of the documented gap). `sanitize_fts_query("foo OR")` equals `"foo OR"` (the function does not remove operators, which is why the docstring says its output is only safe after quoting). This test exists so a later change of behaviour has to update the docstring too.

## Amendment 1 (2026-10-25, developer BLOCKED m_3837, verified by the architect)

The locked text made F3 the killer of M8 (decode as Latin-1 instead of UTF-8). `send_frame` (`protocol.py` lines 94 to 98) calls `json.dumps(obj)` with the default `ensure_ascii=True`, so every body it produces is pure ASCII and a UTF-8 decode equals a Latin-1 decode: F3 can never fail under M8 (probed: `json.dumps({"é": "😀"}).isascii()` is `True`; a raw UTF-8 body decoded as Latin-1 gives mojibake keys, not an error). The consultant's review had asserted F3 would kill M8; that was wrong, and the architect did not probe it. Resolution (option a of the BLOCKED message): F3 stays as written; F5 is added (section 4) to send raw UTF-8 wire bytes; M8 is killed by F5; acceptance item 1 lists F5 among the passing contract tests. `send_frame` is not changed (out of scope, section 7). Gate step 7 re-run: the old wording `F3 with non-ASCII text` and `F1, F3, F4, Q1` no longer appear outside this amendment; F5 appears in section 4, section 8 items 1 and 5, and here only.
