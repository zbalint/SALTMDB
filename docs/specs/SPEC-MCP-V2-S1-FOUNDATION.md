## 1. Why

Unknown tool arguments are rejected today by a loop at the end of `tools.py` that sets `extra="forbid"` on each tool's argument model through a private FastMCP attribute (`mcp._tool_manager`, marked `shortcut:`). The rejection reaches the agent as a raw pydantic `ToolError` (an MCP error result with free text, no envelope, no list of valid fields). An unknown tool name is also a bare `ToolError` ("Unknown tool"), so a stale client calling a removed tool gets no replacement. Every v2 slice needs a place to put these behaviours: this slice builds it once. Rejected alternatives: keep the private-API loop and wrap errors in each tool (duplicated, 24 places); a `__signature__` trick or hand-registered flat models (hides the parameter list, private API); a decorator on each tool (easy to forget on a new tool).

## 2. Decisions

- D1 `src/saltmdb/mcp/guard.py` defines `class GuardedFastMCP(FastMCP)` overriding the public coroutine `call_tool(self, name, arguments)`, and `REMOVED_TOOLS: dict[str, str]` (old tool name to replacement sentence; EMPTY in this slice, later slices add entries). `server.py` creates `mcp = GuardedFastMCP("SALTMDB", lifespan=server_lifespan)`. The lowlevel handler binds `self.call_tool`, so every protocol call goes through the override; a guard test proves it by spying on the override through the lowlevel request handler. Tools are registered by `server.py`'s side-effect import AFTER the server object is built, so everything the override caches (the allowed keys, the output-schema flags) is built LAZILY on the first call, never in `__init__`. The override tolerates `arguments=None` (treated as `{}`).
- D2 Order of checks inside the override:
  1. Unknown tool name: if `name` is a key of `REMOVED_TOOLS`, rejected envelope with code `REMOVED_TOOL`, `field: "tool"` and the replacement sentence; otherwise code `UNKNOWN_TOOL`, `field: "tool"`, message listing the valid tool names.
  2. Unknown top-level fields: the allowed keys are the `properties` of the tool's published input schema (read once through the public `list_tools()` and cached per tool). Each unknown key yields one error `{code: "UNKNOWN_FIELD", field: <key>, message: "...valid fields: a, b, c"}` carrying `corrected_call` (the existing helper, called with the tool function, drops unknown keys and keeps required ones). The tool function is obtained lazily as `getattr(importlib.import_module("saltmdb.mcp.tools"), name)` to avoid a guard, tools, server import cycle; there is no private FastMCP access anywhere in `guard.py` (FastMCP 1.30 has no public `get_tool`).
  3. Otherwise call `super().call_tool`. A `ToolError` whose `__cause__` is a pydantic `ValidationError` whose model title equals `f"{name}Arguments"` (the generated argument model, so the error is the CALLER's input) becomes a rejected envelope with one error per pydantic error: code `UNKNOWN_FIELD` for `extra_forbidden`, `VALIDATION_ERROR` otherwise, `field` the dotted/indexed location (for example `items[1].title`), `message` the pydantic message without the documentation URL. Any other exception, including a `ValidationError` raised inside the tool body or by output conversion (a different model title), becomes an `INTERNAL_ERROR` envelope (see D4).
  The rejection envelopes of 1 to 3 are normal tool results (MCP error flag false) shaped like the tool's own results WITHOUT private API: read the tool's `outputSchema` from the cached public `list_tools()`; if it is the single-`result` wrapper (tools annotated `-> dict | list`, today `archive_memory`, `manage_relation`, `consolidate_memories`) return the 2-tuple `([TextContent(json envelope)], {"result": envelope})`, otherwise return `[TextContent(json envelope)]` (a test compares both forms with `fn_metadata.convert_result`, where tests may touch private API; once S2 to S4 annotate every tool `-> dict` the wrapper form disappears). Nothing is written before a rejection (the daemon is not called).
- D3 `src/saltmdb/utils/envelope.py` moves to the design spec's R4 shape: `ok(...)` always carries `errors: []`; `error(code, message, field=None, corrected_call=None, corrected_calls=None)` may carry one structured `corrected_call` or a list `corrected_calls` of alternatives (mutually exclusive); `ok()` and `rejected()` lose their top-level `corrected_call` parameter; a rejected envelope has NO `data` key (as today; parent spec amendment 2 aligns R4 and R7); the module docstring is rewritten to the new shape. Every existing producer that passed a top-level `corrected_call` (`store_memory` at about `tools.py:584`, `manage_relation` at about 881 and 903, plus anything a grep of `src` finds) attaches it to the error it corrects (the error named by `field`, else the first error). The tool DESCRIPTIONS that quote the top-level key (the `manage_relation` docstring at about `tools.py:938-939` and the `store_memory` docstring at about 510) are updated to the new shape in this slice, because agents learn the shape from them. No behaviour changes besides where the key sits.
- D4 `INTERNAL_ERROR`: an unexpected exception in a tool is converted by the override to a `ToolError` whose message is the JSON text of a rejected envelope with a single error `{code: "INTERNAL_ERROR", message: <short safe text>}` (no stack trace, no secrets, no file paths), so the lowlevel server returns it as an MCP error result (error flag true) whose content is the envelope; it is logged with the traceback on the server side. Tools that already catch their own failures and return envelopes are unchanged. The daemon status dictionaries `DAEMON_STARTING` and `DAEMON_CONNECTION_LOST_DURING_WRITE` stay as they are (they are not exceptions).
- D5 The private-API loop at the end of `tools.py` and its comment are deleted. The argument models keep pydantic's default (`extra="ignore"`) for top-level keys because the override filters them first; nested models introduced later declare `extra="forbid"` themselves.
- D6 Test harness (NEW `tests/mcp_contract.py`, a helper module, not a test): builds the guarded server with a `DirectDispatchBackend` on a temporary database, configures the adapter identity, and exposes `call(name, arguments)` (returns the parsed envelope or, for a tool that returns a list, the parsed list), `call_protocol(name, arguments)` (goes through the lowlevel request handler and returns the MCP result including the error flag), `tool_names()` and `published_properties(name)`; it also holds the inventory constant `TOOL_NAMES` (the 24 names present today) that the coupling test of slice S5 and the guard tests read. Later slices update the inventory when they remove or add tools.
- D7 Existing tests that encode the old behaviour are updated, and these are the ONLY authorised assertion changes: `tests/test_mcp_tools.py` `test_..._get_memory` unknown-id rejection (about lines 1244 to 1247, `assertRaisesRegex(ToolError, "Extra inputs are not permitted")`), `TestMCPToolArgumentValidation.test_search_memory_rejects_unknown_query_argument` (about 1866 to 1873) and `test_every_registered_tool_forbids_unknown_arguments` (about 1875 to 1878, replaced by a guard test); `tests/test_envelope.py`, `tests/test_corrected_call.py`, `tests/_test_helpers.py` and the `corrected_call` assertions of `tests/test_mcp_tools.py` and `tests/test_store_contract_phase5.py` where they read the top-level key (they read `errors[...]["corrected_call"]`); the whole-envelope equality assertions at about lines 457, 685 and 688 of `tests/test_memory_service_characterization.py` (and any other `assertEqual(result, {"status": "ok", ...})` a grep finds) get `"errors": []` added (`ok()` reaches every service result because 12 modules use the envelope helpers and the result crosses the daemon wire). Every other assertion change is a BLOCKED query to the architect. The sweep `git diff -U0 -- tests | grep assert` must show only these.
- D8 New tests in `tests/test_mcp_guard.py`, parametrised over `mcp_contract.tool_names()` where it says so (literal expected values): for EVERY tool: an unknown top-level field is rejected with `UNKNOWN_FIELD`, `field` equal to the key, the valid-field list in the message equal to the published properties, error flag false, and zero side effects (for write tools the entity and event counts are unchanged); a missing required field gives `VALIDATION_ERROR` with that field; a wrong type gives `VALIDATION_ERROR`; an explicit `null` for a non-nullable list parameter is rejected with `VALIDATION_ERROR` (documents the latent bug, whose fix comes later); several simultaneous errors are all reported. Also: an unknown tool name gives `UNKNOWN_TOOL` listing valid names; a monkeypatched `REMOVED_TOOLS` entry gives `REMOVED_TOOL` with the replacement; the tools with an output schema (`archive_memory`, `manage_relation`, `consolidate_memories`) return guard rejections that pass the lowlevel handler's output validation (call them through `call_protocol`); a backend that raises makes the call return an MCP result with the error flag true whose content parses to an `INTERNAL_ERROR` envelope, with no traceback text; a `ToolError` whose cause is not a validation error is not mislabelled as a validation error, and a `ValidationError` raised inside a tool body (a different model title) is `INTERNAL_ERROR`, not `VALIDATION_ERROR`; the guard rejection result equals `fn_metadata.convert_result(envelope)` for one output-schema tool and one plain tool; `arguments=None` works; the cache is lazy (a tool registered after construction is known); the override is the code path that runs (spy); `ok()`/`rejected()`/`error()` shapes (R4) including `corrected_calls`; the inventory constant equals the registered tool names (a tool added without updating it fails).
- D9 Complexity and literals: no function's cognitive complexity rises above its baseline except the new functions, which stay at or below 12; report complexipy for `guard.py` and the changed producers.
