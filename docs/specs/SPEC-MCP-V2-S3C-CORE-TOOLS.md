## 1. Why

An existing memory cannot be made core through the MCP surface any more. Slice S2 removed the `entity_id` path of `store_memory`, which was the only way (the agent re-sent title and content unchanged and added `is_core`), and the parent spec promised its replacement: `set_core_memory`. Until it lands an agent that finds a hazard in a stored memory has to store a copy. Separately `review_core_memory` is the last write tool still on the pre-v2 names: `entity_id` instead of `memory_id`, every parameter optional in the published schema (a call with no arguments reaches the service), a result `id` instead of `memory_id`, no envelope mapping.

Probe of the old promotion path (2026-10-23, temporary database, `store_memory(entity_id=..., is_core=True, ...)` on a memory of the same agent): the row is updated in place (entity count 1 to 1, so no history row), `is_core`, `core_reason`, `core_exit_condition` and `core_review_after` (default 14 days out) are set, `updated_at` changes, the `#core` tag appears; another agent's memory is refused with `IMMUTABLE_MEMORY` on field `agent_id`; a second call with a changed `core_reason` succeeds as an edit. `set_core_memory` must keep exactly these effects, without the "re-send title and content unchanged" ceremony.

## 2. Decisions

- D1 Tools (`mcp/tools.py`).
  - `set_core_memory(memory_id: str, core: SetCoreInput) -> dict` (2 parameters). New model `SetCoreInput(BaseModel)` with `model_config = ConfigDict(extra="forbid")` and fields `reason: str`, `exit_condition: str`, `detail_memory_ids: list[str] | None = None` (a sibling of `CoreInput` without `review_after`: the parent spec makes the review date settable only through `review_core_memory`, so the schema must not offer it). First sentence of the description: "Use this to make an existing memory core, or to change the declaration of a core memory; use store_memory to create a new core memory and review_core_memory to extend, demote or archive one." The description states: only the memory's own agent may call it; the memory must be active, shared and at most 2,500 characters; `reason` and `exit_condition` are 20 to 500 characters; a promotion gets the default review date (14 days out) and the date of an existing core never changes here; `detail_memory_ids` omitted keeps the current declaration, `[]` clears it, at most 3 shared non-core memories whose title and UUID appear in the content; the call is atomic; an identical repeat is a no-op warning (`ALREADY_DONE`); capacity (`CORE_CAPACITY_EXCEEDED`) and overdue-review rejections are the existing ones; a private memory must first be made shared (`revise_memory(scope="shared", ...)`); a preserved detail declaration that is no longer valid (a detail archived, or no longer named in the content) makes even an identical repeat a `VALIDATION_ERROR`, and `detail_memory_ids=[]` is the fix; a memory over 2,500 characters is rejected, also for a repeat (revise it first); a memory of another agent cannot be made core here (store a new core memory with `store_memory(core=...)` that cites it).
  - `review_core_memory(memory_id: str, outcome: Literal["retain","demote","archive"], review_rationale: str, core_review_after: str | None = None) -> dict`. All three first parameters are required in the published schema. First sentence: "Use this to review an active core memory (retain, demote or archive it); use set_core_memory to change its declaration." The rest of the existing description is kept and updated for the names and the result shape.
  - `entity_id` is a removed field on both tools and the guard rejects it (R8).
- D2 Adapter. Both tools go through `_call_and_record_write` (today `review_core_memory` calls the backend directly): `set_core_memory` and `review_core_memory` are added to `_ID_RENAME_TO_MEMORY_ID_TOOLS` (data `id` becomes `memory_id`) and `_ERROR_FIELD_REMAP_TOOLS` (error field `entity_id` becomes `memory_id`). `set_core_memory` is added to `_AGENT_ID_INJECTED_TOOLS` (`tools.py`, the set that makes `DirectDispatchBackend` re-assert the adapter `agent_id`; it already contains `review_core_memory` and `revise_memory`). The payload of `set_core_memory` is `{entity_id: memory_id, core_reason, core_exit_condition, detail_memory_ids, agent_id}` built from `core.model_dump(exclude_none=True)` so that an omitted list is absent (keep) and `[]` is kept (clear); the payload of `review_core_memory` is today's with `entity_id: memory_id`. `_WRITTEN_ID_KEY` is unchanged: neither tool is trace-linked, deliberately (a promotion or review is not a memory written by the turn). Neither tool takes `agent_id` or `context_id`.
- D3 Service `core_governance_service.set_core_memory(conn, *, entity_id, agent_id, core_reason, core_exit_condition, detail_memory_ids=None) -> dict` (6 parameters, beside `review_core_memory`; it takes plain values because importing `CoreDeclaration` from `memory_service` into this module is a circular import). Transaction boundary: steps 1 and 2 run before the transaction; steps 3 to 9, including the reads, the no-op check, the overdue and capacity checks and the writes, run inside ONE `write_transaction_retrying(conn, fn)` (a bare `fn(conn)` under the coordinator), so two direct-mode promotions cannot both pass the capacity check; every rejection is RETURNED from `fn` having written nothing (do not copy `review_core_memory`, which resolves the id outside its transaction). Order:
  1. `core_reason` and `core_exit_condition` are non-empty strings and `detail_memory_ids` is a list or None (`VALIDATION_ERROR`, field named after the argument).
  2. `agent_id` mandatory (`VALIDATION_ERROR`, as `review_core_memory`).
  3. Target: `resolve_entity_ref` with the owner filter, through the helper that `update_memory_metadata` uses today; the helper `_metadata_target` in `memory_service/lifecycle.py` is renamed `_owned_memory_target` (definition plus its one call site) and imported lazily here (idiom of `_review_archive`'s import of `_archive_entity_unchecked`). Ambiguous prefix gives `AMBIGUOUS_ID_PREFIX` with candidates; an unknown id or another agent's PRIVATE memory gives `NOT_FOUND`; a memory the caller can see (shared) but does not own gives `IMMUTABLE_MEMORY` on field `memory_id`, the code the old path used, with the message "Only the owning agent can make this memory core; store a new core memory with store_memory(core=...) that cites it." To get the second code, `_owned_memory_target` gains a keyword `foreign_code` (default `NOT_FOUND`, so `update_memory_metadata` keeps its behaviour) and this service passes `IMMUTABLE_MEMORY`; no second helper.
  4. Row read: `status`, `scope`, `full_content`, `title`, `memory_type`, `is_core`, `core_reason`, `core_exit_condition`, `core_detail_memory_ids`. `status != 'raw'` is rejected with `CONFLICT` (message names the status).
  5. A `detail_memory_ids` entry equal to the target is rejected (`VALIDATION_ERROR`, field `core`: a core cannot be its own detail). When the stored `is_core` is 0 (a promotion) and `detail_memory_ids` is None the effective list is `[]` (a demoted core keeps its old declaration and `elaborates_on` edges, which must not come back silently; `previous_detail_memory_ids` stays the stored list, so `reconcile_detail_relations` invalidates the old edges); on an edit of an existing core None keeps the declaration. Then `resolve_store_core_state(conn, entity_id=resolved, is_core_requested=True, content=full_content, scope=scope, core_reason=..., core_exit_condition=..., core_review_after=None, detail_memory_ids=...)`; a `ValueError` becomes `VALIDATION_ERROR` on field `core` (private scope, bad lengths, bad detail ids, content over 2,500). On an edit, `detail_memory_ids=None` preserves the stored declaration and it is revalidated against the content (existing behaviour of the helper); the no-op comparison of step 6 compares the validated lists in order (the same ids in another order count as an edit).
  6. No-op: when the memory is already core and the resolved `core_reason`, `core_exit_condition` and detail list equal the stored ones, return `ok` with an `ALREADY_DONE` warning and write nothing (no `updated_at` change). This check runs before steps 7 and 8, because a non-expanding repeat must succeed while another core is overdue or capacity is tight.
  7. `enforce_overdue_boundary(conn, entity_id=resolved, effective_is_core=True, is_new_core=state["is_new_core"], review_after_changed=False, prospective_entry=entry)`; a `ValueError` becomes `VALIDATION_ERROR` on field `core`. `entry` is `{id, title, memory_type (stored, default "fact"), core_reason, core_exit_condition, core_review_after (resolved), full_content, agent_id}`.
  8. `check_capacity_admission(conn, exclude_ids=[resolved], new_entry=entry)`; a rejection payload is returned as is (`CORE_CAPACITY_EXCEEDED` with inventory, as `store_memory` does).
  9. Write, in this order: `UPDATE entities SET is_core = 1, core_reason, core_exit_condition, core_review_after, core_detail_memory_ids (JSON text, NULL for an empty list, as the old path), updated_at WHERE id = ?`; `reconcile_detail_relations(conn, core_id=resolved, agent_id=agent_id, new_detail_ids=state["core_detail_memory_ids"], previous_detail_ids=state["previous_detail_memory_ids"])`; `#core` tag through the existing `_sync_raw_core_tag(conn, resolved, agent_id)` of `memory_service/write.py` (lazy import). `core_last_reviewed_at`, `core_last_reviewed_by`, `core_review_rationale` (a re-promotion keeps the provenance of its demotion; nothing reads it for due logic), content, title, tags other than `#core`, scope, weight, retrieval text, embeddings, `last_accessed_at` and `last_touched_session_id` are not touched; no history row is written (probed in section 1); an edit overwrites the previous reason and exit condition with no record, as the old path did.
  Return `ok({"id": resolved, "message": ..., "core_review_after": state["core_review_after"]})`; message for a promotion "Memory '<id>' promoted to core; next review at <date>.", for an edit "Core declaration of '<id>' updated; next review at <date>."
- D4 Atomicity. Steps 1 to 8 write nothing. The service has no catch-all `except`: an unexpected failure in step 9 (for example `reconcile_detail_relations` raising `RuntimeError`) propagates, and the coordinator job (or the direct-mode `write_transaction_retrying`) rolls back the whole write. The caller sees an unexpected failure as the guard's internal-error path through the MCP server (no traceback) and as the raised `RuntimeError` at service and dispatch level. No savepoint is needed because nothing catches after the write (S3b needed one only for its catch-all). `review_core_memory` needs no change for the same reason. The atomicity test (section 4) injects a `reconcile_detail_relations` error after the `UPDATE` and asserts the row is unchanged in both modes; the DIRECT-mode case is new (the S3b atomicity test covers COORDINATOR mode only).
- D5 Dispatch. New `_dispatch_set_core_memory(**kw)` in `daemon/dispatch.py` beside `_dispatch_review_core_memory`: required `entity_id` and `agent_id` strings, `core_reason` and `core_exit_condition` required strings (a missing one is a `VALIDATION_ERROR` through the existing `_required_str`), `detail_memory_ids` optional list (`_required_str_list` style check when present), a non-None `core_review_after` is rejected here with `VALIDATION_ERROR` on field `core_review_after` ("the review date is set by review_core_memory"); the MCP schema cannot send it, the daemon RPC can, and the dispatcher is the one place RPC input passes through. Registered in `DISPATCH_TABLE`, `MUTATING_TOOLS` and `daemon/protocol.py` `WRITE_TOOLS`. `_dispatch_review_core_memory` and its service signature keep the internal name `entity_id` (R9).
- D6 `review_core_memory` behaviour is unchanged (outcomes, rationale length, `core_review_after` rules, `ALREADY_DONE` no-ops, error codes). Only names and the result key change.
- D7 Existing-test changes (categories; no assertion is weakened): (a) `tests/test_mcp_tools.py` `TestReviewCoreMemoryTool` calls `tools.review_core_memory(entity_id=...)` four times: the keyword becomes `memory_id`; the missing-argument test (`test_missing_required_fields_rejected`) is rewritten to call `mcp_contract.call_protocol("review_core_memory", {"memory_id": ..., "outcome": "retain"})` and assert `VALIDATION_ERROR` on field `review_rationale` with zero change (a direct Python call with a missing required argument raises `TypeError` and is not the contract); the owner-tools tuple at line 90 gains `tools.set_core_memory`; (b) `tests/mcp_contract.py` tool list gains `set_core_memory`; (c) `tests/test_mcp_guard.py` `_SKIP_REASONS`: remove both `review_core_memory` entries (lines 30 and 40; the test does not flag a stale entry by itself); `set_core_memory` needs no entry (its required fields `memory_id` and `core` and the string `memory_id` give every generic guard test a field; the developer proves it by running the file); (d) `tests/test_core_governance_service.py` and `tests/test_consolidation_is_core_inheritance.py` call the service with `entity_id` and stay unchanged. Any other existing failure is reported, not fixed silently.
