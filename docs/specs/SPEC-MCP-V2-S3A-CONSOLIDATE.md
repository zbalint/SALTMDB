## 1. Why

`consolidate_memories` is the last tool with a wrapped output schema (`dict | list`), the last tool with two shapes in one call (single fields next to a `consolidations` list, with a different return shape for each), and the tool with the 14-parameter Sonar `python:S107` finding in `mcp/tools.py`. Its failures are reported as one string (`Bulk consolidation aborted (all-or-nothing): {...}`) without an item index; the cross-item shared-parent case is caught only by an accident of the revalidation; an active-core parent without an explicit decision is a free-text `CONSOLIDATION_FAILED`. Parent spec D4 and D6 define the target surface. BL-063 part 1 already made the write path atomic under the daemon coordinator, so this slice reshapes the surface on top of a correct write path. Rejected: converting the old bulk function in place (its tests and callers pin the list-of-strings shape; S2b chose a new function beside the old one for the same reason); keeping the single form next to the list (two shapes per tool, the thing v2 removes); parsing the message text of the core rejection to recover its code.

## 2. Decisions

- D1 Tool: `consolidate_memories(items: Annotated[list[ConsolidationItem], Field(min_length=1, max_length=20)], context_id: str | None = None) -> dict` (two parameters; the return annotation is `dict`, so the tool has no output-schema wrapper). `ConsolidationItem` is a pydantic model with `extra="forbid"`: `parent_memory_ids: list[str]`, `title: str`, `content: str | None = None`, `content_file_path: str | None = None`, `tags: list[str] | None = None`, `scope: Literal["private", "shared"] = "shared"`, `override_justification: str | None = None`, `context_id: str | None = None`, `core: CoreInput | None = None`, `demote_core: bool = False`. `CoreInput` is the existing model used by `store_memory`. `ConsolidationBatchItem` (TypedDict), the single-form parameters, `weight`, `is_core`, `core_reason`, `core_exit_condition`, `core_review_after`, `detail_memory_ids` and the top-level `parent_ids`, `title`, `content`, `tags`, `scope`, `override_justification` are removed from the published schema. `weight` stays an internal item key with default 1 (full-text ranking multiplies by it). The batch-wide `context_id` is the default for an item that sets none; an item's own `context_id` wins.
- D2 Adapter (`tools.py`). Before any backend call, for every item in order: (a) exactly one of `content` or `content_file_path` (the existing `_resolve_content` rules and codes; it gains an optional `field_prefix` parameter so the error's `field` reads `items[i].content` / `items[i].content_file_path`; the existing callers pass no prefix and keep their literals); (b) `core` together with `demote_core: true` is rejected with code `CORE_AND_DEMOTE_CONFLICT` at `items[i].demote_core`. All adapter-level errors of all items are collected and returned in ONE rejected envelope in item order; nothing is dispatched when there is any. The loop is item-major and checks (a) before (b) within an item, so the errors come out in item order and, inside an item, content before conflict. There is no tool-level JSON-string branch: FastMCP pre-parses a JSON string for a list parameter before the function runs (probed 2026-10-22 with `manage_relation`), so by the time the function runs `items` is a list of `ConsolidationItem` models (a pinned contract test covers the string). The per-item mapping and validation live in new helpers (the tool body stays at or below 8). Then each item is dumped with `model_dump(exclude_none=True)` and mapped to the internal keys: `parent_memory_ids` to `parent_ids`; `content` resolved; `core` to `is_core=True` plus `core_reason`, `core_exit_condition`, `core_review_after`, `detail_memory_ids`; `demote_core: true` to `is_core=False`; neither to no `is_core` key. The `None` keys are dropped here AND again in the service (D3 step 1), so that an item without `context_id` inherits the batch value on every path, including dispatch-level callers that pass dicts directly. The call is `{"items": [...], "context_id": <batch>, "agent_id": <injected>}`; the tool never forwards an `agent_id` from an item (it is an unknown field of the model). After a successful call `_queue_trace_write` records EVERY item's `memory_id` (D8).
- D3 Service `apply_consolidations(items, agent_id=None, context_id=None, agent_session_id=None, db_connection=None, db_path=None) -> dict` in `relation_service.py`. `items` is a list of dicts with the internal keys of D2 (`parent_ids`, `title`, `content`, `tags`, `scope`, `weight`, `override_justification`, `context_id`, `is_core`, `core_reason`, `core_exit_condition`, `core_review_after`, `detail_memory_ids`). It reuses, unchanged in behaviour, `get_fresh_entity_centroids`, `_commit_bulk_consolidation_item` and `_write_bulk_consolidations` (the savepoint and the deferred vector clears of BL-063 part 1), and `managed_connection` for the connection. Steps: (1) an empty or non-list `items` and a non-dict item are `VALIDATION_ERROR` at `items` / `items[i]`; every item is then copied without its `None` values and without any `agent_id` key (the owner identity comes only from the `agent_id` argument, as in `apply_relations`; the old item-level override of `_commit_bulk_consolidation_item` stays for the old callers and is simply never fed here); (2) per item, parents are resolved and validated outside any transaction by `_prepare_bulk_consolidation_parents`, which gains the failing item's index in its error result and still returns the FIRST error only; the error keeps its consolidation code: `UNKNOWN_PARENT_ID`, `AMBIGUOUS_PARENT_ID`, `INACTIVE_PARENT` or `REJECT_PARENT_COUNT` (these are the codes of `_validate_parent_reference` and `_resolve_and_validate_parent_ids`; they are NOT the lifecycle codes `UNKNOWN_ENTITY_ID`, `AMBIGUOUS_ID_PREFIX`, `INACTIVE_TARGET`), with `field: "items[i].parent_memory_ids"`; a repeated parent inside ONE item is deduplicated silently (`[A, A, B]` is accepted as `[A, B]`; `[A, A]` is `REJECT_PARENT_COUNT`); (3) in `apply_consolidations` itself (NOT in `_prepare_bulk_consolidation_parents`, so the old bulk path keeps its behaviour), after step 2 passed for every item, a resolved parent that appears in two items is rejected before any write with code `DUPLICATE_PARENT_ID` at `items[j].parent_memory_ids` (j is the LATER item; the message names the parent and the earlier index); step 2 stops at the first failing item, so a duplicate in a later item is reported only after the earlier items are clean; (4) centroids once, outside the transaction; (5) the write phase: `write_transaction_retrying` around `_write_bulk_consolidations`; an item whose commit comes back rejected raises the item-rejection exception of D4, which the existing `savepoint` aborts (zero changes), and the function returns ONE rejected envelope with that item's errors, each with `field` prefixed `items[i]` (an error without a field uses `items[i]`); consolidation items depend on earlier items' writes, so the FIRST failing item stops the batch (unlike `apply_relations`, which collects all). An unexpected exception propagates out of the block (outer rollback). Outside the block, exactly like `apply_relations`: under the coordinator (`is_coordinator_connection(conn)`) the exception is RE-RAISED (the coordinator job fails and rolls back, so a failure after the savepoint was released, for example in `_clear_archived_parent_vectors`, can never commit the batch while an envelope claims otherwise); in direct mode it becomes ONE `INTERNAL_ERROR` rejection with no stack trace in the message. A write fault INSIDE an item is not an unexpected exception: the single `consolidate_memories` `except` returns it as `CONSOLIDATION_FAILED`, which surfaces as a rejection at `items[i]`; `INTERNAL_ERROR` comes only from code outside the item commit (the savepoint, `_clear_archived_parent_vectors`, `_write_bulk_consolidations`). Success: `ok({"items": [{"memory_id": <new id>, "title": <clean title>, "parent_memory_ids": <resolved parents>, "orphaned_relations": [...]}, ...], "consolidated_count": n, "worklist_guidance": <one string>})`, items in request order. The three aliases of the same worklist in the old shape (`orphaned_relations`, `orphaned_edge_worklist`, `orphaned_edges`) collapse to `orphaned_relations` in the new shape.
- D4 Rejection plumbing (`relation_service.py`). `_commit_bulk_consolidation_item` raises a new `_BulkItemRejected(RuntimeError)` that carries the rejected envelope in `.errors` and keeps the exact message `Bulk consolidation aborted (all-or-nothing): {result}` of today, so `bulk_commit_consolidation` and every test of its string results behave identically. The exception derives `.errors` from the result in its own `__init__` (no new conditional at the raise site, which keeps `_commit_bulk_consolidation_item` at its baseline). `apply_consolidations` derives the failing item's index from the number of items already committed in the savepoint (the results list; `results.clear()` runs at the start of every write attempt), not from the message.
- D5 Core decision (parent D6, consolidation items). A new `CoreDecisionRequired(CoreGovernanceRejected)` in `core_governance_service.py` (a subclass of the existing exception, NOT of `ValueError`, so the `except ValueError` of `_consolidation_core_state` does not touch it and that function stays at its baseline) is raised, with today's message text unchanged, at the site where `resolve_consolidation_core_state` rejects "an active core parent and `is_core` omitted"; it carries the keep fragment (below). `consolidate_memories`'s `except` gets one `except CoreDecisionRequired` clause before the generic one and returns `CORE_DECISION_REQUIRED` instead of `CONSOLIDATION_FAILED`, with `corrected_calls=[<keep fragment>, {"demote_core": True}]` on the error. The keep fragment is built from the FIRST active core parent IN THE ORDER OF `resolved_parents` (the query at the raise site must select `core_reason` and `core_exit_condition` in addition to `id`, `is_core`, `status`, and the code sorts the rows by the index in `resolved_parents`; a `WHERE id IN (...)` row order is not defined): `{"core": {"reason": <its core_reason>, "exit_condition": <its core_exit_condition>}}`, plus `"scope": "shared"` when the item's scope is not shared (a private core is prohibited, so the hint would otherwise fail). `review_after` and `detail_memory_ids` are deliberately NOT pre-filled: an old deadline can already be overdue, and a declared detail memory must be named in the NEW content (and may be another parent archived by the same call), so copying it would make the hint itself fail. The decision is made in the transaction against fresh state (the existing authoritative check); a parent that turned core after the adapter returned still produces the rejection. `demote_core: true` with no active core parent is accepted and means "ordinary" (same as absent). `is_core=False` (demote) and `is_core=True` (core) keep today's service semantics, including capacity admission and the overdue boundary (codes unchanged).
- D6 Completing the correction (adapter). A rejected envelope whose error has code `CORE_DECISION_REQUIRED` and a `field` of the form `items[i]` or `items[i].parent_memory_ids` is post-processed by a helper in `tools.py` (written for reuse by S3b): the submitted items are first converted to plain dicts, `[item.model_dump(exclude_none=True) for item in items]` (FastMCP hands the function models, which cannot take a dict merge, and `build_corrected_call` only looks at top-level parameters); each fragment in `corrected_calls` is then merged into item `i` of that list (public shape, with the file path kept when the caller used one) and replaced by a full call built with `build_corrected_call(consolidate_memories, submitted, {"items": merged_items})`. The helper also replaces the error message by the public wording (the service text names the internal parameters `is_core` and `core_reason`, which the v2 tool rejects as unknown): `One or more parents of this item is an active core memory. Resend the item with core (keep the result core: reason and exit_condition) or demote_core true (let the result become an ordinary memory).` The service text stays unchanged for the old paths. After the helper no `corrected_calls` entry is a bare fragment. A malformed field that matches neither form leaves the fragments and the message as they are.
