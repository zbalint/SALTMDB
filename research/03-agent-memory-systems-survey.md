### Detail per system

**mem0.** The original pipeline runs two LLM passes per incoming message pair: an *extraction* phase (using a rolling conversation summary + a window of recent messages) that produces candidate facts, and an *update* phase that retrieves the top-s semantically similar existing memories and asks the LLM, via function-calling, to choose ADD / UPDATE / DELETE / NOOP for each candidate rather than using a separate classifier. The graph variant (Mem0ᵍ) represents facts as a `(entity, relation, entity)` triple graph in Neo4j, with each node carrying a type, embedding, and timestamp; conflicting relationships are marked obsolete (not deleted) specifically to preserve temporal-reasoning ability, and Mem0ᵍ scored highest on the paper's temporal-reasoning benchmark (F1 51.55) ([arXiv:2504.19413](https://arxiv.org/html/2504.19413v1)). By April 2026, mem0 shipped a v3 rewrite that drops the UPDATE/DELETE branches entirely: extraction becomes a single LLM call, memories are **ADD-only** (v3 explicitly treats even contradicted facts as coexisting, relying on hybrid semantic+keyword+entity retrieval-time ranking to surface the "current" fact), and the external graph-store dependency (Neo4j) was replaced with a built-in entity-linking collection populated at `add()` time. This produced large benchmark jumps (LoCoMo 91.6, LongMemEval 93.4, vs. the v2 baseline) with roughly half the extraction latency ([mem0 v2→v3 migration guide](https://docs.mem0.ai/migration/platform-v2-to-v3)). Scoping is via `user_id`/`agent_id`/`run_id` filters on every `add`/`search` call — there is no shared cross-tenant graph ([mem0 GitHub](https://github.com/mem0ai/mem0), [mem0 memory-types docs](https://docs.mem0.ai/core-concepts/memory-types)).

**Letta / MemGPT.** The foundational idea (from the MemGPT paper) is *virtual context management*: treat the LLM context window like physical RAM and give the agent OS-style paging tools to move data to/from "disk" (external storage), producing the illusion of unbounded memory within a fixed window. Concretely this becomes three tiers: **core memory** (small, always-in-context blocks — e.g., persona/human — that the agent edits directly via tool calls like `core_memory_append`), **recall memory** (the complete raw conversation history, saved to disk automatically and searchable via `conversation_search`), and **archival memory** (explicitly formulated, indexed knowledge in an external vector/graph store, queried via `archival_memory_search`). The agent itself decides what's worth promoting/demoting between tiers — there is no separate background daemon required, though Letta additionally supports **sleep-time compute**: dedicated background agents that revise memory blocks asynchronously during idle time. The most architecturally distinct feature for multi-agent setups is **shared memory blocks**: the same block object can be attached to multiple independent agents, and an edit by any one of them is immediately visible to all others (last-write-wins under concurrent edits, since `set value` is a full replace, not an append) ([Letta: Agent Memory blog](https://www.letta.com/blog/agent-memory/), [Letta shared-memory docs via search](https://docs.letta.com/guides/core-concepts/memory/shared-memory), [Letta multi-agent docs](https://docs.letta.com/guides/agents/multi-agent/)).

**Zep + Graphiti (the deepest comparison).** Graphiti is the open-source temporal-graph engine; Zep is the hosted product built on it. Data enters as discrete, timestamped **episodes** (raw events/messages), which are organized into three subgraph tiers: an **episode subgraph** (raw events, each annotated with its original timestamp), a **semantic entity subgraph** (extracted entities/relationships), and a **community subgraph** (higher-level clustering of related entities). The single most important mechanism is the **bi-temporal edge model**: every graph edge carries *four* timestamps — `created_at`/`expired_at` (system/transaction time: when Graphiti recorded or retracted the fact) and `valid_at`/`invalid_at` (real-world/event time: when the fact actually became true or false in the world). These two temporal axes are tracked and resolved **independently**. When new information arrives, Graphiti runs semantic + keyword + graph search to find edges that might be affected, then uses an LLM-based invalidation prompt to decide whether a genuine contradiction exists; if so, it sets `expired_at`/`invalid_at` on the superseded edge rather than deleting it, preserving a complete, queryable history. Critically, this handles **out-of-order ingestion**: if a "divorce" episode is processed before the "marriage" episode that logically precedes it, Graphiti sorts by `valid_at` (world time, not ingestion order) and invalidates the earlier-occurring edge — i.e., temporal correctness is anchored to the *claimed* event time, not arrival order. Retrieval is a genuinely hybrid fusion of vector similarity, BM25 full-text, and graph-distance-based traversal/reranking (e.g., MMR), explicitly designed to avoid needing an LLM call at query time (unlike GraphRAG's batch/LLM-summarization approach) — this gives sub-second query latency versus GraphRAG's multi-second-to-tens-of-seconds. Storage is Neo4j (default) or FalkorDB, with Amazon Neptune+OpenSearch also supported (Kuzu support is being deprecated). Multi-tenancy is native and two-tiered in the Zep product layer: a `user_id` gives a fully isolated **user graph** (a `thread.get_user_context()` call only ever sees that user's own graph), while a `group_id` gives a shared **group graph** for organizational/team-level knowledge — the two are composable but never implicitly merged ([Zep/Graphiti paper, arXiv:2501.13956](https://arxiv.org/pdf/2501.13956), [Graphiti overview docs](https://help.getzep.com/graphiti/getting-started/overview), [Beyond Static Knowledge Graphs](https://blog.getzep.com/beyond-static-knowledge-graphs/), [Graphiti README](https://raw.githubusercontent.com/getzep/graphiti/main/README.md), [Zep Users and User Graphs docs](https://help.getzep.com/users-and-user-graphs), [Zep Threads docs](https://help.getzep.com/threads)).

**Cognee.** Built around an **ECL pipeline** (Extract → Cognify → Load): `add()` ingests 30+ file formats and content-hashes for dedup; `cognify()` runs a six-stage pipeline (classify documents → check permissions → chunk → LLM entity/relationship extraction → summarize → embed + commit graph edges), producing a hybrid graph-vector store where the atomic unit is a Pydantic `DataPoint` (entities, chunks, summaries, and relationships are all `DataPoint`s with their own embeddings). The distinctive piece is `memify()`: a *separate, later* pass that **prunes stale nodes, strengthens frequently-traversed connections, reweights edges by usage signals, and derives new facts** from the existing graph — explicitly framed as the "self-improvement" step where memory evolves after ingestion rather than only at write time. Backends are fully pluggable (graph: Kuzu default, or Neo4j/FalkorDB/Neptune/Memgraph; vector: LanceDB default, or Qdrant/pgvector/Redis/Pinecone/Chroma; relational/provenance: SQLite default, or Postgres). Retrieval offers 14 modes, with the default `GRAPH_COMPLETION` using vector search only as a "hint" to locate graph triplets, then traversing the graph to assemble structured context (rather than returning raw top-k chunks). Multi-tenancy is dataset-scoped: graphs can be instantiated per-user, per-group, or as shared/public, with read/write/delete/share permissions enforced at the dataset level across whichever backend is configured ([Cognee: How Cognee Builds AI Memory](https://www.cognee.ai/blog/fundamentals/how-cognee-builds-ai-memory), [Cognee GitHub](https://github.com/topoteretes/cognee)).

**OpenAI ChatGPT Memory.** Publicly documented at a conceptual level only (no architecture paper). Two mechanisms: explicit **saved memories** (user says "remember X," ChatGPT can later update/combine/remove them, similar to custom instructions but self-maintained) and implicit **chat-history-derived memory** (details ChatGPT infers are useful without being asked). Retrieval is RAG-style: relevant memories are fetched and injected as context at the start of a chat. The one named internal mechanism with any technical framing is **"Dreaming"**: a background process that periodically reprocesses many past conversations to re-synthesize a fresher, more coherent memory state, intended to surface naturally-occurring context (not just explicit "remember this" requests) without users having to manage it manually. No public detail on embedding models, storage engine, staleness/expiry rules, or exact forgetting criteria beyond user-facing controls to disable "saved memories" and/or "chat history" independently ([OpenAI: Memory and new controls for ChatGPT](https://openai.com/index/memory-and-new-controls-for-chatgpt/), [OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq), [Embrace The Red: how ChatGPT memory works](https://embracethered.com/blog/posts/2025/chatgpt-how-does-chat-history-memory-preferences-work/)).

**Anthropic's memory tool + context editing (Claude Developer Platform).** This is the most precisely documented of all systems here because it's a shipped API feature, not a research description. The **memory tool** (`memory_20250818`) is entirely **client-side**: Claude only *requests* file operations (`view`, `create`, `str_replace`, `insert`, `delete`, `rename`) against a virtual `/memories` directory; the calling application executes them against whatever storage it chooses (disk, DB, cloud) and returns results in `tool_result` blocks — Anthropic's server never stores memory content itself. The API auto-injects a system-prompt instruction telling Claude to always `view /memories` before starting work and to treat every session as possibly-interrupted, so it should write progress to memory proactively. This pairs with **context editing**: a server-side (but client-history-preserving) mechanism where, once a token or tool-use-count trigger fires (`clear_tool_uses_20250919`, default trigger 100k input tokens, default `keep` = 3 most recent tool-use/result pairs), the oldest tool results are automatically cleared and replaced with placeholders before the prompt reaches Claude — critically, Claude is warned *before* clearing happens, so it can write important findings to a memory file first. Anthropic reports 84% token savings and 39% performance improvement on a 100-turn web-search task combining both features. A separate `clear_thinking_20251015` edit independently manages extended-thinking block retention (model-dependent defaults; clearing invalidates the prompt cache, keeping thinking blocks preserves it). None of this includes any built-in vector search, dedup, or temporal-fact model — those are explicitly left to the implementer; the design philosophy is "just-in-time" retrieval (Claude decides what to read back, rather than the platform doing similarity search for it), and the docs explicitly recommend periodic manual expiry of memory files that haven't been accessed in a long time ([Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool), [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)).

**Other systems worth naming.**
- **txtai** unifies an embeddings index with an optional synced graph network (graph nodes mirror index entries; edges are auto-derived from index similarity on every upsert), and recently added first-class agent `memory` alongside `agents.md`/`skill.md` conventions, but has no published bi-temporal or multi-tenant model — it's positioned as an embeddable single-deployment library, not a hosted service ([txtai GitHub](https://github.com/neuml/txtai)).
- **LangChain/LangMem and LlamaIndex Memory** both moved away from "memory = raw chat buffer." LangMem sits on LangGraph's native key-value/vector long-term store (no external graph). LlamaIndex's newer `Memory` class replaces the old `ChatMemoryBuffer` with pluggable `MemoryBlock`s (static injection, `FactExtractionMemoryBlock`, vector-similarity memory), backed by SQLite for cross-restart persistence. Neither publishes a contradiction-detection or bi-temporal mechanism; both compose retrieval strategies per block rather than unifying them in a graph (via web search results comparing these frameworks in 2026 surveys).
- **Microsoft Research** shipped two distinct 2026 memory systems worth flagging: **Memory OS of AI Agent**, a literal "OS" metaphor with three storage tiers (short/mid/long-term) and FIFO-then-paged promotion between them; and **Memora** ("A Harmonic Memory Representation Balancing Abstraction and Specificity," ICML 2026), which explicitly separates *what's stored* (rich, uncompressed memory content) from *how it's indexed* (short "primary abstractions" + "cue anchors" that consolidate related updates and expand retrieval access) — conceptually a middle ground between mem0's flat facts and Graphiti's full graph ([Memory OS arXiv:2506.06326](https://arxiv.org/abs/2506.06326), [Microsoft Research: Memora blog](https://www.microsoft.com/en-us/research/blog/memora-a-harmonic-memory-representation-balancing-abstraction-and-specificity/)).

## Current SALTMDB State

(Baseline as given, for comparison purposes — not re-derived from source code.)

- **Storage**: a single local SQLite file. Hybrid retrieval combines FTS5/BM25 keyword search with dense vector search (`fastembed`, `BAAI/bge-small-en-v1.5`, 384-dim, via a `sqlite-vec` vec0 virtual table), merged with Reciprocal Rank Fusion (RRF).
- **Entity lifecycle**: entities carry a `status` (raw → consolidated → archived), an SCD-Type-2-style `valid_from`/`valid_to` temporal versioning scheme, and a `parent_ids` JSON lineage trail.
- **Consolidation**: a background "Librarian" worker performs garbage-collection-style consolidation — merging/superseding near-duplicate raw memories into a single consolidated entity, soft-archiving originals (never hard-deleting) and auto-creating `consolidated_from` graph edges.
- **Dedup**: explicit content-hash exact-match checking plus embedding cosine-similarity thresholds (0.75 = "supersession candidate," 0.85 = "likely duplicate").
- **Quality gate**: a pre-write scorer (entropy, n-gram repetition, perplexity, readability) rejects low-quality/garbage writes before embedding/storage.
- **Organization**: tags are a freeform folksonomy with canonical-alias merging; a separate typed directional `relations` graph (source→predicate→target) connects entities.
- **Multi-agent design**: explicitly built to be shared across differently-branded CLI tools (Claude Code, Antigravity, Copilot, Codex, Cursor), with per-agent `owner_id` and shared vs. private `scope`.
- **Memory model**: no episodic/semantic/procedural distinction — everything is one flat "entity" type, differentiated only by tags/relations/status.

## Gaps / Problems

1. **No true bi-temporal model.** SALTMDB's `valid_from`/`valid_to` is a single SCD-2 axis that conflates *when a fact was true* with *when the system learned/recorded it*. Graphiti's four-timestamp model (`created_at`/`expired_at` for transaction time, `valid_at`/`invalid_at` for real-world time) is resolved independently precisely so that out-of-order or backdated information ("I actually started that job in March, not June") can be corrected without destroying the audit trail of what the system believed at each point in time. SALTMDB currently has no way to represent "we now know this fact was true earlier than we thought" without conflating it with "we just learned about it."
2. **No explicit fact-level contradiction detection.** The Librarian merges near-duplicates by embedding similarity, but nothing in the described pipeline specifically detects that memory B *contradicts* memory A (as opposed to merely overlapping/duplicating it) the way Graphiti's invalidation prompt or mem0 v2's UPDATE/DELETE branch does. Consolidation and contradiction are different problems; SALTMDB currently only solves the former.
3. **No memory-type distinction.** Every system surveyed except OpenAI's opaque implementation distinguishes at least two kinds of memory with different lifecycles: Letta's core (always-in-context) vs. archival (search-on-demand) vs. recall (raw log); Zep's episode vs. semantic-entity vs. community subgraphs; Cognee's session vs. permanent memory. SALTMDB's flat entity model has no equivalent of "this is a small always-injected fact" vs. "this is deep archival knowledge only surfaced on relevant search" — everything is retrieved the same way regardless of how foundational or frequently-needed it is.
4. **No virtual-context/overflow handling analogue.** Letta's core idea — explicit agent-driven paging between in-context "RAM" and external "disk" as the context window fills — and Anthropic's context-editing (auto-clear + pre-clear warning) both solve a real problem: a long agent session's tool-call/context history growing unbounded. SALTMDB is a memory *store*, but has no companion mechanism for the *host agent's own context window* — it depends entirely on the calling agent (Claude Code, etc.) manually deciding to search/store at the right moments (per Phase A–D of the CLAUDE.md protocol), with nothing automatic on the overflow side.
5. **No relation/entity auto-extraction.** SALTMDB's `relations` graph is populated by explicit `manage_relation` calls from the calling agent. Every graph-based competitor (mem0ᵍ, Graphiti, Cognee) runs an LLM extraction step that *automatically* derives entities and relationships from raw stored text. Without this, SALTMDB's relation graph is only as complete as agents remember to make it — there's a real risk of a sparse, inconsistent graph over time (the flip side of avoiding LLM-in-the-loop cost, see Risks below).
6. **No community/summary layer.** Zep's community subgraph and Cognee's `memify` pruning/reweighting pass both provide a cheap, higher-level "gist" view of a growing memory store. SALTMDB's consolidation produces one merged entity from a small duplicate cluster, but nothing periodically re-clusters *unrelated-but-topically-adjacent* memories into higher-level summaries the way a community-detection pass would.
7. **Coarser multi-tenancy than Zep's user/group graphs.** SALTMDB's `owner_id` + `scope` (shared/private) is designed for cross-*vendor* agent sharing (Claude vs. Antigravity vs. worker subagents), which is a genuinely different and arguably harder problem than Zep's/Cognee's cross-*human-user* isolation — but as a result, SALTMDB has no equivalent of a fully isolated "graph per human user" if it were ever asked to serve multiple actual humans, only per-agent-brand and shared/private scoping.
8. **No client-directed "just-in-time" file tier.** Anthropic's memory tool shows a lighter-weight pattern than full semantic search: an agent explicitly writing/reading named files it controls, useful specifically for the "resume exactly where I left off" multi-session software-project case. SALTMDB's `ephemeral_memory` is closest to this in spirit but is explicitly volatile/in-memory rather than a durable, agent-organized file-like tier that survives process restarts without going through the full store/consolidate/search pipeline.

## Proposed Improvement Plan

### Quick Wins (low schema risk, days not weeks)

1. **Split transaction-time from event-time on `relations` only.** Add two nullable columns to the `relations` table — `valid_at` (when the calling agent asserts the fact became true in the world; defaults to `created_at` if not supplied) and `invalid_at` (when it stopped being true / was superseded) — alongside the existing row-level `created_at`. This is a much smaller, lower-risk surface than retrofitting bi-temporal fields onto every entity, and `relations` is exactly the layer other systems (Graphiti, mem0ᵍ) treat as "facts." `manage_relation` gains an optional `valid_at` param; a new `invalidate_relation` action sets `invalid_at` rather than deleting the edge, mirroring Graphiti's non-destructive invalidation.
2. **Add a lightweight `memory_kind` tag convention** (`#episodic`, `#semantic`, `#procedural`) as canonical top-level tags via `get_canonical_tags`, so retrieval and future consolidation logic can filter/weight by kind without a schema migration. This is the cheapest possible first step toward the memory-type distinction every competitor has.
3. **Contradiction flag on the 0.85 "likely duplicate" path.** When `store_memory`'s dedup check hits the 0.85 cosine threshold, add a cheap heuristic pre-check (e.g., negation/antonym pattern match, or a one-line prompt to the *calling* agent rather than an embedded LLM call — see Risks) asking "does this contradict or merely restate the existing memory?" before deciding merge vs. supersede vs. flag-for-review. Even a crude version closes gap #2 without adding a hard LLM-in-the-loop dependency to the server itself.
4. **Expose `is_core` as a genuine "always retrieved" tier**, not just a search filter. Concretely: `search_memory` with no explicit `tags_filter` should always prepend any `is_core=true` entities matching the current `owner_id`/scope before RRF-ranked results, capped at a small token budget — a cheap approximation of Letta's core-memory-block behavior using SALTMDB's existing `is_core` flag.

### Medium-Term (schema additions, one migration)

5. **Bi-temporal `relations` becomes a first-class invalidation workflow.** Build on Quick Win #1: when `manage_relation` is called with a `predicate`/`source_id`/`target_id` combination that semantically conflicts with an existing non-invalidated edge (detected via embedding similarity between predicate+target text, analogous to Graphiti's semantic/keyword/graph search step), automatically set the older edge's `invalid_at` to the new edge's `valid_at` — including the out-of-order case (if the new edge's `valid_at` predates an existing edge's `valid_at`, invalidate based on world-time ordering, not insertion order, exactly as Graphiti does for the marriage/divorce example).
6. **Shared "core memory blocks" analogous to Letta.** Add a `block_ids`-style linkage: a small set of designated entities (tagged `#core` + `is_core=true`) that every `owner_id` sharing a `context_id` or project automatically receives at the start of `search_memory(tags_filter=['#core'])` (Phase A bootstrap already does this) — formalize this as a first-class "pinned to all agents on this project" concept rather than an implicit convention, so a memory edit by one agent brand is guaranteed visible to the next agent's next bootstrap call, matching Letta's "edit propagates to all attached agents" guarantee.
7. **Session/task-scoped durable file tier, modeled on Anthropic's memory tool.** Extend `ephemeral_memory` (currently purely volatile) with an optional `durable=true` mode that writes small, agent-named key/value blobs to a lightweight on-disk table (still inside the one SQLite file, just a separate low-overhead table with no embedding/FTS indexing) — giving agents a cheap "write my progress before I run out of context" escape hatch that doesn't invoke the full quality-gate/embedding/consolidation pipeline for what's often disposable session state.
8. **Auto-derive relations from stored text via the calling agent, not a server-side LLM.** Rather than SALTMDB itself running an extraction LLM call (see Risks — this breaks local-first purity), formalize a convention where `store_memory` responses include a short "suggested relations" prompt-instruction back to the calling agent (which already has an LLM in the loop) asking it to call `manage_relation` for any entities/relationships mentioned in the content it just stored. This gets mem0ᵍ/Graphiti/Cognee's auto-extraction *benefit* (a denser, more complete relation graph) without SALTMDB hosting its own extraction model.

### Larger Bets (multi-week, optional/opt-in)

9. **Community/summary layer.** A periodic (Librarian-adjacent) background pass that clusters tag-adjacent or embedding-adjacent-but-not-duplicate consolidated entities into a new "community" entity type with a synthesized summary and `consolidated_from`-style edges to its members — Zep's community subgraph and Cognee's `memify` reweighting both validate this as worth the complexity once entity count grows large enough that flat search starts returning too many topically-related-but-individually-thin results.
10. **Optional pluggable graph backend for power users**, mirroring Cognee's backend abstraction: keep SQLite + sqlite-vec as the mandatory zero-ops default, but allow an opt-in adapter (e.g., Kuzu, which is itself embedded/serverless like SQLite, unlike Neo4j) for users who want true graph-traversal queries over the `relations` table at a scale where SQL recursive CTEs stop being practical. This should remain strictly additive — never a requirement — to preserve the local-first, single-file guarantee.
11. **A genuine "virtual context management" companion for the *calling* agent's own context window**, not just SALTMDB's stored memory — e.g., a documented pattern (or even a lightweight hook) where the calling CLI agent is prompted to call `store_memory`/`ephemeral_memory` proactively before a known context-clearing event, similar to how Anthropic's context editing gives Claude an explicit warning before clearing. This is squarely a "CLAUDE.md protocol" concern rather than a SALTMDB schema concern, but it's the single biggest fidelity gap versus Letta/Anthropic's approach to overflow, and worth calling out as an adjacent (non-schema) improvement.

## Risks & Trade-offs

- **Local-first single SQLite file is a deliberate constraint, not an oversight.** Zep/Cognee/mem0ᵍ's use of Neo4j (or FalkorDB/Neptune) buys real graph-traversal power but reintroduces an external service dependency SALTMDB explicitly avoids. `sqlite-vec` + FTS5 already gives hybrid retrieval without a separate vector-DB service. Any graph-backend adoption (Larger Bet #10) must stay strictly opt-in and embedded (Kuzu-like), never a mandatory server process, or it breaks the zero-ops promise that differentiates SALTMDB from every hosted competitor surveyed here.
- **No LLM-in-the-loop extraction is also deliberate, and mem0/Graphiti/Cognee's biggest architectural cost.** mem0's ADD/UPDATE/DELETE decision, Graphiti's invalidation prompt, and Cognee's `cognify` entity extraction all cost an LLM call (latency + $ + non-determinism + a hard dependency on a specific model) *per write*. SALTMDB's design deliberately keeps the server itself LLM-free; the pre-write quality gate uses cheap statistical scoring (entropy/perplexity/readability), not a model call. The proposed contradiction-detection and auto-relation-extraction improvements above are written to route any LLM reasoning back through the *calling* agent (which already has one) rather than embedding a model inside SALTMDB itself — this preserves the deliberate trade-off, but means SALTMDB's contradiction/extraction quality will always depend on how diligently the calling agent follows the protocol, unlike Graphiti/mem0 where it's structurally guaranteed by the server.
- **SALTMDB's multi-tenancy problem is different in kind from the surveyed systems', not just smaller.** Mem0/Letta/Zep/Cognee are single-vendor SDKs solving cross-*human-user* isolation (a SaaS company serving many end users). SALTMDB's `owner_id`/`scope` solves cross-*agent-vendor* sharing (Claude Code, Antigravity, Copilot, Codex, Cursor all sharing one human's memory) — a genuinely novel differentiator none of these systems target. Directly porting Zep's `user_id`/`group_id` model would solve a problem SALTMDB doesn't currently have (many humans) while doing little for the problem it does have (many agent brands); any multi-tenancy work should extend `owner_id`/`scope`, not replace it with a human-user-graph model.
- **mem0 v3's "never delete, rank at retrieval time" approach trades write-time cleanliness for read-time complexity** — appropriate at mem0's SaaS write volume and latency budget, less obviously a win for SALTMDB's local single-user setting, where the existing content-hash + cosine-threshold dedup at write time keeps the store small and each `search_memory` call cheap. Adopting ADD-only wholesale would grow the SQLite file and search index unboundedly and shift the entire staleness-detection burden onto RRF ranking; the bi-temporal invalidation approach (Quick Win #1 / Medium-Term #5) gets Graphiti's "never destroy history" benefit without mem0 v3's unbounded-growth trade-off, since invalidated edges can still be pruned/archived later.
- **Bi-temporal fields add real schema and query complexity.** Scoping this to `relations` only (rather than all entities) is a deliberate risk-reduction choice in this plan — a full bi-temporal retrofit of the `entities` table would be a much larger, riskier migration for a benefit (entity-level fact versioning) that's arguably better captured by the existing SCD-2 `valid_from`/`valid_to` + `parent_ids` lineage already in place at the entity level.

## Open Questions for zbalint

1. Is an LLM-in-the-loop extraction/contradiction step ever acceptable inside SALTMDB itself, or should extraction/contradiction-detection always be delegated to the calling agent (as the plan above assumes) to preserve the local-first, model-agnostic design?
2. Is genuine multi-*human*-user sharing (Zep-style isolated user graphs) ever in scope for SALTMDB, or will it always be single-human/multi-agent-brand? This materially changes whether Medium-Term #6 (shared core blocks) or a Zep-style `user_id`/`group_id` split is the right direction.
3. Should bi-temporal fields (`valid_at`/`invalid_at`) go on the `relations` table only (as proposed), or do you also want entity-level fact versioning distinct from the existing SCD-2 `valid_from`/`valid_to` (which currently conflates event-time and system-time at the entity level)?
4. Is an opt-in embedded graph backend (e.g., Kuzu) ever desirable for power users doing heavy graph traversal over `relations`, or is "single SQLite file, no exceptions" a permanent constraint?
5. How much dedup precision are you willing to trade for retrieval-time simplicity? I.e., is SALTMDB's current write-time dedup (0.75/0.85 thresholds + Librarian merge) considered a feature worth protecting, or would you consider moving toward mem0 v3's "never delete, rank at retrieval" model if it improved recall on contradictory/updated facts?
6. Do you want a formal "core memory block" concept (Letta-style, pinned + auto-shared across agents) as a first-class feature, or is the existing `is_core` tag + Phase A bootstrap search close enough in practice?
