## 1. Why

The bulk path computes ONE set of fresh centroids, unresolved reasons and observed states for the union of all parents (`get_fresh_entity_centroids`) and then slices them per item. That is exactly what `_BulkContext` already holds (three fields with the same names), but `_write_bulk_consolidations` (10 parameters) takes the three union maps as separate arguments, passes them to `_commit_bulk_consolidation_item` (9 parameters) as separate arguments, and that function rebuilds the three per-item dicts inline and wraps them in a `_BulkContext`. Besides that, `_write_bulk_consolidations` fills a `results` list passed in by `apply_consolidations` (an out-parameter, cleared at the start of each retry), and the handler for a rejected item in `apply_consolidations` computes the failed item's position as `len(results)` from that same list. `agent_id`, `context_id` and `agent_session_id` travel as three loose parameters although `Provenance` groups them.

Rejected: changing the order or atomicity of the batch (one savepoint around all items, vectors cleared after the savepoint); changing the per-item override rule (`item.get("agent_id", agent_id)`, `item.get("context_id", context_id)`, `agent_session_id` batch-wide); a new class for the batch.

## 3. Decisions

- D1. Behaviour is identical for every input: item order, the per-item defaults and overrides, the single savepoint, the vector clearing after the savepoint, the `CONSOLIDATION_FAILED`/`INTERNAL_ERROR` mapping, the coordinator re-raise (`is_coordinator_connection(conn)`), the rejected item's field prefix `items[<index>]...`, and that after a retry nothing from the first attempt remains (today `results.clear()` at the start of the write; after the change the return value of the final attempt is used).
- D2. Typing: `_BulkContext` keeps `dict | None` fields (single-call callers pass `None`s); `for_parents` is only defined for the union context, so it reads the three fields with a narrowing guard that raises a clear `ValueError` if any is `None` (a programming error, never reachable from `apply_consolidations`), not an `assert`.
- D3. `index` is the zero-based position within `item_resolved_parents` of the item that raised; for an exception that is not `_BulkItemRejected` nothing changes (`apply_consolidations` still goes through its generic `except Exception`).
- D4. No `noqa`; no change to any message text.

## Amendment 1 (2026-10-24): one reading of the failed-item bullet governs

Section 2 states the failed item's index twice, in two bullets that disagree on the return shape of `_commit_bulk_consolidation_item`. The first says it returns ONLY the raw `consolidate_memories` result, with the status check, the `raise _BulkItemRejected(result, index)` and `_bulk_item_success(item, result)` in the loop. A1.2 In the second bullet, the sentence from "`_commit_bulk_consolidation_item` returns" to "receives the raw result)" is superseded by A1.1. Everything else in that bullet stays in force: `_BulkItemRejected` gains `index: int` as its second positional argument, `str(exc)` does not change, `apply_consolidations` reads `exc.index`, `_commit_bulk_consolidation_item` keeps 5 parameters, and `consolidate_memories` is still called with keyword arguments only.
