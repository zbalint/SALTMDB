## 1. Why

Under the daemon the whole service call is ONE coordinator job inside the coordinator's outer `BEGIN IMMEDIATE`, and a nested `write_transaction_retrying` just calls `fn(conn)` (`db/connection.py`, the `conn is _coordinator_connection.get()` early return). A service that raises inside its transaction block and catches outside therefore does not roll anything back: the coordinator commits the earlier writes. S2b found this for the batch tools and fixed the new services with a SAVEPOINT (S2b amendment 2). The consolidation code has the same defect, in two places:

- `consolidate_memories`: `_consolidation_commit` writes the override audit event, the new entity, the parents' archive, tags, embedding jobs and lineage edges in sequence. A failure after the first write (a tag or detail-relation write, a lineage insert, an SQLite fault) is caught by `except Exception` and returned as `CONSOLIDATION_FAILED`, but under the daemon the earlier writes (for example the audit event and the new entity row) are committed with it.
- `bulk_commit_consolidation`: its docstring promises all-or-nothing. Item N's failure raises `RuntimeError` out of `_write_bulk_consolidations`, the outer `except` returns the error list, and under the daemon the coordinator commits items 0 to N-1. `tests/test_librarian_service.py::test_bulk_commit_consolidation_is_all_or_nothing` proves nothing about it: consolidation requires at least two distinct active parents (`REJECT_PARENT_COUNT`, `_resolve_and_validate_parent_ids`), so both of its items (one parent, then none) are rejected during the pre-transaction parent resolution and the write phase is never reached, in any mode. A bulk atomicity test is only meaningful when the failing item is rejected INSIDE the transaction, after an earlier item wrote.

A second hazard decides the shape: `_consolidation_archive_parents` deletes the parents' vector rows (`entity_embeddings`, `entity_chunk_embeddings`, `retrieval_embeddings`, sqlite-vec virtual tables) inside the write. A savepoint rollback of a virtual-table delete is not something this repository tests, so vector deletes must happen only after the last possible rejection.

Alternatives rejected: (a) validate everything first and only then write (the BL-063 "P1" idea, which this spec deliberately supersedes): consolidation validation is the preflight, the TOCTOU revalidation and the core capacity admission, which depend on the writes of earlier items; a no-write pre-pass would duplicate those rules and still need the savepoint for the writes it cannot predict. (b) Run each batch item in its own savepoint and report mixed results: the documented contract is all-or-nothing. (c) Fix it in `dispatch.py` by wrapping every mutating tool in a savepoint: it would hide the same defect in the other catch-after-write services instead of finding it, and changes the job semantics of every tool. (d) Change the old bulk archive and relation services: they are removed by BL-062.

## 2. Decisions

- D1 `savepoint(conn, prefix)` in `db/connection.py`, a `contextmanager`. On entry it requires `conn.in_transaction` (else `RuntimeError`; a SAVEPOINT outside a transaction would start its own deferred transaction and its RELEASE would commit) and issues `SAVEPOINT <prefix>_<uuid4 hex>`. On a normal exit it requires `conn.in_transaction` again (else `RuntimeError`, an outer transaction that died silently must not be committed around) and issues `RELEASE`. When the block raises: if `conn.in_transaction` it calls the existing `rollback_to_and_release`, then re-raises the ORIGINAL exception; if the connection is no longer in a transaction (an SQLite fault rolled it back itself) it re-raises without touching the savepoint. If `rollback_to_and_release` itself raises while the connection is still in a transaction, it issues a full `ROLLBACK` (so the coordinator's COMMIT fails and the job fails closed instead of committing the block's rows), logs the rollback error, and re-raises the ORIGINAL exception. It never swallows an exception. This is the only place the rule "undo the block, keep the outer transaction" lives; the two S2b savepoints stay as they are (their migration to this helper is a separate cleanup, recorded in section 5).
- D2 `consolidate_memories` (single): the `_write` closure runs `_consolidation_commit` inside `with savepoint(c, "consolidation")`, then, after the block exited normally, calls the D3 helper for the resolved parents. Exceptions keep their present mapping (`except Exception` to `CONSOLIDATION_FAILED`, outside the transaction block, message unchanged); the difference is that the failed call now leaves zero rows behind under the coordinator as well. With `_bulk is not None` (called from the batch) only `_consolidation_commit` runs: no savepoint of its own (the batch owns it) and no vector clear (D4). Shape (keeps the existing single `if _bulk is not None` as the only switch, so no new nesting in `consolidate_memories`): one rows-only closure that clears `orphaned_edges` first and calls `_consolidation_commit`; the bulk branch calls it directly; the non-bulk branch runs `write_transaction_retrying(conn, lambda c: _commit_single(c))` where `_commit_single` is `with savepoint(c, "consolidation"): rows(c)` followed by D3. `orphaned_edges.clear()` as the first statement of the rows closure fixes a pre-existing duplication of worklist entries when `write_transaction_retrying` reruns the closure after a lock error at COMMIT in DIRECT mode. A caller that holds its own savepoint around a single `consolidate_memories` call must pass `_bulk` and clear vectors itself (a vector delete inside a region that can be rolled back to is the hazard D3 exists to avoid); S3 inherits this rule.
- D3 `_clear_archived_parent_vectors(conn, parent_ids: list[str]) -> None` in `relation_service.py`: for each id calls `clear_embedding_vectors_for_entity(conn, id)` and `cancel_retrieval_embedding_jobs_for_entity(conn, id, clear_vector=True)` (the lazy import from `embedding_service`, as `_consolidation_archive_parents` does today). One responsibility: the vector side effects of archiving, run after the last possible rejection. `_consolidation_archive_parents` loses its `clear_embedding_vectors_for_entity` call and calls `cancel_retrieval_embedding_jobs_for_entity(..., clear_vector=False)`; everything else it does (jobs, tags, the archive UPDATE, `cancel_embedding_jobs_for_entity`) is plain-table work and stays inside the savepoint. Both vector helpers already swallow `sqlite3.Error` (debug log), so the helper cannot reject.
- D4 `bulk_commit_consolidation`: `_write_bulk_consolidations` wraps its loop in `with savepoint(conn, "bulk_consolidation")`; after the block exited normally it calls D3 once with every item's resolved parents, in item order. A rejected or raising item propagates out of the block (the existing `RuntimeError` from `_commit_bulk_consolidation_item`), the savepoint is rolled back, and the existing outer `except` returns the unchanged single top-level error list. The function's argument list and return shape do not change. The cross-item shared-parent case is caught by the existing TOCTOU revalidation inside the savepoint (the second item sees the first's archive) and is covered by a test.
- D5 Audit (report only, no code change outside D1 to D4): the developer reads every `except Exception` / `except ... as exc` block in `relation_service.py` (the grep gives lines 150, 725, 848, 1020, 1301, 1527, 2684, 2897, 3014) and the governance catch of `store_memory`, and for each states in the report: does a write happen before the catch inside the same coordinator job, and would that write survive a caught failure? For each block the report also names any helper still called inside the D2/D4 savepoint that swallows `sqlite3.Error` (`resolve_or_create_tag`, the core governance calls): a swallowed fault after the outer transaction died lets later statements autocommit before `savepoint`'s exit check. The report also records, from a throwaway probe in a scratch directory, whether sqlite-vec `INSERT`/`DELETE` inside a `SAVEPOINT` followed by `ROLLBACK TO` restores the row count and a KNN result (if yes, the D3 split could later be simplified; this spec keeps it). The report notes the pre-existing masking in DIRECT mode: after an SQLite fault that kills the transaction, `write_transaction`'s own `ROLLBACK` raises "no transaction is active" and hides the original message in `CONSOLIDATION_FAILED`. The report also covers the two latents the tester recorded for S2b: the swallowed outer-transaction death between items of the `apply_relations` loop, and two successive savepoint batches in one coordinator job. Findings the developer proves with a throwaway probe become proposed backlog rows in the report; the architect writes them. No production code outside D1 to D4 changes in this spec.

## 4. Tests

Written failing first. Each case runs in two modes via a parametrized fixture: DIRECT (temporary database, no coordinator) and COORDINATOR (a started `DbWriteCoordinator` on a temporary database, `dispatch_tool("consolidate_memories", ...)`, snapshots read from a fresh connection after the job). Snapshot = full row dumps of `entities`, `relations`, `events`, `entity_tags`, `embedding_jobs`, `retrieval_embedding_jobs` plus the FTS row count; literal expected values.

1. Single consolidation with two parents, failure after the first write (patch `saltmdb.domain.services.relation_service._consolidation_insert_lineage` to raise `sqlite3.OperationalError("injected failure")`; the entity insert, tags, jobs and the parents' archive have already been written, the transaction is still alive): result is `CONSOLIDATION_FAILED`, the snapshot equals the one taken before, parents still `raw`. In COORDINATOR mode this FAILS on the old code (the red phase).
2. Positive control: the same call without the patch commits one consolidated entity, archives both parents, and writes two `consolidated_from` edges.
3. Order: patch `saltmdb.domain.services.embedding_service.clear_embedding_vectors_for_entity` and `saltmdb.domain.services.embedding_service.cancel_retrieval_embedding_jobs_for_entity` (the call sites import them lazily from that module; `relation_service` has no such attributes) with recorders. A failing single consolidation never calls the vector clear (no vector delete on a rolled-back call). A successful one calls it once per parent, and the order is observed with `set_trace_callback` on the job's connection (in COORDINATOR mode the coordinator's connection, installed inside the job): the `RELEASE` statement of the consolidation savepoint precedes the first recorder call.
3b. Transaction death inside the block (separate case): the injected failure executes an explicit `ROLLBACK` on the connection and then raises: the original exception reaches `consolidate_memories`' catch (`CONSOLIDATION_FAILED` with the injected message), and no `ROLLBACK TO` error masks it.
4. Bulk, item 1 of 3 fails INSIDE the transaction: items 0 and 2 are valid (two distinct parents each, four memories), item 1 has two valid parents and content the quality gate rejects (take the literal from the quality-reject case in `tests/test_consolidate_memories_phase4.py`); the preflight runs inside the transaction for bulk items and a non-ok result becomes the `RuntimeError` of `_commit_bulk_consolidation_item`. Result: single top-level error list, snapshot unchanged, no vector helper called. FAILS on the old code in COORDINATOR mode (item 0's rows are committed there). An item with empty or single `parent_ids` is NOT a valid rejecting item: it is rejected before the transaction opens and would pass on the old code.
5. Bulk, failure after item 0 committed its rows (patch the lineage insert to raise on the second call): snapshot unchanged.
6. Bulk shared parent: two items naming the same parent: top-level error, snapshot unchanged.
7. Bulk positive control: three items commit, vector helpers called once per parent, after the last item.
8. Composability, COORDINATOR only (one coordinator job submitted with a function that calls the services directly on the coordinator connection; `dispatch_tool` runs one tool per job): insert an unrelated event row, then run a bulk consolidation rejected as in test 4: the unrelated row persists, no consolidation row does. A second case in the same job: a rejected bulk followed by a valid single consolidation (fresh parents) both in one job: only the valid one persists (the savepoint stack).
9. `savepoint` unit tests: outside a transaction raises `RuntimeError` and issues no statement; success releases (outer ROLLBACK afterwards still undoes the block's rows only when it was the outer one: assert row visibility inside and absence after an outer rollback); a raise rolls back to the savepoint and re-raises the same exception object while earlier outer rows survive; when the connection left the transaction inside the block (simulate with an explicit `ROLLBACK`), the original exception is re-raised and no `ROLLBACK TO` error masks it; a normal exit with `in_transaction` false raises `RuntimeError`; when `rollback_to_and_release` itself raises (patched), a full `ROLLBACK` is issued, the original exception is re-raised and the block's rows are gone.

Mutants the tester must kill (each fails a named test): no savepoint in the single path; no savepoint in the bulk path; `ROLLBACK TO` without `RELEASE`; `RELEASE` without `ROLLBACK TO`; the savepoint swallows the exception; the vector clear moved back inside `_consolidation_archive_parents`; the vector clear run before the savepoint exits; the bulk clears per item instead of once after the last; the single path clears vectors when `_bulk` is set; `savepoint` skips the `in_transaction` entry check; `savepoint` calls `ROLLBACK TO` when the connection already left the transaction; `savepoint` lets a failing `rollback_to_and_release` replace the original exception or skips the fallback `ROLLBACK`; `orphaned_edges.clear()` removed (a test reruns the rows closure twice and expects one worklist).
