## Research Summary

### 1. Classic folksonomy governance (del.icio.us, Flickr, "tag gardening")

Golder & Huberman's foundational study of collaborative tagging (del.icio.us) found that tag vocabularies grow with a **sub-linear, power-law-like distribution** — a small number of tags dominate usage while a long tail of idiosyncratic tags accumulates, and this pattern is "remarkably regular" across resources and over time ([Golder & Huberman 2006](https://journals.sagepub.com/doi/10.1177/0165551506062337); [ResearchGate copy](https://www.researchgate.net/publication/220195608_Usage_Patterns_of_Collaborative_Tagging_Systems)). The practical implication: fragmentation is not a bug that appears occasionally, it is the *default steady-state* of any freeform tagging system with more than one contributor — the long tail of one-off tag spellings never self-heals without an explicit maintenance process.

Peters & Weller's "Tag Gardening" framework ([Webology 2008](https://www.webology.org/2008/v5n3/a58.html), [ResearchGate](https://www.researchgate.net/publication/267415126_Seeding_Weeding_Fertilizing_-_Different_Tag_Gardening_Activities_for_Folksonomy_Maintenance_and_Enrichment)) names three distinct maintenance activities that map directly onto SALTMDB's problem:
- **Seeding** — proactively suggesting tags at creation time from an existing/controlled vocabulary (equivalent to `get_canonical_tags` today).
- **Weeding** — after-the-fact merging/removal of redundant, misspelled, or overly narrow tags (equivalent to `merge_tags_heuristics()` + manual `merge_tags`).
- **Fertilizing** — enriching tags with semantic relations (broader/narrower/related-to) so search and browsing don't depend on exact string match at all. **SALTMDB currently has no fertilizing layer** — tags are flat with only an alias→canonical edge, no broader/narrower/related structure.

The general finding across folksonomy literature ([Studying Social Tagging and Folksonomy: A Review and Framework](https://jodi-ojs-tdl.tdl.org/jodi/article/download/269/278); [Tagging, Folksonomy & Co](https://arxiv.org/pdf/cs/0701072)) is that **seeding alone is insufficient** — even systems with tag auto-complete/suggestion at write time (which SALTMDB already effectively has via `get_canonical_tags`) still fragment, because taggers under time pressure don't always check, and near-synonyms that aren't lexically close (e.g. "fix" vs "bugfix") aren't caught by suggestion-as-you-type UIs anyway. Weeding after the fact is therefore treated in the literature as *mandatory*, not optional cleanup.

Archive of Our Own (AO3)/Organization for Transformative Works runs the largest documented human "tag wrangling" operation: as of 2022, roughly 400 volunteer wranglers plus ~30 supervisors and 4 chairs maintain the canonical/synonym/parent-child tag graph across the whole archive, with a multi-week formal training pipeline for new wranglers ([OTW Tag Wrangling spotlight](https://www.transformativeworks.org/spotlight-tag-wrangling/); [Fanlore: OTW Tag Wrangling Committee](https://fanlore.org/wiki/OTW_Tag_Wrangling_Committee)). This is the closest real-world analogue to "weeding at scale," and it is instructive precisely because of the *scale of dedicated human labor* it takes to keep a large freeform folksonomy coherent — hundreds of trained humans, for one archive. It is strong evidence that **the fragmentation problem is not solvable by clever heuristics alone**; AO3's solution is organizational (a standing curation workforce), not purely algorithmic. SALTMDB has zero human curators in the loop by design, which is the crux of why generic tag-gardening advice under-delivers here (see Gaps section).

### 2. Stack Overflow / Stack Exchange tag synonym system

Stack Overflow's synonym system ([Stack Overflow Blog, 2010](https://stackoverflow.blog/2010/08/01/tag-folksonomy-and-tag-synonyms/); [Stack Overflow for Teams: Tag Administration](https://stackoverflowteams.help/en/articles/8944241-tag-administration)) works as follows:
- A **synonym is a directional mapping** from a "child" tag string to a canonical "parent" tag — e.g. `js` → `javascript`, `java-script` → `javascript`.
- Critically, **a synonym can only be proposed for a tag that already exists on at least one live post** — i.e., the system requires *evidence of real fragmentation* before a synonym mapping is even eligible, rather than trying to pre-empt hypothetical future fragmentation.
- Once approved, the remap is **silent and retroactive**: every existing and future post tagged with the child string is automatically rewritten to show the canonical tag. Users never see "js" in a canonical tag list again — the fragmented string still round-trips as input but the *stored, indexed, displayed* value is always the canonical one.
- Approval is **community-moderated** (votes/review by higher-trust users or site moderators), not simply auto-applied on proposal — there is always a human review gate before a merge is committed, specifically because synonym proposals are occasionally wrong (e.g. two tags that look similar but denote genuinely different concepts, like `session` vs `sessions` in a codebase could be legitimately distinct if one is a Django-app label and one is a general concept — Stack Overflow's own docs warn synonym merges are one-way and hard to reverse cleanly).

This is essentially the same alias→canonical design SALTMDB already has (`canonical_id` self-FK) — the part SALTMDB is missing is **(a) an explicit synonym *proposal* queue with review before commit**, rather than only "heuristic auto-merge" (fully automatic, no gate) or "manual merge_tags" (requires an agent to notice and act, with no queue/backlog tracking of *unactioned* candidates), and **(b) the evidentiary bar** ("must already be attached to ≥1 entity") which SALTMDB's `merge_tags` tool does not enforce as a precondition — nothing stops an agent from inventing a synonym mapping for a tag that isn't even fragmented yet, which is really a `store_memory`-time problem, not a merge-time one.

### 3. Modern PKM tools (Notion, Obsidian, Logseq)

- **Notion** avoids freeform-tag fragmentation almost entirely by *not using freeform tags* for structured data — it uses `Select`/`Multi-select` **properties**, which are a closed enumerated list per-database; new values must be explicitly added to the property's option list (a first-class, curated enum), and the UI defaults to autocomplete-against-existing-options rather than free text ([Notion Help: Database properties](https://www.notion.com/help/database-properties)). This is architecturally the strongest anti-fragmentation stance in the survey: it isn't better *tag hygiene*, it's a different data model — closed vocabulary by construction, with addition of new options being a deliberate, visible, low-frequency action rather than typed at time of every note.
- **Obsidian** uses flat and `/`-nested hierarchical tags (e.g. `#project/website-redesign`); a search for `tag:#project` matches the parent and all children. Obsidian tags are **case-insensitive for matching but display whichever casing was typed first**, which the community explicitly flags as a source of visual (if not functional) inconsistency in the tag pane. Obsidian relies on **autosuggest-from-existing-tags at write time** as its primary anti-fragmentation mechanism — i.e., pure "seeding," no automated "weeding" pass exists in the product; users are advised as a matter of manual discipline to "pick one naming style and stick to it" ([Practically Paperless with Obsidian Ep. 21](https://www.goodreads.com/author_blog_posts/22313310-practically-paperless-with-obsidian-episode-21-tags-in-theory-and-tags); [mattgiaro.com](https://mattgiaro.com/organize-notes-obsidian/); [desktopcommander.app](https://desktopcommander.app/blog/how-to-use-tags-in-obsidian-markdown/)). This corroborates the folksonomy literature's point above: **autosuggest/seeding-only tools still fragment in practice**, because compliance is voluntary and per-writer, and — critically for SALTMDB — Obsidian's writer is a single human with continuity of memory across sessions; SALTMDB's writers are *stateless LLM calls* with no memory of their own past tagging choices unless the tool forces a lookup.
- **Logseq/other outliner tools** offer similar `/`-nested tags with no strong governance beyond autocomplete; no tool in this survey implements automated semantic-similarity-based tag merging as a built-in feature — this appears to be a genuine product gap across the whole PKM category, not something SALTMDB failed to discover.

### 4. Embedding-based tag clustering / near-duplicate surfacing

There is an established pattern (used for LLM training-data dedup and near-duplicate detection generally) of: embed each item → cluster (k-means, DBSCAN, or HDBSCAN) → within-cluster pairwise cosine similarity above a threshold flags candidates → keep/merge on centroid-closeness, frequency, or recency ([Zilliz: How do I use embeddings for duplicate detection?](https://zilliz.com/ai-faq/how-do-i-use-embeddings-for-duplicate-detection); [SemHash for LLM data](https://medium.com/@sreeprad99/how-semhash-simplifies-semantic-deduplication-for-llm-data-a0b1a53e84fe); LLM-embeddings + HDBSCAN pattern referenced across multiple dedup papers). Reported thresholds in practice cluster around **0.85 as a "high precision" near-duplicate cutoff, ~0.80 as an F1-maximizing balance point, and >0.9 for near-identical/near-exact matches** — but these numbers come from *sentence/paragraph*-level embeddings, not single-word-or-short-phrase tag strings, and the literature is explicit that the right threshold is data-dependent and must be tuned per corpus, not assumed.

Two important caveats specific to SALTMDB's actual embedding model, `BAAI/bge-small-en-v1.5` (384-dim, via fastembed):
- The BGE v1.5 line was specifically re-tuned to **improve (spread out) the similarity distribution** relative to v1.0 — meaning cosine similarities are less uniformly "crushed" toward the high end, which helps threshold-based clustering discriminate ([BAAI/bge-small-en-v1.5 on HuggingFace](https://huggingface.co/BAAI/bge-small-en-v1.5)). But bge-small is a **general-purpose sentence/passage retrieval embedding**, not a model trained or evaluated specifically on short 1–3 word tag-label similarity (e.g. `fix` vs `bugfix` vs `hotfix`) — general embedding models are known to sometimes rate morphologically similar-but-semantically-different short strings as more similar than intended, and semantically-equivalent-but-lexically-different pairs (like `subagent` vs `worker` in this project's own vocabulary, if that pairing exists) as less similar than intended, purely because they were optimized for sentence-length inputs, not tag-length inputs. This means naive cosine-threshold clustering on raw tag-name embeddings is a reasonable *first pass* but should be treated as a **candidate-surfacing signal for a review queue, not an auto-merge trigger** — exactly the Stack Overflow "propose then gate" pattern, not the "heuristic auto-merge" pattern SALTMDB currently uses for exact/case-insensitive matches.
- Because SALTMDB already computes and stores dense embeddings **per entity** (not per tag), a second complementary signal is available beyond tag-name embedding similarity: **tag co-occurrence structure over entity embedding clusters** — i.e., cluster entities by their content embeddings, then look at which tags co-occur heavily within a cluster but rarely across clusters. Two tag strings that are lexically dissimilar (`#fix` and `#bugfix`) but are attached to entities that cluster tightly together are strong candidates for the same underlying concept — this catches synonym pairs that pure tag-string embedding similarity would miss entirely (since "fix" and "bugfix" as bare strings are not that close in embedding space, but the *entities* tagged with each are near-identical in content).

### 5. Getting multiple independent LLM agents to converge on shared vocabulary

This is the crux research question and the one where generic tagging-system literature is least directly applicable, since it assumes either a single tagger with memory, or a large community with a moderation layer — neither matches "N stateless LLM callers, no shared human, no persistent working memory beyond what's fetched via tool calls."

Findings:
- **Structured/enum-constrained output measurably increases consistency over free generation.** Constraining LLM output to a fixed enum (grammar/constrained decoding, JSON schema `enum`) forces selection from a predefined set rather than open-ended string generation, which is reported as more reliable for exactly this kind of downstream categorical consistency use case ([LM-Kit structured output guide](https://docs.lm-kit.com/lm-kit-net/guides/glossary/structured-output.html); [Humanloop: Structured Outputs](https://humanloop.com/blog/structured-outputs); general constrained-decoding literature). This directly supports the "seed then gate" strategy over "generate then reconcile."
- **Retrieval-augmented few-shot grounding beats pure few-shot.** Research on LLM tagging/classification tasks found that "without few-shot examples, LLMs tend to create their own categories with varied naming conventions that are difficult to integrate into results," and that retrieval-based in-context learning — fetching a small relevant slice of the *existing* vocabulary/examples at call time and injecting it into the prompt — measurably improves adherence to an existing taxonomy across sessions, effectively substituting for the persistent memory a single human tagger would have ([emergentmind LLM Tagging summary](https://www.emergentmind.com/topics/llm-tagging); LLM4Tag paper below). This is precisely the mechanism `get_canonical_tags` is meant to provide today — but per the Gaps section, its use is *advisory*, not enforced, which is the actual failure mode.
- **LLM4Tag** (arXiv 2502.13481, [full text](https://arxiv.org/html/2502.13481v2)) is a directly-relevant production pattern: rather than letting the LLM generate tags freely, it runs a **graph-based "tag recall" stage first** that narrows a massive tag repository down to ~20 highly-relevant *existing* candidate tags, and only then has the LLM select/rank from that closed candidate set (plus a confidence-calibration step). The paper does not itself solve synonym redundancy *within* the candidate vocabulary — it assumes that vocabulary is already curated — but the recall-then-select architecture is exactly the shape of fix that would harden `get_canonical_tags` from "optional lookup tool" into "mandatory pre-write gate."
- **Multi-agent convergence-through-interaction is a different mechanism and does not transfer to SALTMDB's architecture.** A 2026 study of simulated multi-agent LLM annotation/discussion (arXiv 2512.00047, [abstract](https://arxiv.org/abs/2512.00047)) found that groups of LLM agents *do* converge lexically and semantically on shared vocabulary — but only when they **interact over multiple rounds and can observe each other's outputs** ("semantic compression" of the group's embedding geometry over rounds). SALTMDB's tagging agents are independent, asynchronous, and non-interactive — they never see each other's in-flight choices, only what's already durably stored. This rules out "let the agents negotiate" as a viable convergence mechanism here; the only viable substitute for that interactive convergence is **forcing every write through a shared, queryable, up-to-date canonical registry** (which is what `get_canonical_tags` + a mandatory-call policy is trying to approximate) — i.e., asynchronous agents need an explicit external ground truth to converge on, since they cannot converge on each other.
- Ontology-for-agent-memory writing specifically frames the problem in the terms SALTMDB has: "without proper ontology definition, entity graphs can end up with multiple synonyms like 'Vendor', 'Supplier', and 'Counterparty' all meaning roughly the same thing," and argues the fix is a **constrained extraction schema supplied at write time**, not post-hoc cleanup, precisely because post-hoc cleanup in a knowledge-graph/memory system is expensive once relations and downstream retrieval already depend on the fragmented labels ([summarized via search result set; original discusses agent-memory ontology design]). This reinforces that **prevention at write-time must be structurally enforced (schema/tool-contract level), not left to agent discretion**, because discretion is exactly what's already failing today (agents *can* call `get_canonical_tags` and often don't).

### 6. Hierarchical / faceted tag models

- **Faceted classification** (distinct from strict hierarchy) assigns an item to multiple independent classification dimensions ("facets") simultaneously rather than one deep tree — described as easier to browse/maintain than deep taxonomies and a good middle ground between rigid controlled vocabularies and unstructured folksonomies ([Hedden Information Management: Faceted Classification](https://www.hedden-information.com/faceted-classification-and-faceted-taxonomies/); [Controlled Vocabularies in IA](https://informationarchitectureauthority.com/controlled-vocabularies/)).
- **Facetag / Quintarelli's "bottom-up and top-down" integration** proposes exactly the hybrid SALTMDB would need: keep folksonomy's low-friction bottom-up tagging, but layer a lightweight top-down faceted structure over it so that, e.g., `type:` (fix/feature/doc), `component:` (agent/tool/schema), and free-form descriptive tags are distinguished facets rather than one flat namespace where `#fix`, `#docs`, and `#skill` all collide as peers ([Facetag, Bulletin ASIS&T 2007](https://asistdl.onlinelibrary.wiley.com/doi/full/10.1002/bult.2007.1720330506)).
- **WordNet's synset (synonym ring)** model — a set of interchangeable terms representing one concept, with typed relations (hypernym/hyponym = broader/narrower) between synsets rather than between individual words — is the canonical academic data model for "many surface strings, one canonical concept, plus typed relations to other concepts" ([WordNet](https://wordnet.princeton.edu/); [Synset overview](https://medium.com/@jolalf/wordnet-lexical-database-grouped-into-synsets-case-study-e059f66e847b)). This maps closely onto Stack Overflow's synonym-to-canonical-tag model, and is worth naming explicitly as the target data shape for a "Larger Bet" (see below): SALTMDB's current `canonical_id` self-FK is a *degenerate, single-level* synonym ring (alias → one canonical), with no representation for broader/narrower relations between *canonical* concepts (e.g. `#bugfix` broader-than nothing, but conceptually child-of a hypothetical `#maintenance` facet).
- Obsidian's `/`-nesting is a cheap, purely-syntactic hierarchy (parent tag = string prefix) with no independent data modeling — useful precedent for a **low-cost, no-schema-change v1** of hierarchy (`domain:subdomain` naming convention) before investing in true faceted/graph relations.

## Current SALTMDB State

(Restated for grounding, not re-derived.)

- **Schema**: `tags` table (`id`, `name` UNIQUE, `normalized_name`, `canonical_id` self-referencing FK), indexed on `canonical_id` and `normalized_name`; `entity_tags` join table.
- **Automatic merging**: background `merge_tags_heuristics()` in `src/saltmdb/domain/services/librarian_service.py` does case-insensitive/normalized-name alias merging.
- **Write-time resolution**: `_resolve_tag_id()` in the same file resolves a tag name to its canonical id at write time.
- **Manual merge tool**: `merge_tags(keep_tag, tags_to_merge)` MCP tool repoints `entity_tags` rows to a chosen canonical tag.
- **Discovery tool**: `get_canonical_tags(query, domain)` MCP tool searches for existing near-match canonical tags before an agent invents a new one.
- **Convention, not constraint**: tags are conventionally `#`-prefixed (e.g. `#core`); `is_core` is a separate boolean column on entities, not derived from the `#core` tag string.
- **Known live fragmentation** (per 2026-07-25 internal audit already stored in SALTMDB memory): `#fix` vs `#bugfix`, `#subagent` vs `#subagents`, `#skill` vs `#skills` vs `#agent-skills`, `#dedup` vs `#deduplication`, `#doc` vs `#docs` vs `#documentation`, plus stray non-prefixed anomalies (`502`, `fake`) with no validation blocking them.
- **Multi-agent root cause**: Claude Code, Antigravity, Copilot, and other agents each independently choose tag names with no single human curator in the loop.
- **Existing embedding infrastructure**: dense embeddings already computed per-entity via `BAAI/bge-small-en-v1.5` (fastembed) for the hybrid FTS5+vector RRF search — not currently used for tag-level clustering.

## Gaps / Problems

Mapping the research above directly onto *why the existing tooling still let fragmentation happen*:

1. **`get_canonical_tags` is advisory, not enforced — this is the single biggest gap.** Every piece of research on write-time prevention (Notion's closed enum, LLM4Tag's recall-then-select, the agent-memory-ontology argument, Obsidian's autosuggest) converges on the same principle: prevention has to be **structurally unavoidable at the moment of write**, not a tool an agent *could* call. Nothing in `store_memory`'s current contract requires `get_canonical_tags` to have been called first, or rejects a tag string that wasn't returned/confirmed by it. An LLM agent under its own token-budget pressure (exactly the kind of pressure the folksonomy literature already predicts causes fragmentation even for *human* taggers with full continuity of memory) will skip the lookup call when it's optional — and unlike a human, the agent has **zero session-to-session memory** of having invented `#bugfix` last week, so it has no internal signal telling it to go check.

2. **`merge_tags_heuristics()` only catches lexical/normalization variants, not synonym pairs — this is a category-mismatch, not a tuning problem.** Case-insensitive/normalized-string matching can never catch `#fix` vs `#bugfix`, `#dedup` vs `#deduplication`, or `#skill` vs `#agent-skills` — these are **semantically** related but **lexically** unrelated (or only partially related) strings. This is exactly the gap embedding-based clustering (Section 4) is suited to close and heuristic normalization structurally cannot, no matter how it's tuned. The audit findings aren't a sign the heuristic is buggy; they're the expected result of applying a lexical-only tool to a semantic problem.

3. **No proposal/review queue means detected candidates have nowhere to go.** Even if an agent (or a human) *notices* `#fix`/`#bugfix` look related, there's no equivalent of Stack Overflow's synonym-proposal object — a durable, listable "candidate merge, unresolved" record. Today, noticing a fragmentation candidate and *acting* on it (calling `merge_tags`) are the same atomic step, with nothing in between to accumulate evidence, allow later confirmation, or let a "cognitive sweep" pass (per CLAUDE.md Phase D) systematically clear a backlog. Compare to Stack Overflow's requirement that a synonym only be *proposed* once it demonstrably exists on real content, and is then reviewed before commit — SALTMDB has the "auto-merge on certainty" path (heuristics) and the "manual merge on demand" path, but nothing structured in between for the ambiguous middle ground where most of the audit's actual fragmentation examples (`#fix`/`#bugfix`, `#skill`/`#skills`/`#agent-skills`) sit.

4. **No validation gate on tag shape at write time.** `502` and `fake` slipping through as bare tags shows there is currently **no schema-level or write-time-service-level constraint** rejecting non-`#`-prefixed, non-semantic, or suspiciously generic tag strings. This is the cheapest gap to close and the research (Notion's closed-list-by-construction model, GitHub's prefix-convention-as-best-practice) both point to validation as table stakes, not an advanced feature.

5. **Flat single-level alias model can't express what several of the audit's own examples actually need.** `#skill` vs `#skills` vs `#agent-skills` is not cleanly "three spellings of one concept" — `#agent-skills` may legitimately be a *narrower* concept (skills specifically for agent orchestration) that deserves a broader/narrower relation to `#skill` rather than being merged flat into it, losing information. The current schema has no way to express "B is narrower than A" as distinct from "B is an alias of A" — `canonical_id` conflates both cases into one merge operation. This is the WordNet-synset / faceted-classification gap from Section 6.

6. **No cross-agent shared "session memory" substitute.** The research on multi-agent LLM convergence (Section 5) shows convergence requires either shared interactive context (which SALTMDB's async agents don't have) or an external forced-lookup ground truth. SALTMDB has the ground truth (`get_canonical_tags`) but, per gap #1, doesn't force agents through it — so the one convergence mechanism that *could* work for stateless independent agents is present but not load-bearing.

7. **Root cause is organizational, not just technical, and the research says so directly.** AO3's ~400-strong human tag-wrangling operation is evidence that even very mature, well-resourced folksonomy governance still needs an active, ongoing curation *process*, not a one-time tooling fix. SALTMDB substituting "tooling exists" for "a process runs regularly and closes the loop" is itself a likely contributor — `merge_tags` and `get_canonical_tags` existing doesn't mean either is exercised with the frequency or rigor an equivalent human process would apply. This argues for treating tag hygiene as a recurring *operational* task (e.g., a scheduled consolidation sweep, per CLAUDE.md Phase D) rather than solely a one-off schema/code fix.

## Proposed Improvement Plan

### Quick Wins (schema/tooling changes, low risk, no architecture change)

1. **Write-time validation in `memory_service.py` (or wherever `store_memory`/tag-write path lives):**
   - Reject/normalize tags that don't match `^#[a-z0-9][a-z0-9-]*$` (or the project's actual convention) — closes the `502`/`fake` anomaly gap directly. Auto-prefix a bare word with `#` rather than hard-failing, to avoid breaking agent calls, but log a `log_event(type='issue')` when this correction fires so the offending caller pattern is visible.
   - Reject overly generic single-token tags below a length/specificity threshold unless they already exist in the canonical set (stops accidental new near-duplicates of existing generic tags).

2. **Make `get_canonical_tags` a mandatory pre-check baked into the `store_memory`/`store_new_tag` code path itself, not an agent-optional tool call.** Concretely: when `store_memory` receives new tag strings not already present as an exact `tags.name` match, have the service **internally** call the same lookup `get_canonical_tags` performs (fuzzy/normalized match against existing tags) before creating a new tag row. If a high-confidence near-match exists, either auto-redirect to it (low ambiguity) or store the entity write while flagging the *tag* as `pending_review` (see Medium-Term synonym-candidate queue) rather than silently creating a new sibling tag. This moves enforcement from "hope the agent calls the tool" (per Gap #1) to "the service can't create a fragmenting tag even if the agent never calls the lookup itself" — directly addressing the multi-agent-no-shared-memory root cause identified in Section 5.

3. **Tighten `get_canonical_tags`' matching to catch simple morphological variants (plurals, `-s` suffix) deterministically**, independent of the embedding work below — e.g. Porter-stemming or simple suffix-stripping comparison in addition to today's normalized-name exact/substring match. This alone would likely have caught `#subagent`/`#subagents` and `#skill`/`#skills` without needing embeddings at all; cheap and immediately deployable in `librarian_service.py`.

4. **`get_canonical_tags(domain=...)` param already exists — enforce that agents pass a domain/component hint** (this project already tags by rough domain, e.g. `agent_docs`) so lookups are scoped and higher-precision, reducing false negatives from an overly broad global search.

### Medium-Term (embedding-based near-duplicate surfacing — leverages existing fastembed/bge-small infra)

5. **Add tag-name embeddings as a first-class signal, but as a *review queue*, never an auto-merge trigger** (per Section 4's caveat about bge-small being tuned for sentence-length text, not tag-length strings, and Section 2's "evidence + gate" pattern from Stack Overflow):
   - Compute and store an embedding per `tags.name` (or per `tags.normalized_name`) using the same fastembed/bge-small-en-v1.5 pipeline already in use — cheap, since infra already exists.
   - Add a new table, e.g. `tag_merge_candidates` (`tag_a_id`, `tag_b_id`, `similarity_score`, `signal_source` [`'embedding'`|`'cooccurrence'`|`'stem'`], `status` [`'pending'`|`'confirmed'`|`'rejected'`], `detected_at`) — this is the missing "synonym proposal object" from Gap #3, modeled directly on Stack Overflow's propose-then-gate workflow.
   - A periodic background job (extending `merge_tags_heuristics()` or a sibling function in `librarian_service.py`, e.g. `surface_tag_merge_candidates()`) computes pairwise cosine similarity across all tag-name embeddings, inserts candidates above a conservative threshold (start around 0.80–0.85 per the general dedup literature, but treat as a starting point to tune against this project's own tag corpus, not a fixed constant — per Section 4's caveat that thresholds are corpus-specific) into `tag_merge_candidates` with `status='pending'`, and skips anything already linked via an existing `canonical_id`.
   - Expose these via `get_events(type_filter='consolidation_request')` or a dedicated `mode` on an existing tool so an agent's Phase D cognitive-sweep (already mandated by CLAUDE.md) naturally surfaces and resolves them — reusing the consolidation-request pattern SALTMDB already has for memories, applied to tags. This turns "weeding" from something that only happens if an agent happens to notice, into a queue that gets systematically drained, addressing Gap #3 and Gap #7 (the "needs to be a recurring process" lesson from AO3) together.

6. **Add entity-cluster co-occurrence as a second, complementary signal** (per Section 4's second bullet): periodically cluster entities by their existing content embeddings, and for each cluster compute which tag pairs co-occur disproportionately within it vs. globally. Insert high-co-occurrence, lexically-dissimilar pairs into the same `tag_merge_candidates` queue with `signal_source='cooccurrence'`. This is specifically aimed at catching pairs like `#fix`/`#bugfix` that tag-name-embedding similarity alone may under-rate (bare short strings, general-purpose embedding model) but that the *entities* tagged with each make obviously synonymous.

7. **Surface `tag_merge_candidates` review as part of `commit_consolidation`'s existing flow**, so tag consolidation and memory consolidation are handled through one familiar agent-facing ritual rather than a second parallel system to learn.

### Larger Bets (structural/data-model changes)

8. **Introduce a lightweight faceted/hierarchical tag model, informed by Facetag's bottom-up/top-down hybrid (Section 6) and Obsidian's cheap `/`-nesting precedent:**
   - Cheapest version (no schema change): adopt and *enforce* (via the write-time validator from Quick Win #1) a `facet:value` naming convention for a small fixed set of facets — e.g. `type:fix`, `type:feature`, `component:memory`, `component:tools` — coexisting with free-form descriptive tags. This directly prevents the `#fix`/`#bugfix` class of collision by giving "type of change" its own namespace instead of competing in the flat tag space with domain-descriptive tags.
   - Fuller version (schema change): extend `tags` with a `parent_tag_id` (broader/narrower, distinct from `canonical_id`'s alias semantics) so `#agent-skills` can be modeled as *narrower-than* `#skill` rather than forced into a lossy flat merge (Gap #5) — this is the WordNet-synset-style typed-relation model. `manage_relation`'s existing `predicate`-based edge system could plausibly carry this (`predicate="broader_than"`/`"narrower_than"`) without even needing a new column, if the team prefers reusing the existing relations graph over extending `tags` directly — worth an explicit design decision (see Open Questions).

9. **Consider a true synonym-ring/synset table** (`tag_concepts` with many-to-many `tag_concept_members`) if the `canonical_id` self-FK ever needs to support *multiple* equally-valid canonical spellings rather than always collapsing to one "winner" string — lower priority than #8, since the current one-canonical-wins model matches Stack Overflow's proven approach and is simpler to reason about; only worth it if agents start needing per-context display-name variance (unlikely for an internal memory DB with no end-user-facing tag display requirement).

10. **Structured/constrained tag choice at the LLM call boundary** (per Section 5's enum-consistency and LLM4Tag findings): where feasible, have `mcp/tools.py`'s tag-accepting parameters (on `store_memory` particularly) return, alongside any rejection/redirect, the actual closed candidate set that *should* have been considered (recall-then-select pattern) — effectively making the tool response itself teach the calling agent the vocabulary in-context, without requiring a separate `get_canonical_tags` round-trip. This is a low-effort way to import LLM4Tag's "narrow to ~20 candidates, then select" pattern into a tool-response contract rather than a separate model stage.

## Risks & Trade-offs

- **False-positive auto-merges are asymmetric-cost mistakes.** Per Stack Overflow's own experience, a wrongly-merged synonym silently loses distinctions that may matter later, and is hard to cleanly reverse once entities have been repointed. This is the strongest argument for keeping all embedding/co-occurrence-based signals in a `pending`-status review queue (Medium-Term #5) rather than ever wiring them to auto-merge, even though it means fragmentation isn't fixed the instant it's detected.
- **Embedding thresholds tuned on general text may not transfer to short tag strings** (Section 4) — expect to need an empirical calibration pass against SALTMDB's actual existing tag corpus (including the known audit examples as a labeled validation set) before trusting any specific cosine cutoff.
- **Write-time validation risks rejecting or mis-normalizing legitimate agent-generated tags**, especially early on — recommend a "soft" rollout (log + auto-correct, don't hard-reject) for at least one operational cycle before tightening to hard rejection, to avoid breaking working agent flows over a schema nuance.
- **A facet/hierarchy layer adds a second axis for agents to get wrong** — if facets themselves proliferate uncontrolled (e.g. an agent inventing a new `urgency:` facet nobody agreed on), this recreates the fragmentation problem one level up. Mitigate by keeping the facet *names* themselves in a small, hard-coded enum (not agent-extensible), even if facet *values* remain more open.
- **A synonym-candidate review queue only helps if something actually drains it.** Per Gap #7, tooling without an operational habit reproduces the current failure mode one layer down — this plan should be paired with an explicit recurring process commitment (e.g. wiring the queue into the existing Phase D cognitive-sweep cadence), not just a new table nobody queries.
- **No single-tagger continuity to lean on.** Every mitigation here is substituting for the "one human remembers their own past tagging choices" property that most of the surveyed prior art (Obsidian, a single del.icio.us user) actually relies on informally. That means SALTMDB's fixes have to be *more* structurally enforced than the precedents, not just "as good as" them, to compensate for having zero natural continuity across writers.

## Open Questions for zbalint

1. Should facet/hierarchy relations reuse the existing `manage_relation` graph-edge mechanism (`predicate="narrower_than"`), or warrant a dedicated `parent_tag_id` column on `tags`? The former reuses existing infra faster; the latter is more queryable/indexable for tag-specific operations (e.g. "give me all tags narrower than `#skill`" without a graph traversal).
2. What's the acceptable false-positive tolerance for the embedding-based candidate queue — should a `pending` candidate require *any* agent confirmation before merge, or is auto-merge above a very high threshold (e.g. >0.95, closer to true near-duplicate) acceptable to reduce queue backlog, reserving human/agent review only for the 0.80–0.95 band?
3. Is a small fixed facet enum (e.g. `type:`, `component:`, `scope:`) something you want to define now, or should it emerge organically from an analysis of the current fragmented-tag corpus first (i.e., let the audit findings suggest the facets, rather than guessing them upfront)?
4. Should the write-time validator's "soft rollout" (log-and-correct before hard-reject) run for a fixed time window, or until a specific false-positive/true-positive ratio is observed?
5. Given multiple independent agent *products* write to this same tag space (Claude Code, Antigravity, Copilot), is there appetite for a shared, cross-product "tag contract" document (a canonical facet/tag-naming spec each agent's system prompt references), separate from runtime enforcement — i.e., prompt-level convergence support in addition to tool-level enforcement?
