## 1. Why

Reading one memory takes two tools today with overlapping contracts (`get_memory` with the content, `inspect_memory` with a snippet instead), `get_memory` carries a half-removed alias pair (`entity_id` and `memory_id`, both optional in the schema), and there is no way to read several known memories in one call although agents routinely cite several hit ids. The parent design (D8) merges the two reads into `get_memory(memory_id, detail)`, adds `get_memories`, and removes `inspect_memory` and the alias.

## 2. Decisions

- D1 `get_memory(memory_id: str, detail: Literal["full","summary"] = "full", include_trace_provenance: bool = False) -> dict` (3 parameters; `memory_id` required and FIRST, because `tests/test_trace_mcp_tools.py:155` calls `tools.get_memory("entity-1", ...)` positionally). `detail="full"` is today's `get_memory` result; `detail="summary"` is today's `inspect_memory` result (no `content`, a `snippet`, lineage kept). `memory_service.inspect_memory` gains `include_trace_provenance: bool = False` and forwards it to `_assemble_memory_record`, which already supports it (`lifecycle.py:1156`, `:1196-1199`; today only `get_memory` forwards the flag), so that both flags work at both detail levels. An unknown `detail` value is a `VALIDATION_ERROR` on `detail` in both dispatchers (the Literal is enforced only by the MCP schema). The default is `full` so that a forgotten argument never returns a snippet that gets cited as fact. The `entity_id` field and the alias logic are removed; `entity_id` is a removed field and the guard rejects it with a corrected call that carries `memory_id` (D6).
- D2 `get_memories(memory_ids: Annotated[list[Annotated[str, Field(min_length=1, max_length=128)]], Field(min_length=1, max_length=20)], detail: Literal["full","summary"] = "full", include_trace_provenance: bool = False) -> dict`. Result `ok({"items": [...]})` in request order, one item per requested id: `{"requested_id": <as sent>, "outcome": "ok" | "not_found" | "ambiguous", "memory": <D3 record> | None, "candidates": [...] (only when ambiguous, with `candidates_truncated` when the service says so)}`. The per-item key is `outcome`, not `status`, because the memory inside has its own lifecycle `status` (`raw` or `archived`) and the two would be confused; the parent text says `status`, a deviation recorded in amendment 6. An id that is empty after stripping is rejected before any read with `VALIDATION_ERROR` on `memory_ids[<i>]`. Identical ids (exact string match after stripping) reject the whole request with `VALIDATION_ERROR` on `memory_ids`, zero side effects; two different spellings that resolve to the same memory (a prefix and the full UUID, an exact title) are not detected and each gets its own item in request order (resolving all ids first is out of scope). Size bound (a trust-boundary and client-limit rule): `get_memories(detail="full")` inlines content while the cumulative inlined characters stay within `GET_MEMORIES_INLINE_BUDGET_CHARS = 40000` (new constant in `config.py`); a later item that would exceed the remaining budget is returned as `content_file_path` plus `content_preview` (the existing dump form). Mechanism: `large_content_descriptor(content, threshold=None)` gains the optional threshold (default unchanged = `CONTENT_FILE_DUMP_THRESHOLD_CHARS`), `get_memory` and `_assemble_memory_record` / `_assemble_memory_content` pass an optional `inline_threshold_chars` through, and `_dispatch_get_memories` passes `min(CONTENT_FILE_DUMP_THRESHOLD_CHARS, remaining_budget)` per item and subtracts the inlined length. Each dumped file stays on the server host with the existing no-retention shortcut of `large_content_descriptor`. The parent text lists a fourth status `forbidden`; it is not produced: a private memory of another agent must read as unknown (the existing visibility rule of `get_memory`, `_can_read_entity`), and `forbidden` would reveal it. Recorded in parent amendment 6. A mixed result is an `ok` envelope (per-item statuses carry the outcome); a request-level problem (empty list, over 20, duplicate, wrong type) is a rejection.
- D3 Record shape: the service dictionary with the key `id` renamed to `memory_id` (adapter-level, R9, via `_remap_public_data` for `get_memory`, and per item for `get_memories`). Everything else keeps its name. The nested `lineage` structure and `parent_ids` are NOT renamed here: lineage is built by the same helper that serves `get_lineage` and is renamed with it in S4c, so both tools stay consistent (dependency noted in amendment 6).
- D4 Errors: an empty-after-strip id is pre-validated (D2) because the service answers it with `MISSING_ENTITY_ID`. `get_memory` keeps the service codes (`UNKNOWN_ENTITY_ID`, `AMBIGUOUS_ID_PREFIX` with candidates, `MISSING_ENTITY_ID`, `MEMORY_READ_FAILED`); the field `entity_id` is remapped to `memory_id` (`get_memory` joins `_ERROR_FIELD_REMAP_TOOLS`). `get_memories` maps the same codes per item: `UNKNOWN_ENTITY_ID` to `not_found`, `AMBIGUOUS_ID_PREFIX` to `ambiguous`, any other per-item failure (`MEMORY_READ_FAILED`) rejects the whole request with `INTERNAL_ERROR` (a read failure is not a per-item outcome; a test pins it for item k of 3).
- D5 Daemon: `_dispatch_get_memory` gains the `detail` argument (a `summary` request calls `memory_service.inspect_memory`); a new `_dispatch_get_memories` opens one connection with `get_connection(get_db_path())`, closes it in a `finally`, passes it as `db_connection` to each service call (the service closes only connections it opened, `lifecycle.py:1225-1229`, `:1278-1280`), applies the budget of D2, and returns the raw per-id envelopes in a list for the adapter to map; `get_memories` is registered in `DISPATCH_TABLE` and in `protocol.py` `READ_TOOLS` (never a mutating tool: read tools keep their retry-safe read semantics). The explicit-read bump of `last_accessed_at` happens only on a writable connection, i.e. in direct mode (tests, `DirectDispatchBackend`): under the daemon a read tool runs on a read-only connection and `_touch_assembled_memory` silently keeps the stored value (`lifecycle.py:1084-1102`, `connection.py:100-105`, `dispatch.py:791-822`); `get_memories` keeps that behaviour unchanged. The `inspect_memory` tool leaves the MCP surface: its adapter function, its entry in `_AGENT_ID_INJECTED_TOOLS` (`tools.py:196-197`; `get_memories` is added to the same set), its `DISPATCH_TABLE` entry, its `protocol.py` `READ_TOOLS` entry and `_dispatch_inspect_memory` are removed (no caller outside the tool, grep in section 8); the service function `memory_service.inspect_memory` stays.
- D6 `mcp/guard.py` `RENAMED_FIELDS` (added by S4a) gains `"get_memory": {"entity_id": "memory_id"}` and `"get_memories": {}` is not needed (new tool). ## Amendment 1 (2026-10-23)

Found by the developer during planning and verified by the architect: D2's mechanism threaded `inline_threshold_chars` through `get_memory`, `_assemble_memory_record` and `_assemble_memory_content`. `_assemble_memory_record` is a shared helper that already has 9 parameters and callers outside this slice's scope (`relation_service.py` around lines 1127 and 1180, and `tests/test_memory_service_characterization.py` around line 732), so adding a tenth parameter conflicts with D9 and with the scope of section 3.

Resolution (replaces the "Mechanism" sentence of D2): the budget is applied in `_dispatch_get_memories` AFTER each service call, not inside the service. The dispatcher keeps `remaining = GET_MEMORIES_INLINE_BUDGET_CHARS`; for each `ok` record in `detail="full"` that still carries inline `content` it calls `large_content_descriptor(content, threshold=remaining)`; if the result is the dump form (`content_file_path` plus `content_preview`), the record's `content` key is replaced by those two keys, otherwise `remaining` is reduced by `len(content)`. A record that the service already returned in dump form (over 20,000 characters) costs nothing. Only `large_content_descriptor(content, threshold=None)` (`utils/text.py`, default behaviour unchanged) and the constant `GET_MEMORIES_INLINE_BUDGET_CHARS` (`config.py`) change; `get_memory`, `_assemble_memory_record`, `_assemble_memory_content` and `relation_service.py` are NOT touched, and section 3 loses the `inline_threshold_chars` plumbing (the `lifecycle.py` line keeps only the `inspect_memory` `include_trace_provenance` parameter). The D9 cap of 6 parameters applies to new and changed private helpers; a pre-existing helper is not changed here. Test impact: the budget test of section 4 is unchanged (three memories of 18,000 characters inline the first two and dump the third).
