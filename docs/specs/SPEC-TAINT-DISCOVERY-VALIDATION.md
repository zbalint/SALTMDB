## 1. Why

The consultant's survey (m_2654) found that no less-trusted party can write the discovery file in the default single-user setup (the writer creates it `0600` with `O_EXCL`), so the five findings are not exploitable today. They do point at real gaps: `discovery.read` accepts any JSON dict with two keys, without checking that `service_port` is an integer in range, that `auth_token` has a sane shape, that the other fields have the right types, or that the file belongs to the current user and is not group- or world-writable; the directory `~/.saltmdb` is created with the default umask; and a second reader of the same file, the trace-capture hook (`_daemon`, which cannot import `saltmdb`), does `int(info["service_port"])` with no check at all. Rule 24 of the coding standards asks for each check in one place every entry point passes through: `discovery.read` is that place for the package, and the hook gets the same checks written out because it cannot import it. A value that is not an int can reach `socket.create_connection` and, through `%s` in the two log calls, a log line (a port such as `"1\nFORGED"` forges a log line). Rejected: validating at each of the five sinks (five places to forget), a suppression or status change (owner rules). Whether Sonar's taint engine accepts an int-typed, range-checked value as clean is not proven; if an issue stays open after the push, the architect reports it to the owner.

## 2. Decisions

- D1. In `discovery.py` add `_valid(data: Any) -> bool` and call it from `read` after `json.load` (replacing the current key-presence test; a failure returns `None`, as an unreadable file does today). A valid record is a dict with: `service_port` an `int` that is not a `bool`, `1 <= service_port <= 65535`; `auth_token` a `str` of 1 to 256 characters, every character printable ASCII and not a space (`"\x21" <= ch <= "\x7e"`; the real token is `secrets.token_urlsafe(32)`, 43 characters from `A-Za-z0-9_-`; the rule is deliberately looser so existing tests that use `"tok"` keep working); when present, `daemon_pid` an `int` that is not a `bool` and greater than 0, and `db_path` a `str`. Other keys are ignored. `read` returns the original dict.
- D2. Ownership check (skipped on `sys.platform == "win32"`): `read` opens the file once, takes `os.fstat(f.fileno())`, and treats the file as unreadable (returns `None` and logs one `logger.warning` per path per process (keep a module-level set of paths already warned about; the client's retry loop polls `read` repeatedly and must not flood the log) with a fixed message that names the path only, never content, and says "not owned by the current user or writable by group/others" so a user on a drive that reports every file as 0777 (for example a WSL DrvFS mount without metadata) can diagnose it) when `st.st_uid != os.getuid()` or `st.st_mode & 0o022` is non-zero. The test and the read use the same open file, so there is no check-then-open gap.
- D3. `discovery._discovery_dir` and the `os.makedirs` of `~/.saltmdb` in `config.get_db_path` (line 53, the de-facto first creator on almost every code path: `resolve_canonical_db_path` calls `get_db_path` first) both create the directory with `mode=0o700`. The mode applies to a newly created leaf only (parents keep the default, and the mode is filtered by the umask, so a stricter umask can only tighten it). An existing directory is not changed (the live one is 0755; a chmod of an existing directory is the owner's decision, not this spec's), and the hooks' own `mkdir(parents=True)` of `~/.saltmdb/hooks/...` is left alone.
- D4. `client.py`: the two log calls (`ensure_daemon_running` and `SessionConnection.open`) print the pid and port with `%d` and integers instead of `%s` with `info.get(...)`. AMENDMENT 1 (tester finding m_2694, verified by `complexipy`): writing `int(info.get("daemon_pid") or 0)` inline adds one boolean-operator sequence to each of the two functions and raises their cognitive complexity from 15 (exactly Sonar's S3776 limit; `sonar-project.properties` has no override) to 16, which would be a NEW S3776 issue and, with the gate enforced, a red CI. So do NOT put any new branch, `or`, `and` or conditional expression into those two functions. Add ONE small module-level helper in `client.py`, `_logged_ids(info: dict[str, Any]) -> tuple[int, int]`, that returns `(int(info.get("daemon_pid") or 0), int(info["service_port"]))` (the pid default exists because many mocked infos in existing tests carry no pid and a real record always has it; the port is always a valid int after D1), and let each call site read `pid, port = _logged_ids(info)` and log the two ints with `%d`. Complexity of each client function stays at its HEAD value (the developer proves it with `complexipy` on the HEAD copy and the worktree copy, same tool, same flags) and the helper scores 1 or 2. No other change in `client.py`.
- D5. `hooks/saltmdb-stop-trace-capture.py` `_daemon`: apply the same checks on port and token (same rules as D1, with a comment cross-referencing `daemon/discovery.py`), and on POSIX the same owner and mode check, done on the OPEN file: `with open(path, "rb") as handle: st = os.fstat(handle.fileno()); info = json.load(handle)` inside a `try` that treats `OSError` and `ValueError` as "no daemon" (`_read_json` stays as it is for `_adapter`). That removes any stat-then-read gap, so no `# shortcut:` comment is needed. `daemon_pid` and `db_path` are not required here.
- D5a. The existing hook test `hooks/tests/test_trace_capture_copilot.py` writes a discovery file with `write_text` (lines 203-205), so its mode is `0o666 & ~umask`: `0o644` at umask 022, but `0o664` at the common user-private-group umask 002, which D5 would reject and make that test fail depending on the machine. Add exactly one line after that `write_text`: `os.chmod(<that path>, 0o600)`. No assertion changes. This is the only edit to an existing test and the architect checks it with `git diff -U0` on that file (one added line, nothing removed).
- D6. The new tests assert, with literal expected values: for `discovery.read` on a real temporary file: a valid record returns the dict; `service_port` as the string `"4000"`, as `True`, `0`, `65536`, `-1`, a float, and as the string `"1\nFORGED"` each return `None`; `auth_token` missing, an int, empty, 257 characters, containing a space, a newline or a non-ASCII character each return `None`; `daemon_pid` a string, `0`, negative and `True` each return `None`; `db_path` an int returns `None`; a JSON list returns `None`; a file with mode `0o666` returns `None`; a file whose owner differs (monkeypatch `os.getuid`) returns `None`; for `reachable_daemon_info` with an invalid file, `socket.create_connection` is never called; for the two log calls, mock `reachable_daemon_info` (bypassing D1) to return `service_port` 4000.0 and `daemon_pid` 7.0 and assert with `caplog` that the line reads `4000` and `7` and not `4000.0` (with D1 in place every real value is an int, so `%s` and `%d` render identically; only values whose renderings differ can tell the two formats apart; do not use a newline string, `int("1\nFORGED")` raises `ValueError`, which the spec does not define); for `discovery._discovery_dir` and for `config.get_db_path` under a temporary `HOME`, a newly created `~/.saltmdb` has mode `0o700` (`stat.S_IMODE`; the test sets `os.umask(0o022)` itself and restores it in a `finally`) and an existing directory keeps its mode; patch `discovery.os.getuid` (the name the module looks up) for the foreign-owner case; the mode case chmods the file after writing it so it is umask-independent; for the hook, the same port and token cases return `None`, a valid pair returns `(port, token)`, and a group-writable file returns `None`.
- D7. No new Sonar finding and no suppression. `ruff check --select ARG,F,RET` on the three source files shows nothing new. Windows: the ownership check is skipped, the rest applies. Specifically: no function the diff touches may exceed its HEAD `complexipy` score or 12 for a new function (proved on a HEAD copy and the worktree with the same tool), and no string literal may appear three or more times in a file the diff touches where it appeared fewer times at HEAD (Sonar S1192, now failing CI): in `discovery.py` the keys `\"daemon_pid\"`, `\"db_path\"`, `\"service_port\"`, `\"auth_token\"` already occur in `write`; reuse them through module-level constants or a single table-driven check (for example one dict of optional-key types) instead of repeating them in `_valid`.
