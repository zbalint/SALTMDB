## 1. Why

`revise_memory` and `supersede_memory` are the two remaining lifecycle tools on the pre-v2 shape: `entity_id` instead of `memory_id`, a `content`/`content_file_path` pair, responses with `old_id`/`new_id`, no way to set the retrieval text of the new memory, and `reason` optional in the signature although the service requires it. Reading the code for this slice found two defects that the parent spec did not know about:

1. Core memories. Probed 2026-10-22 on a temporary database (`store_memory(is_core=True)`, then `revise_memory`): the successor of an active core memory silently becomes core too. `_replacement_insert_entity` copies the whole predecessor row (`dict(locked_before)`), so `is_core`, `core_reason`, `core_exit_condition`, `core_review_after`, `core_detail_memory_ids`, `core_last_reviewed_at`, `core_last_reviewed_by`, `core_review_rationale` and also `retrieval_text`, `retrieval_text_hash` and `parent_ids` are carried over. The derived `#core` tag is not carried (the new row has `is_core=1` and no `#core` tag), the capacity (5), content length (2500), overdue-review and detail-memory rules are never evaluated, and the archived predecessor keeps `is_core=1`. The parent spec says a core predecessor is replaced by a non-core successor; the code does the opposite, half-way. No existing test revises or supersedes a core memory.
2. Atomicity. The replacement write has no savepoint. Under the daemon coordinator a service call is one job inside the coordinator's transaction and `write_transaction_retrying` is a bare `fn(conn)`; `_replacement_operation` catches every exception after the write has started and returns `LIFECYCLE_WRITE_FAILED`, so the coordinator then commits the new row and the archived predecessor of a half-finished replacement (same class as BL-063 and BL-067). It is reachable in normal use as soon as a core detail declaration can fail after the row exists (`reconcile_detail_relations` raises `RuntimeError` when an edge is rejected).

This slice gives both tools the v2 shape and makes the core outcome an explicit, validated, atomic decision, exactly as S3a did for consolidation.

## 2. Decisions

- D1 Tools (`mcp/tools.py`). `revise_memory(memory_id: str, title: str, reason: str, content: str | None = None, content_file_path: str | None = None, tags: list[str] | None = None, scope: Literal["private","shared"] | None = None, memory_type: Literal["fact","event","procedure","decision","preference"] | None = None, retrieval_text: str | None = None, repoint_relations: bool = False, context_id: str | None = None, core: CoreInput | None = None, demote_core: bool = False) -> dict` and `supersede_memory` with the same signature (13 parameters each, so no S107; `CoreInput` is the model `store_memory` and `consolidate_memories` already use). First sentences of the descriptions: revise = "Use this when a stored memory was wrong or badly worded when it was written; use supersede_memory when it was true then and the facts changed since."; supersede = the mirror. `reason` is required. Omitted `tags`, `scope`, `memory_type`, `context_id` inherit the predecessor's value (unchanged behaviour); `retrieval_text` is NOT inherited, omitted means the successor has none (a change: today the predecessor's text is copied; the description says so). The descriptions state the core rule and that `content_file_path` must be readable by the SALTMDB server host. `entity_id` is a removed field and the guard rejects it (R8).
- D2 Adapter. Per call, all errors collected before any backend call: `_resolve_content` (existing codes, unprefixed fields); `core` together with `demote_core` is rejected with `CORE_AND_DEMOTE_CONFLICT` on field `demote_core`. `memory_id` maps to the internal `entity_id`; `core` maps to `is_core=True`, `core_reason`, `core_exit_condition`, `core_review_after`, `detail_memory_ids`; `demote_core` maps to `is_core=False`; `None` values are dropped from the dispatch payload so an omitted decision stays distinguishable from every explicit one. `_replacement_payload` is replaced by a mapping helper with this logic (no hidden aliases).
- D3 Service entry (`memory_service/lifecycle.py`, exported from `memory_service/__init__.py`). The private `_ReplacementRequest` becomes the public frozen `ReplacementRequest` and gains `retrieval_text: str | None = None` and `core: CoreDeclaration | None = None` (`CoreDeclaration.is_core` is the tri-state: `None` no decision, `True` declare, `False` demote). It already carries `db_connection`, `db_path` and `in_transaction`. A public `replace_memory(operation: Literal["revises","supersedes"], request: ReplacementRequest) -> dict` is `_replacement_operation` made public (no extra parameters). The service functions `revise_memory` and `supersede_memory` keep their signatures and call it; they cannot carry a core decision, so with D4 an active core predecessor is rejected with `CORE_DECISION_REQUIRED` for those callers (fail closed, a declared change; they are test-only after this slice and BL-062 removes them). The dispatcher calls `replace_memory`.
- D4 Core outcome. A NEW shared function in `core_governance_service.py`, `resolve_derived_core_state(conn, *, source_ids: list[str], declaration: CoreDeclaration, content: str, scope: str, new_entry: dict) -> dict`, takes over the body of `relation_service._consolidation_core_state` (do not copy it): it calls `resolve_consolidation_core_state(conn, resolved_parents=source_ids, ...)`, runs `enforce_overdue_boundary` for a core result (the sources, including the one about to be archived, are checked), runs `check_capacity_admission` with `source_ids` excluded and `new_entry` (the neutral dict `check_capacity_admission` already takes), and converts `ValueError` to `CoreGovernanceRejected` as today. `_consolidation_core_state` becomes a thin caller (behaviour identical, pinned by the S3a and consolidation tests). The replacement calls it with `source_ids=[predecessor_id]`. Results: no decision plus an active core predecessor raises `CoreDecisionRequired` (keep fragment `{"core": {"reason", "exit_condition"}}`, plus `"scope": "shared"` when the effective scope is not shared); `is_core=False` yields an ordinary successor with every core column cleared; `is_core=True` validates reason, exit condition, review date, content length, scope shared and the detail-memory rule against the NEW content. A non-core predecessor with no decision stays ordinary; `core` on a non-core predecessor promotes the successor; `demote_core` on a non-core predecessor is an accepted no-op (same as S3a).
- D5 Row writes (`_replacement_insert_entity`). The successor row is built from the predecessor snapshot as today, with an explicit constant `_REPLACEMENT_RESET_COLUMNS` (next to the existing frozen-column list) naming the columns that are never carried: `is_core`, `core_reason`, `core_exit_condition`, `core_review_after`, `core_detail_memory_ids`, `core_last_reviewed_at`, `core_last_reviewed_by`, `core_review_rationale`, `retrieval_text`, `retrieval_text_hash`, `parent_ids`; the first five are then set from the resolved core state, the rest are NULL, `retrieval_text` and its hash from the request. `weight` and `project_id` stay carried. A test walks `PRAGMA table_info(entities)` so a future column is knowingly carried or reset. The inherited tag list never contains `#core` (it is derived); a core successor gets `#core` through `resolve_or_create_tag` (the pattern of `relation_service.py:2044`). Details of a core successor are exactly its declared `detail_memory_ids`: `reconcile_detail_relations(previous_detail_ids=[])` after the row exists, and `_replacement_repoint_edges` skips `elaborates_on` edges whose target is a core predecessor (read fresh in the transaction), adding their ids to `still_orphaned_ids` so the response lists them. The predecessor's own `is_core` column is left as it is (archived rows never count).
- D6 Retrieval text. `retrieval_text` goes through `validation.normalize_retrieval_text` (NFKC, strip, secret redaction, length cap, non-string rejected) before the transaction; a `ValueError` becomes the replacement error `INVALID_RETRIEVAL_TEXT` (field `retrieval_text`, the `_replacement_error` convention of the other replacement validation codes; `store_memory` reports the same text as a plain `VALIDATION_ERROR` string); the hash is `_retrieval_text_hash` of the normalized text; the retrieval embedding job is enqueued from those values (today from the copied predecessor values).
- D7 Atomicity of the replacement write (`_replacement_write` and `_replacement_operation`). Order inside the transaction: `_replacement_locked_source`, the core resolution of D4 (every check that can raise happens here, before any row is written), then `with savepoint(c, "replacement")` around the entity insert, tags, `#core` tag, detail reconciliation, predecessor archive, embedding job calls that write rows, lineage edge and repoint; the vector clears (`clear_embedding_vectors_for_entity`, `cancel_retrieval_embedding_jobs_for_entity(clear_vector=True)` parts that touch vec tables) run after the savepoint is released, as in `_consolidation_clear_parent_vectors`. The outer `except Exception` in `_replacement_operation` re-raises when `is_coordinator_connection(conn)` (the `apply_relations` pattern) and keeps `LIFECYCLE_WRITE_FAILED` in direct mode. The known rejections map as in D8 and never leave a partial write. BL-067's audit text gains this path.
- D8 Rejections. Caught in `_replacement_operation` next to `_LifecycleRejected`, `CoreDecisionRequired` FIRST: rejected envelope with code `CORE_DECISION_REQUIRED`, field `entity_id`, message as the exception's, `corrected_calls` fragments left for the adapter to complete; then `CoreGovernanceRejected`: a capacity payload dict is returned as is (`CORE_CAPACITY_EXCEEDED`, as `store_memory` does), a string becomes `VALIDATION_ERROR` on field `core` (or `scope` / `demote_core` when the message is about those).
- D9 Response and public mapping. The service response keys stay (`old_id`, `new_id`, ...): renames are adapter-level (parent R9). `_to_public_write_result` gets a per-tool key map (replacing `_ID_RENAME_TO_MEMORY_ID_TOOLS`) so the public `data` carries `predecessor_memory_id` and `successor_memory_id` in place of `old_id` and `new_id`; the other keys are unchanged. `_remap_public_errors` is applied to these two tools (field `entity_id` becomes `memory_id`). `changed` echoes the resolved core decision under its public name: `changed.core = {reason, exit_condition, review_after, detail_memory_ids}` for a core result, `changed.demote_core = true` when demoted; core never appears in `inherited`. The trace key (`_WRITTEN_ID_KEY` in `tools.py`, `WRITTEN_ID_KEY` in the stop hook) is `successor_memory_id` for both tools, read from the public result.
- D10 Core-decision completion (adapter). The S3a helper is split: `_core_decision_error(result) -> tuple[int, dict] | None` (position and entry of the first `CORE_DECISION_REQUIRED`) and `_complete_core_decision(result, *, tool_func, submitted: dict, fixes_for: Callable[[dict], dict], message: str) -> dict` (for each fragment, `build_corrected_call(tool_func, submitted, fixes_for(fragment))`, then message and `corrected_calls` replaced on that entry). The consolidation wrapper keeps its regex and its `items[i]` merge as `fixes_for`; the replacement wrapper runs AFTER the public error remap (so the error field already reads `memory_id`), passes `fixes_for=lambda fragment: fragment` and `submitted` = the call as received (`memory_id`, `title`, `reason`, `content`/`content_file_path`, ..., `core` as `model_dump(exclude_none=True)`), error field `memory_id`, message in the tool's words (core = keep the result core with reason and exit_condition and re-declare the details in `core.detail_memory_ids`, naming them in the content; demote_core = let the result become an ordinary memory). Behaviour of the consolidation path is unchanged (S3a tests).
- D11 Dispatch (`_dispatch_replacement`): reads `retrieval_text` and the core fields, builds `ReplacementRequest` with a `CoreDeclaration` only when a core field or `is_core` is present, validates with the existing `_DispatchValidationError` pattern, calls `replace_memory`.
- D12 Existing tests: the authorised assertion changes are (a) public tool calls `entity_id`→`memory_id`, `old_id`/`new_id`→`predecessor_memory_id`/`successor_memory_id` in the MCP-level tests (`test_mcp_tools.py`, `test_trace_mcp_tools.py`, `test_large_content_file_transport.py`, `test_phase4_mcp_surface.py` and any other test that calls the tool functions or `call_tool`), (b) tool calls that omit `reason` get one, (c) trace-hook fixtures (`hooks/tests/test_trace_capture_copilot.py`). Service-level tests (`test_lifecycle_replacements*.py`, `test_provenance.py`) keep their keys; any change there is reported and justified. Every changed assertion line is listed in the developer report.
- D13 Complexity (measured 2026-10-22 with complexipy; bounds this slice may reach): `_replacement_operation` 10 (bound 12), `_replacement_write` 2 (bound 6), `_replacement_insert_entity` 4 (bound 8), `_replacement_response` 4 (bound 6), `_replacement_repoint_edges` 9 (bound 11), `_dispatch_replacement` 3 (bound 8), `_to_public_write_result` 8 (bound 9), `_remap_public_errors` 4 (bound 5), `_complete_consolidation_core_decision` 11 (bound 11, after the split every part at or below 8), `_consolidation_core_state` 5 (bound 5), new functions at or below 10. No new suppressions, no threshold gaming: the split follows responsibilities (find the error, complete the call).
- D14 Docs: `docs/architecture.md` one sentence (replacement and core). Backlog rows and parent amendment 5 are the architect's, committed with the lock. `skills/saltmdb-usage/SKILL.md` and `README.md` examples are S5 (BL-058).
