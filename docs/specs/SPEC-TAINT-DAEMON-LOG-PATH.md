## 1. Why

`_spawn_daemon_process` creates a directory and opens a log file at `dirname(db_path)/daemon.log`. The consultant's survey (m_2654) judged this a scanner artifact for the default setup, because `db_path` is the invoking user's own setting and may legitimately be anywhere, so no containment check against a fixed base can be applied without breaking valid setups. The owner chose to remove the dependence on user text: the log location is derived from the daemon key (`sha256(realpath(db_path))[:16]`, already the identity used for the discovery file and the election port) under `~/.saltmdb/logs/<key>/daemon.log`. This has side benefits: the log no longer lands in a database directory that may be shared or world-readable, it is created `0600` in a `0700` directory, and the log path has ONE definition (today it is computed twice, in `client._daemon_log_path` and in `server._daemon_log_redirect`, which must agree). Behaviour change for users: the log is no longer next to the database; the docs and the failure messages say where it is. Old `daemon.log` files stay where they are (no migration, no deletion). Whether Sonar's taint engine treats a hash-derived path as clean is not proven; if the two issues stay open, the architect reports them to the owner.

## 2. Decisions

- D1. In `discovery.py` add the single source of truth: `daemon_log_path(canonical_db_path: str) -> str` returning `~/.saltmdb/logs/<daemon_key(canonical_db_path)>/daemon.log` (the base from the same `expanduser("~/.saltmdb")` the discovery code uses), and `open_daemon_log(canonical_db_path: str) -> IO[str]` that creates the directory with `os.makedirs(directory, mode=0o700, exist_ok=True)` and opens the file append-only with owner-only permissions: `os.fdopen(os.open(path, os.O_WRONLY | os.O_CREAT | os.O_APPEND, 0o600), "a", encoding="utf-8")`. The file name stays exactly `daemon.log` (existing tests and messages assert the substring `daemon.log`). Both helpers take the CANONICAL path; callers pass `discovery.resolve_canonical_db_path(db_path)`.
- D2. `client.py`: remove `_daemon_log_path`; `_read_daemon_log_tail` reads `discovery.daemon_log_path(...)` (the two fallback strings keep their text); `_spawn_daemon_process` uses `discovery.open_daemon_log(...)` instead of `os.makedirs` and `open`; `_intermediary_main` (the win32 launcher) configures its logger on the handle from `open_daemon_log` (`logging.basicConfig(stream=handle, ...)`, same level and format) because the directory must exist before `basicConfig` runs; open the handle only when `not logging.getLogger().handlers` (`basicConfig` is a no-op when the root logger already has handlers, which is the case under pytest, and an unused open handle would leak); never use `force=True` (it would strip pytest's capture handlers). Every client helper that needs the log path (`_read_daemon_log_tail`, `_spawn_daemon_process`, `_intermediary_main`) calls `discovery.resolve_canonical_db_path(db_path)` itself instead of trusting its caller (idempotent `realpath`; two callers pass their own `db_path` parameter and the intermediary gets `argv[2]`). No other change in `client.py`; the Windows creation flags and the Popen keyword arguments are untouched.
- D3. `server.py`: `_daemon_log_redirect(db_path)` uses `discovery.open_daemon_log(discovery.resolve_canonical_db_path(db_path))` and assigns the handle to `sys.stdout` and `sys.stderr` as today; its docstring says where the log is now.
- D4. `service.py`: the three user-facing strings that say "see daemon.log" (about lines 224, 266 and 337) name the real path (`see {discovery.daemon_log_path(canonical_db_path)}`) and still contain the substring `daemon.log`. Existing tests: `tests/test_daemon_service.py` 301 and 406 are `assertIn("daemon.log", ...)` substring checks and keep passing; 429-433 is an `assertEqual` on the full string `"failed to spawn persistent daemon: spawn denied; see daemon.log"` and MUST change, because the message now carries the real path: this is the ONE permitted existing-assertion change; the new expected value is built from the same helper in the test (`f"... see {discovery.daemon_log_path(<canonical path used by the test>)}"`), with no other change to that test.

The new test file asserts, with literal expected values and a temporary `HOME`: `daemon_log_path` equals `<home>/.saltmdb/logs/<daemon_key>/daemon.log` for a canonical path; two different canonical paths give two different log paths; the path contains no component of the database path; a hostile database path (containing `..`, spaces and a newline) still yields a path under `<home>/.saltmdb/logs/`; `open_daemon_log` creates the directory `0700` and the file `0600` (the test sets `os.umask(0o022)` itself and restores it in a `finally`, and chmods nothing), does not change the mode of an existing directory, and appends: with TWO handles open at the same time, write `A\n` through the first and flush, then `B\n` through the second and flush, and the file must read `A\nB\n` (sequential opens in append mode pass even without `O_APPEND`; concurrent handles are the real situation, because the spawning client, the win32 intermediary and the daemon's own redirect all write to the same file); `_read_daemon_log_tail` returns the last lines of that file and the existing fallback text when it is missing; `_spawn_daemon_process` with `Popen` patched passes a handle whose `.name` is the new path as `stdout` and `stderr`; `_daemon_log_redirect` points `sys.stdout` and `sys.stderr` at that path (restore both in `finally`); the three `service.py` messages contain the new path.
