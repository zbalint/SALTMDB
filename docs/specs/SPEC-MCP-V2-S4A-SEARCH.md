## 1. Why

`search_memory` is the most used tool and the only one that still returns a bare list, which the parent design (R4) forbids, and its default result is heavy: every item carries a per-item `cursor`, `weight`, a long `relevance_preview` with a warning prefix, `related_entities` (default on) and `trace_evidence_count`, while pagination has no `has_more` signal ("an empty next page is your only indicator"). A fault is reported as a one-item list `[{"error": ...}]` that callers must detect by the missing `id` key. The parent spec D7 asks for: an envelope, compact items by default, `detail` to opt in to the longer preview, `has_more` and `next_cursor`, the parameter named `query`, and `memory_id` instead of `id`.

## 2. Decisions

- D1 Signature (adapter, `mcp/tools.py`): `search_memory(query: str | None = None, limit: Annotated[int, Field(ge=1, le=50)] = 5, cursor: str | None = None, context_id: str | None = None, agent_session_id: str | None = None, tags_filter: Annotated[list[str], Field(max_length=20)] | None = None, memory_type_filter: Literal[...] | None = None, is_core: bool | None = None, include_related: bool = False, mode: Literal["strict","broad","history"] | None = None, detail: Literal["compact","preview"] = "compact", return_diagnostics: bool = False) -> dict` (12 parameters). Renames: `query_keywords` becomes `query` (adapter-level, R9; the service keeps `query_keywords`); a call with the old name is rejected by the guard as a removed field (R8). New bounds (rule: bound every input size): `limit` is `Annotated[int, Field(ge=1, le=50)] = 5` (not nullable; the guard maps a range error to `VALIDATION_ERROR` on `limit`); `cursor` must match `^offset:(0|[1-9][0-9]{0,3})$` and its offset must be at most `MAX_SEARCH_OFFSET = 1000` (a constant in `mcp/tools.py`), otherwise `VALIDATION_ERROR` on `cursor` (the offset feeds the candidate window and the vector k directly, so it is a size an untrusted caller controls); `tags_filter` has at most 20 entries (`Field(max_length=20)`, each entry becomes SQL bind parameters). In strict mode nothing beyond `STRICT_OVERFETCH_CANDIDATE_CAP` (200) is reachable, so a deeper page there is an empty page with `has_more` false. The daemon RPC dispatcher `_dispatch_search_memory` keeps its own unbounded `limit` and its `include_related=True` default: internal callers use it and this slice must not change it. `include_related` now defaults to False (it was True: related entities dominate the default payload); the description says so.
- D2 Result (always an envelope). Success: `ok({"items": [...], "has_more": bool, "next_cursor": str | None})`, plus `"diagnostics": {...}` inside `data` when `return_diagnostics` is true. `next_cursor` is `offset:<offset + limit>` when `has_more` is true and `None` otherwise. `has_more` is computed by the adapter: it calls the service with `limit + 1`, returns the first `limit` items and sets `has_more` when the service returned more than `limit`. Contract (state it in the description): while `offset + limit + 1 <= RERANK_CANDIDATE_POOL_SIZE` (20, `config.py`) the first `limit` items equal those of a plain `limit` call; beyond that the candidate window is `max(offset + limit, 20)` and a wider window can reorder results, the same property every offset cursor already has (each page recomputes its own window), so paging is deterministic per page for an unchanged corpus but not guaranteed duplicate-free or gap-free past 20 candidates. In broad mode `has_more` means "more ranked candidates exist", not "more relevant hits" (the vector channel always returns its k nearest, so it stays true until the corpus is exhausted). With `return_diagnostics` the adapter overwrites `diagnostics["result_count"]` with `len(items)` (the service counted `limit + 1`). A strict-mode abstention is `items == []`, `has_more` false, and carries a warning `{"code": "NO_MATCH", "message": "mode=strict returned no hit that passed the relevance gate; ..."}` (the adapter cannot tell a gate abstention from no candidates at all; the hook keys on the code, D6). `NO_MATCH = "NO_MATCH"` is added with a docstring to `src/saltmdb/utils/error_codes.py` (today it defines only `VALIDATION_ERROR`, `NOT_FOUND`, `ALREADY_DONE`, `CONFLICT`, `INTERNAL_ERROR`). A service fault (`[{"error": ...}]`, or the `error` key of the diagnostics shape) becomes `rejected([error("INTERNAL_ERROR", message)])` and drops the diagnostics.
- D3 Compact item (default): `memory_id`, `title`, `snippet`, `score`, `memory_type`, `is_core`, `created_at`, and, only when present, `drift_flag` and (history mode) `is_superseded`. Removed from the default item: `weight`, the per-item `cursor`, `relevance_preview`, `relevance_preview_meta`, `related_entities` (unless `include_related`), `trace_evidence_count`, `cross_encoder_score`. `detail="preview"` adds `relevance_preview` and `relevance_preview_meta` (the service output, unchanged) and `trace_evidence_count`. `include_related=True` adds `related_entities` in either detail level. The service still computes previews and trace counts that compact mode discards (accepted cost; no service change). Deviations from the parent D7 text, recorded in amendment 6 (together with the note that `search_traces` keeps `query_keywords` until S4c): the item has no `status` and no `successor_memory_id` because search never returns an archived memory (`_build_search_filters` starts from `e.status != 'archived'`), so `status` would always be the active value (apart from legacy `consolidated` rows no writer produces); a live-but-superseded hit in history mode is already marked by `is_superseded` and its lineage is one `get_memory` call away.
- D4 Service: the only change is that `_base_search_item` adds `"created_at": _created` (the value is already selected and unused, `orchestrator.py` around line 1177). The service signature and every other output are unchanged, so the 24 test files that call the service directly are untouched.
- D5 Description: first sentence "Use this to find memories by text or filters; use get_memory when you already have an id and retrieve_context to expand around hits."; it states the `mode` values (`broad` default, `strict` abstains with an empty result, `history` keeps superseded hits labelled), that results are ranked by relevance and the best answer may not be first, the `is_core` filter trap (a missing core hit is no evidence that no rule exists), that `agent_session_id` matches the CREATION session only, that `has_more` and `next_cursor` page the results, the item fields, that `detail="preview"`/`include_related` are opt-in, that results after the first 10 are not reranked by the cross-encoder, and the `has_more` contract of D2. The old long diagnostics text is condensed to the field list location.
- D6 Hook: `hooks/saltmdb-post-tool-response-nudges.py` `handle_search_memory` detects an empty strict result by the literal substring `NO_MATCH` in the response text plus its existing check that the request `mode` is strict, and `EMPTY_RESULT_PATTERN` is deleted (a substring survives every harness's response wrapping: a structured dict, a content-block list or JSON escaped in a string; parsing `data.items` would depend on the harness, and the hook serves Claude, Codex and Copilot). It must not raise on a non-envelope response (`hooks/tests/test_retrieval_outcome_flow.py` feeds `{"result": []}` at lines 167, 195, 222). Its tests are updated. No other hook reads search results (grep, section 8).
- D7 Existing-test changes (line numbers below are as of `f88ecb4` and have drifted after S3c: the test NAMES govern, find them by name; categories; no assertion is weakened, an assertion that encodes the old contract is inverted or re-read through the new shape and named here): (a) `tests/test_mcp_tools.py`: `test_search_memory_rejects_unknown_query_argument` (lines 1884 to 1889) asserted that `query` is an unknown field and is inverted (`query_keywords` is `UNKNOWN_FIELD`); the test at 1891 to 1900 uses `query` and reads `data.items[0].memory_id`; call sites at 62, 570, 588 and the diagnostics test from 1902 read `data.items`; the owner-tools tuple at line 81 stays; (b) `tests/test_mcp_guard.py`: line 133 to 135 probes `query_keywords` and now expects `UNKNOWN_FIELD`, so it probes `query`; the `_SKIP_REASONS["nullable"]["search_memory"]` entry (line 37) is removed because the generic null test now has a non-nullable field to probe (`limit`), the `"required"` entry stays; (c) `tests/test_relevance_preview.py` lines 111 to 125 read `relevance_preview`, which compact mode removes: the calls gain `detail="preview"` (the D3 contract, not a weakening); `tests/test_session_identity.py` and `tests/test_search_memory_drift_flag.py` read `data.items`; `tests/test_phase3_mcp_surface.py` lines 43 to 46 pass unchanged; (d) `tests/test_search_memory_characterization.py` lines 446 to 481 (and any other whole-dict equality over a service item) gain the `created_at` key with the fixture's value, no other change; (e) hook tests per D6. Service-level tests otherwise stay. Any other existing failure is reported, not fixed silently.
- D9 Guard rename map. `build_corrected_call` keeps only current parameters, so the `corrected_call` of an UNKNOWN_FIELD rejection silently drops a renamed field: `search_memory(query_keywords="x")` would be answered with a ready call that has no query, which is a valid browse and looks like an answer. `mcp/guard.py` gains `RENAMED_FIELDS: dict[str, dict[str, str]] = {"search_memory": {"query_keywords": "query"}, "revise_memory": {"entity_id": "memory_id"}, "supersede_memory": {"entity_id": "memory_id"}, "review_core_memory": {"entity_id": "memory_id"}}` (the renames shipped in S3b, S3c and this slice; later slices extend it). `_unknown_fields` passes `{new: submitted[old]}` as the `fixes` argument of `build_corrected_call` for each submitted old name and appends \" It was renamed to '<new>'.\" to that field's message. Test: the corrected call of `search_memory(query_keywords="x")` carries `query`, and `revise_memory(entity_id=...)` carries `memory_id`; a call that already has the new name keeps it.
