## 1. Why

The three graph read tools still speak the old vocabulary and shapes: `entity_id`/`entity_ids` parameters, `id` inside nodes, `entity_id` in `retrieve_context` memories, `parent_ids`, and `include_inspect` (named after a tool that no longer exists). `retrieve_context` has a bespoke success shape with no envelope and two modes selected by `strategy`/`query` although the parent design keeps only the id-anchored mode. `get_related_memories` returns two names for one count (`total_dependencies_found` and `total_related_found`, which counts edges although it reads like a memory count) and an `entity_id` echo; `get_lineage` has an unlabeled `total`. `max_depth` is an unbounded integer from an untrusted caller. After this slice every read tool that returns a memory speaks `memory_id`, so a `memory_id` taken from any read result can be pasted into any other tool.

## 2. Decisions

- D1 `get_lineage(memory_id: Annotated[str, Field(min_length=1, max_length=200)], direction: Literal["ancestors","descendants"] = "ancestors", max_depth: Annotated[int, Field(ge=1, le=10)] = 5) -> dict`. Same traversal and same `ok(...)` envelope. Data keys: `memory_id` (was `entity_id`), `direction`, `root`, `nodes`, `edges`, `total_edges` (was `total`: it is the edge count, `total_nodes` counts nodes), `total_nodes`, `graph_exhausted`, `point_in_time`, `max_depth`. In `root` and every item of `nodes` the key `id` becomes `memory_id` (helper D6). Edge items keep `relation_id`, `source_id`, `target_id`, `predicate`, `depth`, titles and statuses: `source_id`/`target_id` name relation endpoints exactly as in `manage_relation` and are not renamed.
- D2 `get_related_memories(memory_id: Annotated[str, Field(min_length=1, max_length=200)], max_depth: Annotated[int, Field(ge=1, le=10)] = 5, direction: Literal["outbound","inbound","both"] = "both", include_summary: bool = False) -> dict`. `include_inspect` is renamed `include_summary` (same behaviour: each node carries the summary fields of `get_memory(detail="summary")`, no content, no lineage, no `last_accessed_at` bump). Data keys: `memory_id` (was `entity_id`), `root`, `related_memories`, `edges`, `total_edges`, `graph_exhausted`, `point_in_time`, `max_depth`. The count is the number of EDGES found (not memories; `related_memories` also holds the depth-0 root): `total_related_found` and `total_dependencies_found` (both equal `len(edges)`, `relation_service.py:1209`, `:1640`) are replaced by the single honest name `total_edges`. `root` and EVERY `related_memories` item (the depth-0 root included, with or without `include_summary`) are renamed with the record helper of D6: `id` to `memory_id` and, in summary items, `parent_ids` to `parent_memory_ids`. Edge items are unchanged.
- D3 `retrieve_context(memory_ids: Annotated[list[Annotated[str, Field(min_length=1, max_length=200)]], Field(min_length=1, max_length=20)], budget_tokens: Annotated[int | None, Field(ge=1)] = None) -> dict`. The query mode and the `strategy` parameter leave the agent tool: the tool is always the local, id-anchored strategy (the daemon method and the service keep the global strategy; removing that dead code is BL-076, out of scope here). Success is `ok(data)` where `data` is today's local payload with these renames (helper D6): `entity_ids` becomes `memory_ids`; each `memories[]` item `entity_id` becomes `memory_id`; in `lineage` the dictionary keys (head ids) are unchanged, and `current.id`, `historical[].id` become `memory_id`; in `conflict_sets[]` each `members[].id` becomes `memory_id` (the set id `cs-n` and edge `source_id`/`target_id` keep their names); in each `memories[].retrieval_provenance[]` entry `origin_hit_id` becomes `origin_memory_id` and `orphan_entity_id` becomes `orphan_memory_id`; the lineage field `contradicted_with` (a list of ids) keeps its name. Everything else (`inclusion`, `retrieval_provenance`, `edges`, `metadata`) is unchanged. Rejections already use the standard envelope (dispatcher `dispatch.py:856-860` and service `retrieve_context_service.py:39,48,56,76,86` set `field` to `entity_ids`); `_remap_public_errors` (`tools.py:1406`) takes a per-tool field map `{"entity_id": "memory_id", "entity_ids": "memory_ids"}` (its signature is extended, no second helper) and `retrieve_context` joins `_ERROR_FIELD_REMAP_TOOLS`; the error message texts (for example "No memory matches entity_id '...'") stay unchanged, as in S4b. Adapter result handling for `retrieve_context`, one branch each and one test each: a dict WITHOUT `status` is the success payload and becomes `ok(context_data(result))`; `status == "rejected"` gets the error-field remap; any other dict WITH a `status` (the adapter's own `DAEMON_STARTING` and `DAEMON_CONNECTION_LOST_DURING_WRITE`, `tools.py:237-275`) is returned unchanged; a non-dict becomes an `INTERNAL_ERROR` rejection.
- D4 The adapter passes the caller's `memory_ids` to the daemon as `entity_ids` (R9: RPC names stay) with `query=None` and `strategy="local"` fixed, so the daemon and service contracts are untouched.
- D5 `mcp/guard.py` `RENAMED_FIELDS` gains `"get_lineage": {"entity_id": "memory_id"}`, `"get_related_memories": {"entity_id": "memory_id", "include_inspect": "include_summary"}`, `"retrieve_context": {"entity_ids": "memory_ids"}`. `query` and `strategy` on `retrieve_context` become plain unknown fields (the rejection lists the valid fields and its message says the tool takes anchors only: find them with `search_memory` first). `build_corrected_call` keeps only real parameters and drops nulls, so `{query: "q"}` alone yields `corrected_call == {}` (not resubmittable, memory_ids is required): pinned by a test, no placeholder is added; `{strategy: "local", entity_ids: [x]}` yields `{"memory_ids": [x]}`.
- D6 One small module `src/saltmdb/mcp/public_shapes.py` owns every public-shape rename of node-like structures, so no tool re-implements one: `lineage_node(node) -> dict` (`id` to `memory_id`, other keys unchanged, input not mutated), `memory_record(data) -> dict` (`id` to `memory_id`, `parent_ids` to `parent_memory_ids`, and `lineage_view` when a `lineage` is present: the ONE record rename, used for `get_memory`, for every `get_related_memories` node including the root, and, through them, `get_memories` items), `lineage_view(view) -> dict` (maps `lineage_node` over `ancestors` and `descendants`), `lineage_data`, `related_data`, `context_data` (the full data renames of D1 to D3; `context_data` may split into small private helpers, one per structure). `_remap_public_data("get_memory", ...)` (S4b) calls `memory_record`, so a `get_memory`/`get_memories` record is fully `memory_id`-based and the temporary inconsistency named in parent amendment 6 ends. Every function is pure, never mutates its input and is total on a missing key; the only size gate is D9 (no separate branch-count rule).
- D7 Descriptions (first sentences): `get_lineage`: "Use this to see where a memory came from or what replaced it (revision, supersession, consolidation history); use get_related_memories for manage_relation edges." `get_related_memories`: "Use this to walk the relations you created with manage_relation from one memory; use get_lineage for revision history and retrieve_context for a ready budgeted bundle." `retrieve_context`: "Use this when you already hold anchor ids and want their connected context (graph neighbours, contradictions, lifecycle history) packed into a token budget in one call; use search_memory first to find the anchors." The retrieve_context description keeps the correctness constraints and drops the strategy prose: no item carries body content (call `get_memory` for what you will cite), a too-small `budget_tokens` can drop an anchor (check `metadata.budget.primary_dropped_count`), `edges` lists only relations between two of your anchors, `inclusion` is `primary`, `expansion`, `conflict_only` or `orphan_community`, an unresolvable or ambiguous anchor rejects the whole call, private memories of other agents read as unknown. `get_related_memories` states that `total_edges` counts edges. Target about 1000 characters each.
